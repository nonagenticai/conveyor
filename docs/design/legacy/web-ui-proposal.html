Design for review

Conveyor Web UI

A working surface for a system that runs work, stops at gates, and has to prove it is getting better. Simple on arrival. Deep on request.

Not implemented Leptos CSR · ADR 0001 23 screens · 9 destinations Wave 3 panels are planned

The thesis

Conveyor's server is not a set of resources with endpoints. It is 189 actions behind one dispatcher, one tenancy model, and three channels — web, Telegram, MCP. The same authorization decides all three. That fact should shape the UI, not hide inside it.

So the app is not a CRUD console with a sidebar of entities. It is three loops: what needs a human, what the work is, and whether the machine is improving. Everything else — procedures, members, permissions, the action registry — is configuration of the machinery that serves those loops.

The design's central move is that configuration never crowds the working view. One global Advanced switch deepens every screen at once, and ⌘K reaches every action the caller's role permits. A screen that lacks a knob is not a dead end; the registry is one keystroke away.

Six principles

Each one has a mechanical consequence, not just an intention.

01

The registry is the contract

Every control names the action it invokes. The app bootstraps from GET /api/actions and renders only what the caller's role can reach.

Consequence: no hidden mutations, and an action shipped today is reachable today.
02

One switch, not twenty panels

Advanced is global. It reveals object IDs, versions, the action behind each button, and a raw-JSON inspector — everywhere at once, consistently.

Consequence: no per-screen "advanced settings" sections to build or to learn.
03

⌘K is the escape hatch

Fuzzy over screens, objects and every permitted action. Picking an action renders its input schema as a form, with a JSON mode beside it.

Consequence: fine-grained configuration has a guaranteed home, so screens can stay simple.
04

One route per object

A card is always /board/:id/card/:id; a run is always /runs/:id; an eval report is always /evals/:id/report.

Consequence: links are shareable and every deep view is a destination, never a modal.
05

Decisions are the product

An approval is the one human primitive, answerable from web, Telegram or MCP. It gets an inbox with age and staleness, and it does not expire on its own.

Consequence: "waiting 6 days" is visible, so a stalled project is a choice, not an accident.
06

State is shown, never implied

Every async surface renders its position in the state machine and its last update time. No spinner stands in for a state.

Consequence: a queued run and a dead run never look the same.

Three depths

The same screen at three levels of detail. Depth is a user choice, not a separate route tree.

Depth 1 · default

Do

One screen answers one question. A row shows what it is, who owns it, and what state it is in. No IDs, no versions, no JSON.

Depth 2 · on selection

Inspect

Selecting any object opens the right-hand inspector: its detail, its history, and the actions you can take on it. The list stays where it was.

Depth 3 · the switch

Configure

Advanced deepens every screen: IDs, versions, the action name on every control, and a raw payload tab. ⌘K opens any action as a generated form.

RBAC: what the two screens require

Today the permission table is compiled into the binary. The screens make it tenant data, with the compiled table as the default.

Today

Five fixed roles

admin (the tenant-admin), member, viewer and the machine role kata_executor. There is no owner role: the tenant owns itself, and a single-user tenant's user is tenant-admin by default. 63 scopes are compiled: reads open to all, work writes for member and up, administration writes for admin and up.

A tenant admin cannot change any of it today.
Proposed

Defaults plus a tenant policy

A new tenant_role_scope row overrides one (role, scope) pair. No row means the compiled default, so a fresh tenant stores nothing and the screen starts truthful.

Admin and kata_executor are compiled — Admin so a tenant cannot lock itself out, kata_executor because a machine role is not a person's to edit.

Risk · the manifest has no precondition flag

Open questions

Three, each with a default so work is not blocked on an answer.

  1. Invite and remove. No action exists and there is no just-in-time provisioning — an unknown identity is refused rather than created. Default: ship Members with role changes only, and add invite/remove as a follow-up bounded to existing users.
  2. Owner versus admin — settled (2026-11-09). There is no owner: the tenant owns itself and admin is the tenant-admin. A sole member is tenant-admin by default, and a tenant must always keep at least one admin.
  3. Today as a destination. It has no S12 row of its own. Default: record it as a UI-only contract-change request rather than adding a screen the plan does not declare.
