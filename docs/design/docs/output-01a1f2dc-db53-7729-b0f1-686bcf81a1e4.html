Principles

P1 — One model, one store, one action registry

Statement. A programme, its projects, their work, their decisions and their evidence are rows in one Postgres database written through one action registry; a concept has one table and one set of actions.

Rationale. The estate's pain is distributed fragments of one model; one registry makes permission, audit and replay uniform, and its exact set is asserted by its own test.

Implications. A new capability is a table plus actions in this workspace, not a new service; no feature keeps a private file or cache as its record of truth.

Evidence. crates/actions/src/lib.rs; migrations/*.sql; crates/actions/tests/registry.rs.

P2 — Every mutation is an action; the database is not the API

Statement. A write goes through an action with its scope, tenant, precondition and event; no handler, UI or script writes rows by SQL.

Rationale. RFC 9457 errors, If-Match/_version preconditions, revision history and audit hang off the action envelope; a SQL write bypasses every one of them.

Implications. A new write is an action with a schema, a scope and a test; a read-only probe is BEGIN READ ONLY.

Evidence. crates/actions/src/invoke.rs; crates/actions/tests/registry.rs:committed_action_dump_matches_the_registry.

P3 — Tenant isolation is structural, not a filter

Statement. Every tenant-owned table has RLS enabled and forced, and every query runs under the tenant's scope; a cross-tenant id resolves to 404.

Rationale. The store's begin_scoped is the only path that sets the tenant GUC; a filtered query is one forgotten predicate away from a leak.

Implications. A new table ships with its policy in the same migration and a foreign-tenant 404 test; a session-level GUC through a pooler is forbidden.

Evidence. crates/store/src/scope.rs; crates/actions/tests/registry.rs:a_foreign_tenant_parent_id_resolves_to_404_never_to_a_write.

P4 — Publication is a decision, never a side effect

Statement. A row is public only when an admin's publish decision makes it public; an author's write never publishes and author markup is never executable on the public page.

Rationale. The executor never approves its own work; documents.publish is the only action that moves the public bit, and the renderer neutralises raw HTML.

Implications. A new public surface filters on the public bit and carries the tenant; preview uses the same renderer as the public page.

Evidence. crates/actions/src/documents/revisions.rs; crates/render/src/markdown.rs.

P5 — Every output is versioned, attributable and reversible

Statement. A text output carries its author, a content hash and a revision history; every edit is versioned and a restore copies a version forward.

Rationale. The programme is judged on its intermediate work products; an output a reviewer cannot trace to author, version and evidence is not auditable.

Implications. A new aggregate that holds work products reuses the document model or carries the same provenance; deletion is a tombstone.

Evidence. migrations/0042_document_workflow.sql; crates/store/src/document.rs.

P6 — Programme truth is computed, never hand-written

Statement. A project's status, units, dependencies and expected outputs come from measured sources and are regenerated by scripts; a checklist is derived from the standard.

Rationale. A hand-written status is the first thing to rot; the standard generates every project's expected set and the pack is built from the tree.

Implications. A new programme fact gets a generator and a --check gate; a document may explain the truth but may not be its only home.

Evidence. scripts/build-coverage.py; scripts/build-programme-seed.py; scripts/check-output-standard.py.

P7 — Gates refuse; a gate that never refuses is broken

Statement. A quality gate is a refusal with an actionable reason, exercised by a test that proves the refusal; a gate that never refused in a full cycle is treated as broken.

Rationale. The programme's publish and dependency gates exist because a publish without evidence happened; a refusal is the product, not an error path.

Implications. A gate names what is missing and offers the next step; a refusal is covered at the boundary the caller uses.

Evidence. crates/actions/tests/authoring_standard.rs; the 409 blocked_by gate in crates/actions/src/programme.rs.

P8 — Typed dependencies, explicit gates

Statement. A dependency between projects is typed and the programme gate enforces the blocking kind; a tranche review is a programme decision on evidence.

Rationale. Untyped coupling hides the order the programme actually needs; the gate answers 409 blocked_by naming the open dependency.

Implications. A project's inception names its dependencies and the contract it sits under; a deviation is a decision record.

Evidence. migrations/0044_plan_spine.sql; crates/actions/tests/plan_spine.rs.

P9 — Secrets never leave their boundary

Statement. A secret is write-only; no action returns its value, and no secret, token or private host enters the public repository or a published output.

Rationale. The repository is public, so a leak is permanent; the secret aggregate stores only a sealed form.

Implications. A credential is referenced, never printed; a public output and the snapshot are scanned before publication.

Evidence. crates/actions/src/documents/secrets.rs; scripts/ci/no-private-refs.sh.

P10 — The estate is one deployable service per concept, absorbed not duplicated

Statement. A service the organisation depends on is either this workspace's own code or an absorbed, contract-tested module behind an action; a second deployment of the same concept is retired.

Rationale. ADR 0005 fixes the absorption sequence; the public repository cannot carry a hidden dependency on a private host.

Implications. A new integration adds an action and a client in this workspace; a retired service's data is migrated, not forked.

Evidence. docs/decisions/0005-absorption-sequence-and-repo-scope.md; crates/actions/src/ops/.

Application

Every principle names the code or gate that enforces it. The realization record is the Principle Realization Diagram (01a1f2c1-9c75-78a2-a2a4-647687dfbe10, diagram, approved version 2), linked by a realization link: all ten principles have an entry naming a file or gate above, because a principle with no realization is a slogan.

The Principle Derivation Diagram (01a1f2c1-94ad-7a92-8aca-57202f48ece9, approved version 2) carries the derivation link; its seven entries map B1, B2, B4, B5 and B6 to principles, and B3 has none — the gap it exists to show.

A deviation is an architecture_waiver approved by the board, never a silent fork: it names an accepting owner, reason, cost, risk and reassessment date; the board cannot waive a deviation it owns, and the delivery gate refuses a dated waiver without an owner (criterion D4 of the Phase A contract).

The board meets at each tranche review and on a contract request. A principle no project applied, or a gate that never refused in a full cycle, is evidence that the principle or the gate is wrong; the correction is a recorded decision, never an edit to an approved body.
