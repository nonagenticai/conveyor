Project: T11 — Metrics, metering and maturity · Track: v2 · Tranche: 1 · Plan: docs/SPEC_V2.md §12 Unit: #84 (this design is dependency-shaping work; blocked-by P0 only) Measured at: main@61edfcf8, 2026-11-18 · Project row: active, meta.depends_on = ["P0"]

Context and boundary

T11 owns the measurement layer over the conveyor's own rows: the §7.5 metric families (flow, quality, cost, governance, knowledge), D52 metering roll-ups and drill-down, C0–C5 maturity with configured thresholds (D37), billing reconciliation and the never-refused gate flag. It is continuous: it starts once T0/T1 supply attribution (run.job_binding_id, department, wbs_node) and grows as other slices add source rows.

It must not duplicate:

  • analyse.* — measures the subject of a project; T11 measures this system's process (§10.4.1).
  • the eval and benchmark instrument — S17–S20 own definitions, versions and sign-offs; T11 reads and never edits an instrument that judges it (§9.3).
  • billing_service — charging stays there; T11 reconciles, and a divergence opens an incident.
  • the inference-router's ledger — each service keeps its own; T11 reads the conveyor's inference_call, never another service's database.
  • the portfolio read model (D49) — T11 supplies numbers; it does not own the in-flight set.
  • T9's architecture_maturity — a capability assessment, not process maturity.

It fits the blueprint: one Postgres, one action registry, no new port (8930), no second frontend runtime; the console reads the same derivation the API serves.

Invariants:

  1. No stored metric or cost. Every response names its source rows and the threshold or price version; recomputing twice gives the same figures and writes nothing.
  2. Partition. Every call lands in exactly one bucket; buckets sum to the tenant total; unattributed calls are reported separately.
  3. Recorded joins only. A call belongs to its run → card → project → programme; job attribution is run.job_binding_id; department is the binding's primary department, with others as a breakdown, never an invented split.
  4. A level changes only through an assessment. No action sets a level; crossing a recorded threshold with new evidence is the only transition.
  5. A divergence is an incident. A non-zero delta produces a divergent row and an incident card; no retry loop.
  6. Minimum sample. A gate below the configured minimum is "no signal", not "never refused".

Events (to create): metric.flagged, maturity.level_changed, billing.reconciliation_diverged.

Decisions

  • D-T11-1 — read models, not stored metrics. Alternative: materialised daily roll-ups. Consequence: each read is windowed and indexed, and a recompute test is mandatory (D37).
  • D-T11-2 — thresholds are versioned tenant configuration with platform defaults. Alternative: constants in code. Consequence: calibration is a data change, not a deploy (D37, D50).
  • D-T11-3 — price history is versioned. Alternative: the current commercial_price row. Consequence: a migration adds commercial_price_version and backfills one row per model, making history reproducible (§7.5, D52).
  • D-T11-4 — reconciliation is exact at the billing grain: tenant × UTC day × project × actor × app × provider × model, on tokens and money. Alternative: a percentage tolerance, or a coarser grain at which project, actor and app differences net out unflagged. Consequence: T11 compares at the charging system's own grain, and every coarser view is a sum of reconciled rows; any unexplained difference opens an incident, so boundaries are fixed and tested (§7.5, §12 T11).
  • D-T11-5 — maturity is its own aggregate. Alternative: thresholds inside metric_definition. Consequence: maturity needs immutable assessments, evidence refs and supersession (D37).
  • D-T11-6 — C0–C5 is process maturity over the measured families; the nine-dimension assessment stays in T9's architecture_maturity. Alternative: merge them. Consequence: two instruments, each with one owner, labelled distinctly in the UI (D37, §8.1).
  • D-T11-7 — five actions beyond §10.4's four (metrics.metering, metrics.reconcile, metrics.gates, metrics.config.get, metrics.config.set). Alternative: fold the three reads into the four and keep configuration off the action surface. Consequence: the §10.4 family grows by five and the addition is recorded on the unit's issue, not silently.

Architecture artefacts

The PSA set at inception

  • Principles applied. P1 — one record per fact: every metric is a read model over the one ledger and the one set of gate rows; no figure is stored twice. P3 — no completion without evidence: a maturity level is an assessment carrying its evidence refs, never a stored opinion. P5 — measurement before adoption: a procedure change is judged on an instrument T11 reads and never edits. P9 — every model call is ledgered and budgeted: inference_call is the cost source. P10 — no speculative aggregate: each new table exists because a named action writes it and a gate clause reads it. P11 — thresholds, sample minimums and price history are versioned tenant-scoped rows with platform defaults, not code constants.
  • Requirements. SPEC_V2 §7.5 (the metric families), §9.3 (the eval and benchmark instruments are judged, not edited), §10.4.1 (analyse.* measures a subject; T11 measures this system's process), §11.9 (inference and metering), §12 row T11 (the measured gate); decisions D37, D50, D52.
  • Stakeholder map. The tenant administrator (thresholds and calibration), the PM (flow and gate effectiveness), the billing owner (the reconciliation and its incidents), the programme's governance (maturity evidence), the eval owner (never edited, only read), and the delivery teams whose work is measured.
  • Driver, goal and objective. Driver: the programme cannot claim a benefit or a cost it cannot recompute — a stored figure or a stale price makes the claim unfalsifiable. Goal: every metric and every D52 metering level recomputes from rows, and the reconciliation is exact or opens an incident. Objective: a benefit transition cites a measured delta, and a gate that never refused is visible rather than silent.
  • Solution concept. Read-model actions over the existing ledger, run and gate rows; versioned metric_definition and maturity_threshold rows; immutable maturity_assessment rows that compute their level; commercial_price_version for reproducible cost; one billing_reconciliation row per tenant × period whose divergence opens an incident. No metrics runtime, no time-series store, no new port.

Migration and rollout

  • One lane, one PR. Migrations take the next free number after migrations/0051_tranche_review.sql; no new service, port, Redis or frontend runtime.
  • Order: attribution audit; configuration tables with platform-default seeds; commercial_price_version plus backfill; the metrics.* reads; reconciliation and its incident path; maturity_assessment; the Portfolio, Organisation and Measure panels.
  • tool_call does not exist before T13 (#76): tool spend reports "not recorded", never zero, and its matrix cell stays explicitly empty.
  • Rollback: read actions are removable, configuration rows are retired rather than deleted, assessment and reconciliation rows are append-only and kept.
  • The live proof is the gate recorded on the project as its run and evidence output; this document and its matrix prove nothing alone.
