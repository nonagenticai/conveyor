Context and boundary

T7 owns incident lifecycle and gated writes: open → triage → mitigate → resolve → postmortem, with runbooks as published procedures. It composes built surfaces — the ops read/write handlers (crates/actions/src/ops/reads.rs, crates/actions/src/ops/writes.rs), the host family (crates/actions/src/ops/host.rs), the invoke gate (crates/actions/src/control/approvals.rs:enforce_destructive_gate), andon (crates/actions/src/control/andon.rs:ANDON_ENGAGED) the executable processes (migrations/0035_process_tree.sql:process) and the SOP text (migrations/0035_process_tree.sql:procedure) — on T2 (severity/runbook selection), T4, T13 (#76) and T14 (#83). Out of scope: T11 metrics, the tool catalogue, T6 rollouts, cluster manifests. Boundaries: same binary and port (8930), no second Kubernetes client, no cluster-admin or shell, no second approval store, no runbook table, no flag service.

Aggregates, tables and actions

Rows.

  • incident (to create at #78, §9.2): card_id, service, severity, detected_at, mitigated_at, resolved_at, mitigation_approval_id, mitigation_run_id, runbook_procedure_id, postmortem_asset_id; the card is the work surface, this row the sole record of state.
  • Built: card/card_type (migrations/0002_domain.sql:card), process/process_step (migrations/0035_process_tree.sql:process), approval/approval_policy (migrations/0002_domain.sql:approval, migrations/0050_approval_policies.sql:approval_policy), governed_asset (crates/domain/src/governance.rs:AssetKind::Postmortem) and host_registry (migrations/0048_host_registry.sql:host_registry).
  • tool_call (to create at T13, #76): the ledger for a toolkit-mediated mitigation.

Invariants. I1 one incident per card, card_type.code = 'incident'. I2 severity from the tenant set; an unresolved severity refuses triage (P8), and an unpublished runbook refuses the run. I3 a write mitigation records an approved approval whose target equals the write target. I4 resolution requires mitigated_at and an evidence ref; it never deletes evidence. I5 a postmortem requires resolved_at, is kind = postmortem, and links the incident. I6 the incident row is the only record of severity and timestamps; card.meta holds no copy. I7 writes are namespace-scoped; a destructive action without the tenant's approvals is refused before the backend call.

Events. incident.opened|triaged|mitigated|resolved|postmortemed (to create at #78); built andon.engaged/andon.released; T13's tool.called.

Decisions

D1 — incident as a card satellite with typed columns. Alternative: all fields in card.meta. Consequence: constraints and T11's MTTA/MTTR aggregate over columns; P10 because the metric reads it. Severity and runbook selection stay T2 decisions and a runbook is a published procedure; alternative: an ops policy table and runbook rows. Consequence: thresholds live in decision_policy_refinement, pinned by decision id; T7 stores outcomes, never policy values (P11).

D2 — approval_policy gains required_decisions (default 2 for destructive ops), and a live call requires dry-run evidence on the approval. Alternative: a code constant and caller discipline. Consequence: §6.5 dual control becomes tenant configuration; the invoke gate requires meta.evidence[] to name a dry-run invocation of the same target; one approval authorises the pair.

D3 — flag flip patches one registry-declared ConfigMap key. Alternative: a feature_flag table. Consequence: no second config store; an undeclared key refuses before the API call; configmaps RBAC is a prerequisite.

D4 — the postmortem is a governed asset; detection enters through built webhooks/schedules, CI failure or a person. Alternative: a labelled document and an alert manager. Consequence: the postmortem inherits the governance lifecycle and feeds the kata/lesson loop (§9.4); the gate scenario names its entry.

Architecture artefacts

PSA set at inception

Principles applied (SPEC_V2 §3). P1 one record per fact. P2 rule → laya → human — severity and runbook selection are laya; an LLM never selects or approves. P4 the executor never approves — dual control, approver ≠ requester. P8 fail closed on missing severity, runbook or policy. P10 one new table, read by T11's metric. P11 decision counts, thresholds, flag keys and windows are tenant rows.

Requirements. R1 an incident is a card plus one typed row (§9.2). R2 triage sets severity and selects a published runbook through T2 (§6.5). R3 mitigation is a gated destructive write with dry run, approval and read-back (§11.4). R4 resolution and the governed-asset postmortem are evidence-linked (§9.2, §9.4). R5 the four verbs are callable (§12 T7). R6 namespace-scoped, never cluster-admin (§9.2).

Driver → goal → objective. Driver: incidents run from chat and kubectl, so record, approval and learning sit outside the model. Goal: operations closes detect → triage → mitigate → resolve → learn inside the card/run/approval primitives. Objective: the §12 gate passes on an injected pod failure; writes are refused without the tenant policy; every incident ends in a postmortem or a recorded reason.

Solution concept. Detection opens a card and an incident row → ops.triage asks T2 for severity and a published procedure → steps read pods, logs, events, Flux and CI → a write step calls ops.restart/:ops.scale/:ops.rollback under one approved target with a recorded dry run → ops.resolve records mitigation and evidence → ops.postmortem composes the asset; a systemic finding becomes a kata or a runbook change. Andon stops the line; only a person releases it.

Migration and rollout

S0 waits on the T2, T4 and T13 gates. S1 ships migrations/0052_ops_incident.sql (to create at #78): the incident table, the approval_policy.required_decisions column, and the incident card-type seed. S2 lands the actions and events. S3 seeds proc-incident and the six runbooks as procedure drafts, published through the existing gate, and adds the Operations screen. S4 extends the invoke gate with dry-run evidence. S5 proves the gate scenario in a disposable namespace. S6 wires postmortem → kata/lesson. Rollback: the migration is additive; actions retire rather than delete; a bad write is reverted with ops.rollback under its own approval, a bad deploy with its revision; incident rows are never deleted.
