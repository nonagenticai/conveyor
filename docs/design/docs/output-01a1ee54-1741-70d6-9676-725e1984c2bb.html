Build vs reuse

  • Lesson aggregate: build. It carries a lifecycle no memory kind has; one would put review state on an append-only row.
  • Evidence refs: reuse trace_link. Extend its kind vocabulary with evidences; tenancy, uniqueness and indexes exist, and independence is computed at read time.
  • Review: build a typed lesson_review, not a generic approval. It records an evidence hash and is served by the Improve screen, not the approval inbox; the reviewer is a person, never the proposer (P4 by analogy).
  • Promotion: reuse the strata ingest contract. T8 builds the intent/commit record around the call and never publishes a pack or writes capability_knowledge.
  • Metric: do not build. Lesson promotion rate is T11's read model over T8 rows.
  • Constraints: public repo (no private host, credential or live id), workspace crates only, no new port (8930), strata via the existing client.

Risks

  • A lesson forked into a memory kind and a lesson row → check: git grep -n 'lesson' origin/main -- migrations/ gains no memory-kind value.
  • One run counted twice through its card and itself → check: an independence-root test where a card plus its only run is one ref.
  • Evidence added after review rides a stale approval → check: a changed hash voids the review and returns the lesson to proposed.
  • Retry double-ingests into strata → check: a stable lesson: <id> body and the reviewed hash; a second promote is 409.
  • Incident refs before T7 → check: an unresolvable kind is refused (P8), marked absent in the matrix.
  • Bad doctrine reaches a run through a pin → check: T8 has no publish or pin action; bind_knowledge_tx stays the only writer.
  • Two principle catalogues collide: the published P0 set is P1–P10, SPEC_V2 §3 is P1–P11 → check: cite §3 only, never map ids.
