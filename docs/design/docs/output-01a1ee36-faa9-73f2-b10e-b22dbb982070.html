Build vs reuse

  • Backlog: reuse wbs_node; build only the materialiser. No backlog table, no stored score.
  • Cadence: reuse programme_cadence; add cadences.plan|demo|retro|refine (to create). No scheduler, no second state store.
  • WIP: reuse list.wip_limit (crates/actions/src/board/pull.rs). No programme WIP column.
  • Demo: reuse the approval primitive. No demo table; evidence stays in meta.evidence[].
  • Tranche: reuse T1's rows and refusals; T10 adds only the read model. The review never rewrites a baseline.
  • Benefits: reuse benefit_transition; add strategy/plan authoring and the realized-versus-planned read. No second benefit store.
  • Do not build: lessons (T8), kata (T5), metrics (T11), architecture artefacts (T9). One owner per fact (P10).
  • Contract and licence: everything proposed is in-repo, so no new upstream dependency and no new licence obligation. The repo is public: no private host, token, email or internal id enters the design or its fixtures.

Risks

  • Materialising twice creates duplicate cards. Check: run cadences.plan twice and assert one card per wbs_node (test to create).
  • WIP read from the wrong list under-fills or over-fills. Check: a programme with two lists, one capped.
  • An evidence gate that accepts [] or {}. Check: empty evidence must refuse (test to create). The existing check rejects null and [] but passes {}; the demo gate must not copy that hole.
  • benefits.update(status='realized') bypasses the transition guard. Check: set realized with no transition; it must refuse (crates/actions/src/spine/mod.rs:benefits_update).
  • The retro owning lessons duplicates T8. Check: the T10 migration adds no lesson table and no lessons.propose action.
  • Governance theatre. Check: each new gate ships a negative test; T11's never-refused flag is absent, so T10's own tests carry the proof.
