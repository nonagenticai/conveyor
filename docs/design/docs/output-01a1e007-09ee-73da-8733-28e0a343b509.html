Architecture and analysis pack — current state, options, risks

Programme: conveyor buildout · Status: adopted by P0 · Date: 2026-11-15

1. Current state (measured)

  • The application is live. conveyor.nonagentic.ai runs the one Rust service on Postgres; the public programme site reads the database through /design/data/snapshot.js, /design/docs/outputs.js and /design/docs/output-<id>.html.
  • The programme is 48 projects. data/coverage.json at this baseline measures 26 built, 2 partial (S14, S21), 17 proposed, 1 archived, 1 standing, 1 planned (P0); tranches 0–13 (scripts/build-coverage.py).
  • V1's build record is 83+ tables and 290+ served operations; the served-spec lock is the drift gate (docs/SPEC_V2.md §1.1).
  • The work store is real but nearly empty. The document aggregate carries body, publishable and ETag; the public route serves published rows; at the P0 baseline one published output exists. The expected outputs per project are the missing index (this definition set adds them).
  • The engine proof is not claimed. No run has executed a step against a model; the seeded agents' allowed_actions are empty. A5 is a separate unit and is not a precondition for this programme's definition work.
  • The tenant identity is being repaired. The app's tenant was seeded locally; the licences registry's canonical tenant differs. The owner's ruling is to licence the app's own tenant, and the signed-in console is gated on that grant (2026-11-15).

2. Options considered

OptionWhy it was rejected
Reuse fr/agent as the runtime and add a UIThe conveyor would become a facade over other applications' models; the program exists to own its whole model (D33). The agent is a front end over MCP.
A fleet of small services per aggregateThe V1 measurement showed the cost of a fleet: cross-service contracts, duplicated concepts, a distributed transaction in every workflow. One Rust app, one database, one action registry wins.
Documents as files in git, not rowsThe programme's work products need retrieve/update/version semantics and a live public URL; git alone cannot give a non-engineer an editor or the app a checklist. The DB is the store; the one-way programme/ export is the public record.
Agents execute the programme's work nowThe engine proof is not done; the programme can run on people and sessions today. Coupling the programme's definition to A5 would block it on model credentials.
A second UI frameworkThe pack is already a working console; a rewrite would repeat the S12 cost before the programme has a single published brief.

3. Risks

From docs/SPEC_V2.md §14, the ones this programme owns directly:

  1. Over-abstraction (R1). Four wf_* types "serve nothing" in the v4 lesson. Rule: no aggregate without a named procedure and a metric; kill any table with zero use after one cycle.
  2. Meta-job recursion (R2). Coach cards about coach cards; 9/9 katas failed. Rule: closed triage/remedy sets, per-signature uniqueness, depth cap, evidence before kata.
  3. Reimplementation drift (R3). The conveyor duplicates concepts from other applications and they diverge. Rule: the conveyor owns its model; concept parity is tested only where a channel contract depends on it.
  4. LLM decision creep (R4). Routing logic reappears in prompts. Rule: the decision-ladder types; a generated result has no transition path.
  5. Governance theatre (R5). A gate that cannot fail. Rule: every gate ships with a negative test; never-refused gates are flagged.
  6. Self-development runaway (R6). The system changes the gates that judge it. Rule: no changing own gates/instruments; merge and deploy are separate human decisions; rollback is mandatory.
  7. Tool sprawl (R13) and SSRF/credential leak (R14). One owner per toolkit; a probe; effect classes; destination aliases; sealed credentials; response caps.
  8. Standards cosplay (R10). TOGAF/SAFe in name only. Rule: a lean profile with named artefacts and gates; the first architecture project is the test.

5. Open issues at this baseline

  • A5 (engine proof): sign-in, model/inference credentials and a non-empty allowed_actions are needed; no run has executed a step. Not a P0 gate.
  • Tenant identity: the app's tenant and the licences registry's canonical tenant differ; the owner chose to licence the app's tenant. The re-key is a separate estate decision.
  • CI capacity: the measured 102-minute run and the runner queue are the development loop's bottleneck (docs/plans/development-process-speed.md); PLATFORM owns it.
  • The programme mirror: the DB is authoritative; the programme/ export is one-way. A merged design PR is applied by a maintainer, not automatically.

6. What this pack commits to

Every delivery project's inception analysis starts from this state and these options; it does not re-open the choices in §2 without a decision record. The risks in §3 are checked at each project's gate; a project that increases one of them names the mitigation.
