Build vs reuse

  • Reuse ops reads, writes and host. T7 composes them; a second Kubernetes client is refused (P1).
  • Reuse the approval gate and policy. Extend the policy with a decision count and dry-run evidence; no ops-specific approval table.
  • Reuse procedures as runbooks. Versioned and published; a runbook table would duplicate the aggregate.
  • Reuse governed_asset for postmortems. T7 adds the action and link, not a document store. Reuse andon; link it, never rebuild it.
  • Build incident and its actions. One satellite table behind a card because T11's MTTA/MTTR reads need typed columns; ops.flag_flip patches a declared ConfigMap key, because a flag service would be a second config store.
  • Refuse: cluster-admin, kubectl or shell from a job, a second alerting stack, a flag service, the mcp-server runtime (D44), archived kag (R19). The Kubernetes API is Apache-2.0, the workspace pins one dependency set, and no GPL component enters.

Risks

  1. The approved write can skip its dry run. enforce_destructive_gate records no dry-run ordering. Check: a test refuses a live write whose approval has no dry-run evidence.
  2. Dual control is unconfigurable. "The tenant's configured approvals" is one decision today. Check: required_decisions = 2 and one decision leaves the write refused.
  3. Incident and card diverge. Two records is the P1 failure. Check: one writer per field, and no card path sets incident state.
  4. Triage defaults instead of failing closed. Check: a missing severity set or runbook produces an explicit refusal (P8).
  5. Detection is assumed. The gate scenario needs a stated entry (webhook, schedule, CI failure or person) or it proves only the middle. Check: the test names and uses it.
  6. Flag flip widens the write surface. Check: only registry-declared keys; an undeclared key refuses before the API call. A host restart that bypasses the incident is checked by the audit and #283's open UNGATED entries.
