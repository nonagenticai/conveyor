T13 Tool platform — inception analysis

The capability T13 adds is the tool spine: one broker between a run step and a job backend, one ledger row per call, an effect ceiling that is data, a closed input schema, and tenant-prefixed object storage whose key never reaches the prompt.

Current state

  • A job reaches a backend today only through V1 external actions: crates/actions/src/integrations/external.rs:150 declares HandlerRef::External for eight targets (workers.list, providers.list, graphs.list, artifacts.list, billing.summary, coding_jobs.create, coding_jobs.get, retrieval.query), dispatched by invoke_external (crates/actions/src/invoke.rs:1030, call site :835). There is no binding row, no pinned toolkit version and no effect ceiling on that path.
  • No tool tables exist: the migrations stop at 0051_tranche_review.sql, and tool, toolkit, tool_binding, tool_call have no CREATE TABLE.
  • No tools.* action family is registered; the registry's 420 actions carry none.
  • Effect classes exist but are barely declared: Effect is read | write | spend | destructive (crates/actions/src/spec.rs:51), yet almost no action declares destructive and nothing gates on it for tools.
  • Input validation exists and is partial: validate_input (crates/actions/src/spec.rs:1203) runs before dispatch (invoke.rs:804) and enforces $ref/$defs, allOf, anyOf/oneOf, type, enum, required, properties, additionalProperties:false and items. It does not enforce pattern, numeric or length bounds, and no 422 tool_input_invalid code exists.
  • Object storage exists for documents only: Objects::from_env (crates/actions/src/integrations/objects.rs:78) reads CONVEYOR_S3_*, and key_for (:161) returns t/<tenant>/<document>/<hash16> — tenant-prefixed, content-addressed, unencrypted, with no project/run prefix and no job-facing storage operation.

Reuse sources

  • In this repository: the action registry and its one ActionSpec declaration (HTTP, MCP and OpenAPI from one source); the run/step executor and its typed failures; secret (migrations/0013_documents.sql:27) for credential storage; approval_decision (migrations/0002_domain.sql:231) and the policy-driven destructive gate (#317) for approvals; governed_asset (:253) for a tool draft; event, audit_event and inference_call for traces.
  • In the wider estate: the external backends themselves (coding, artifacts, billing, retrieval) stay where they are; only their address moves into a toolkit.
  • Upstream: nonagenticai_mcp_server remains reference only (D44) — never a runtime dependency.

Build vs reuse

  • Build the four tables and the tools.* family: they are the ownership boundary and have no V1 counterpart.
  • Build the broker as the one call path; V1's eight external actions move onto toolkit operations rather than running beside it. No second control plane, and the externals_declared guard proves it.
  • Reuse secret for credentials (a binding names a credential alias, never a key), the approvals model for destructive calls, and the output standard for the artefact a tool returns.
  • Boundary: the broker owns resolution, the ceiling, the ledger and the storage key; it does not own the backend's health, the model, or the V1 job queue.

Risks

  • A second control plane. If the eight external actions keep their direct dispatch, jobs can bypass the binding, ceiling and ledger. Reveal: crates/api/tests/externals_declared.rs::no_handler_calls_a_service_directly plus a zero-hit grep for a direct handler call.
  • A ceiling that can be raised at run time. If the binding's ceiling is read from the caller's input, a job widens its own authority. Reveal: the 403 tool_effect_forbidden scenario.
  • A credential in the prompt. If the storage adapter passes the S3 key or a signed URL into the model context, the secret leaks into an audit trail. Reveal: the compiled-prompt scenario in P5.2.
  • A schema that accepts the invalid. Without pattern and bounds, a backend receives input the operator never approved. Reveal: the 422 tool_input_invalid scenario with a zero request count.
  • Migration numbering. 0052 collides with another session's in-flight migration; the ledger check catches it at the PR head.

Open questions

  1. Do the inference-router and laya external calls migrate as tools? Default: no — they are the L1/L2 rungs, not job tools (§11.2).
  2. Do V1's artifacts.list callers move to the storage adapter or keep a shim? Default: move, no shim (§15.2 #17).
  3. §11.10 says tenant/<tenant_id>/; key_for says t/<tenant>/. Default: §11.10 spelling; V1 keys re-prefix, no dual scheme.
  4. Where does "the tenant's configured approvals" for a destructive tool live? Default: the tenant's existing approval configuration, no second approvals model.
