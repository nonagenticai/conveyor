Context and boundary

T8 owns the lesson lifecycle — proposal, counted evidence refs, a person's review, promotion to a knowledge source draft — implementing §7.6 and D36, supplying the §7.5 lesson rows.

Must not duplicate:

  • work-package memory — S15's hot rows and digest; corroboration only, never doctrine.
  • retrieval — strata_rag owns bytes and the source; T8 owns proposal and review.
  • pack publication and pins — the estate release path and capabilities.bind_knowledge; T8 has no publish action.
  • T5, T7, T10 — measurement, postmortems and retros produce lessons via lessons.propose, not the lifecycle; T11 reads the rate.

Fit: one Postgres, one registry, no port (8930); generation may draft a body (§7.4) but cannot transition one (P2).

Invariants:

  1. Roots, not rows. A ref's root is its card, run, incident, eval run or benchmark run (§7.6: independent refs are different cards, runs or incidents); roots count once; propose and review refuse fewer than two.
  2. A review names its evidence. A ref added after approval voids it and returns the lesson to proposed; the review is kept.
  3. Unresolvable is refused. An unreadable owner (incident before T7) is a 422, never trusted (P8).
  4. Promotion is terminal, unique and inert. An approving review on the current hash is required; a second promote is 409; no pack, pin or binding is written.

Events (to create), §12 T8: lesson.proposed, lesson.evidenced, lesson.reviewed, lesson.promoted; a rejection is lesson.reviewed verdict reject.

Decisions

  • D-T8-1 — the lesson is its own aggregate. Alternative: a memory kind. Consequence: 0020 untouched; a lesson outlives its rows and carries review.
  • D-T8-2 — evidence refs are trace_link edges; independence is over roots. Alternative: lesson_evidence. Consequence: one graph; a card plus its only run is one ref.
  • D-T8-3 — review is a typed lesson_review. Alternative: approvals.*. Consequence: the Improve screen serves it, not the inbox.
  • D-T8-4 — promotion creates a source draft only. Alternative: publish a pack. Consequence: doctrine reaches a run only via the estate release path, never T8.
  • D-T8-5 — promotion is recorded on the lesson row. Alternative: a pending/committed table. Consequence: no state unobservable across a call; retries rely on the stable lesson: <id> body and documented dedupe.
  • D-T8-6 — the family grows by three actions. Alternative: UI reads and re-proposing for evidence. Consequence: the family gains six actions beyond the two #79 names (lessons.propose, lessons.review); all are recorded in this design and added to actions.json by #79.
  • D-T8-7 — ref kinds are closed and resolved. Alternative: free text. Consequence: incident and postmortem refs wait, absent, until T7.

Architecture artefacts

The PSA set at inception

  • Principles applied (SPEC_V2 §3). P1 — one record per fact: lesson in conveyor, source in strata, refs in trace_link. P3 — status moves only through lessons.*; P2 — generation cannot transition a state. P3 also requires the counted refs and the review. P4 — the reviewer is a person, never the proposer. P5 — the review cites evidence and T11 measures adoption. P8 — an unresolvable ref or unconfigured strata refuses. P10 — two tables, each written by a named action and read by a named gate. P11 — the two-ref floor is the D36 invariant, not tunable; a tenant may raise it, never lower it.
  • Requirements. §7.6 lesson promotion; §9.4 the loop ends in a lesson; §10.3 lesson; §10.4 lessons.*; §12 T8; D36; P0 §5.
