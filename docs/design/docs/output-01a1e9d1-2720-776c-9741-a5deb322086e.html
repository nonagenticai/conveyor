Artefact standard

Programme: conveyor buildout · Status: proposed for P0 acceptance (drafted 2026-11-17) · Date: 2026-11-17 · Owner: the programme architect · Reviewer: the Architecture Board (charter proposed in PF-1; rows are T9's) · Artefact: AS-1, the proposed artifact_type standard, Preliminary.

Common metadata

Every architecture artefact — catalogue, matrix or diagram — carries the same metadata before it can be approved. An artefact missing any of it is a draft, not an artefact.

FieldMeaning
TitleThe artefact's name, stable across versions
Statusdraft, approved, superseded or retired
VersionA monotonic version; an approved version's body is immutable
Author and dateWho produced it and when
Reviewer and review dateWho accepted it and when
Related initiative / projectThe change initiative or delivery project it serves
Purpose, stakeholders, scopeThe rationale block: why it exists, for whom, and what it covers
Published document or contractThe document that carries the content, or the contract it sits under

The metadata is rows, not prose (docs/plans/T9-architecture-capability.md §4.1). The document may render it; the row is the record.

Catalogues

A catalogue is a one-axis artefact: a unique identifier, the item name, and the description of its use or structure. Examples: the principles catalog (each entry statement/rationale/implications), the requirements catalog (each entry typed condition/constraint/assumption/delta), the application portfolio.

  • One row per item; the item's identifier is unique within the catalogue.
  • The catalogue's own metadata names the phase and plateau it serves.
  • An entry that cannot name its use or structure is not an entry.

Matrices

A matrix is a two-axis artefact. It names both axes (usually two) and records the relationship between them: for each (axis_a, axis_b) pair, the value that relationship carries. Examples: the stakeholder map (stakeholder × concern), the actor/role matrix, the application/function matrix, the value-stream/capability matrix.

  • Both axes are declared in the metadata; a matrix with an undeclared axis is a draft.
  • Every populated cell carries its value; an empty cell is an explicit absence, not a missing row.
  • A matrix is joinable: the same rows answer the questions the ADM asks at every phase.

Diagrams

A diagram is a typed visual artefact: it names its building block or metamodel and its viewpoint, and its content is a document (an SVG, PNG or PDF) — the row carries the metadata and the viewpoint, not the pixels. Examples: the solution concept diagram, the process flow, the platform decomposition.

  • The viewpoint says who the diagram is for and what question it answers.
  • The diagram's content is versioned with the row; a renderer change that alters the drawing is a new version.
  • A diagram without a viewpoint is a picture, not an artefact.

Links

Every artefact carries at least one typed link to another artefact. The four edge kinds are:

EdgeMeaning
derivationThis artefact derives from that one (a solution concept derives from the requirements)
realizationThis artefact realizes that one (a service catalogue realizes a business capability)
reuseThis artefact reuses that one (a project reuses the programme's principles)
dependencyThis artefact depends on that one without deriving or realizing it

The links are what make the repository answer what this artefact derives from, what it realizes and what it reuses — the trace chain of docs/SPEC_V2.md §8.5. An artefact with no link is refused by the phase gate that requires it.

Repository

The repository is designed as the architecture_artifact parent with its three types and its entry rows (architecture_artifact_entry: axis_a, axis_b, value); the tables are T9's. Three things make it a repository rather than a file store:

  1. The type catalogue is seeded (artifact_type): each type names its phase, plateau and whether it is mandatory. The adm_profile filters the catalogue; a young capability carries fewer types.
  2. Every artefact names its phase and plateau (psa, hld or sd), so a phase gate can require the set the profile names.
  3. Search will be across projects, phases and plateaus (architecture.repository.search), so reuse is a query, not a memory; the action is T9's.

Adoption. This standard is proposed for adoption as the programme's artefact standard: the types in the ADM profile (ADM-1) are the mandatory set, the metadata above is required, and every published P0 artefact carries its type, phase, plateau and at least one link. The repository rows, the artifact_type seed and the search action are T9's (#81, proposed). Until they land:

  • the artefacts are document rows on P0 with meta.artifact_type, meta.phase and meta.plateau;
  • their links are recorded in the document body and, where a row exists, in benefit_link or a decision;
  • a missing metadata field or link is a visible gap in the project's checklist, and the review that finds it records a kata candidate.

What the standard refuses. An artefact that is a blob with no metadata, a diagram with no viewpoint, a matrix with undeclared axes, or a catalogue entry with no use/structure is not adopted, whatever its file format. An artefact that has no link derives from nothing and realizes nothing; it is a note, not architecture.
