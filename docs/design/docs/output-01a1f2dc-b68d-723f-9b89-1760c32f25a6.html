T9 — Architecture design

Project: T9 — TOGAF ADM capability · Track: v2 · Tranche: 4 · Plan: docs/SPEC_V2.md §12 / docs/plans/T9-architecture-capability.md Unit: #81 · PR #350 (merged c8204432, 2026-11-19) Measured at: main@f14b7d36, 2026-11-19 · Project row: closed

Context and boundary

T9 owns the architecture capability as rows in the one store: a typed artefact standard and repository, the Preliminary governance (profile, board, maturity, skills), an architecture project walking Preliminary and A–H, four ADM contract kinds, delivery compliance with waivers, the Phase H outcome, and the console surface that reads them. It turns TOGAF from a document set into state a gate can refuse on: a phase advances only on its approved mandatory artefacts and a live contract.

Out of boundary: an ArchiMate editor or live metamodel, a renderer that derives diagrams from the model, an automatic conformance verdict, a portfolio optimiser, TOGAF certification. A diagram is a document with typed metadata, not pixels in Postgres. T9 consumes T1's plan spine (wbs_node, project_register_item), T3's gate routing, P0's Preliminary documents and the document aggregate; it rebuilds none, and owns neither T10's tranche reviews nor benefits realisation. No new service, port or store: eleven tables in the one Postgres database, every write one ActionSpec in the one registry (crates/actions/src/lib.rs:architecture).

Decisions

D-T9-1 — Artefacts get their own tables, not a widened governed_asset. Alternative: add kinds to governed_asset, which already carries fifteen. Refused: catalog, matrix and diagram structure, entries, typed links and immutability are more than a definition row expresses. Trace: SPEC_V2 §10.3.

D-T9-2 — An entry is a row; a diagram is a document plus metadata. Alternative: a JSON blob or a rendered model. Consequence: entries and reuse answer in SQL, while a diagram's pixels live in the document aggregate and its viewpoint on the artefact row.

D-T9-3 — The Board is a governance_body row; its decisions are approval rows; the charter is immutable. board_open is idempotent on the stable key. Known gap: decide_board_tx inserts the approval and leaves governance_body.status untouched, so the live board reads draft (id 01a1f2c0-b22a-7e27-a6cc-1a8e48db327e) while an approved decision exists (approval 01a1f2c8-e26f-79ce-a082-5526648a47c5). The approval row is the decision record.

D-T9-4 — The profile tailors a seeded standard; tailoring is data, never code. seed_standard_tx seeds ten types; P0's profile table names a larger set, and no action adds a type. Consequence: the artefact vocabulary is capped at ten until a new action (not #385, which adds reads only), and a profile can name a requirement nobody can create. This is the design's most visible ceiling.

D-T9-5 — A phase advances in one transaction on an approved mandatory set and a live contract. advance_phase_tx refuses naming the missing artefact or the contract's status and writes no contract row. Trace: D3.

D-T9-6 — A contract change is a new version that re-opens its gate; the approved body is immutable. The unique live index keeps one governing version per project. Trace: D3.

D-T9-7 — Phase H records exactly one outcome: a project_register_item(kind='change') or a kata candidate and no change row; a review without a verdict refuses the gate. A compliance review records one level; a waiver without an owner and date is refused; the delivery design gate resolves only against a live contract. Trace: D4, D5.

Architecture artefacts

The PSA set at inception

  • Principles applied. P1 one model, one store; P2 every mutation an action; P3 structural tenant isolation; P5 versioned, attributable outputs; P7 gates refuse.
  • Requirements. SPEC_V2 §8.1, §10.3, §10.4, §10.5, §12 T9, D63.
  • Stakeholder map. The programme owner, who chairs the board and accepts the capability; the delivery projects the gates govern; the reviewer and audit; the outside contributor reading the public record.
  • Driver, goal and objective. Driver: architecture accountability lived in documents, not rows. Goal: every output a typed row with entries, links and a lifecycle. Objective: the buildout runs under an adopted profile, a live Phase A statement and a board deciding on evidence.
  • Solution concept. A profile tailors ten seeded types; artefacts and links form the repository; a contract closes each phase; reviews and waivers bind delivery; Phase H yields one change or kata.
