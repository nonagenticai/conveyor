Artefact standard

Programme: conveyor buildout · Status: seeded with the ADM profile's adoption on 2026-11-19; the standard has no versioned row of its own · Artefact: AS-1, the artifact_type standard · Record: ten seeded types in artifact_type; cells in architecture_artifact_entry · Board decision: 01a1f2c8-e26f-79ce-a082-5526648a47c5

The standard every architecture artefact in the programme is recorded under: ten seeded types, one entry shape, four link kinds, and a repository search. The rows are the standard; this document is the readable copy. The standard's three artefact kinds are catalogue, matrix and diagram; a fourth, principles_catalog, is the principles catalogue's own kind, because a principle entry has a fixed shape rather than a free-form one.

Common metadata

Every artefact is a row in architecture_artifact carrying its title (stable across versions), artifact_kind, phase_code, plateau, status (draft, in_review, approved, superseded or archived — the migration's set), a monotonic version, purpose and scope, and a meta block with author, reviewer, review date, the status and version copy, and — for diagrams — the viewpoint, building block and elements. The three Preliminary artefacts carry all of it: PF-1, for example, is approved at version 2 with author "programme architect (maintainer sessions)" and reviewer "the Architecture Board", its purpose and scope stated as rows.

An artefact missing any of this is a draft, not an artefact. An approved version's body is immutable; a supersede writes version n+1 through architecture.artifacts_supersede. The metadata is rows, not prose: a document may render it, the row is the record. The meta copy of status and version is the one field known to drift — PF-1's copy still reads "draft for board approval" on an approved version 2 row — so the row's own columns are authoritative wherever the two disagree.

Catalogues

A catalogue is one-axis. Every entry is a row (axis_a, axis_b, value): axis_a carries the item identifier, axis_b the item name, and value the item's fields. PF-1 is the live example — ten entries, axis_a P1–P10, axis_b the principle's short name (for P1, "One model, one store, one action registry"), and value holding the statement, rationale, implications and evidence. The identifier is unique within its catalogue, and an entry that cannot name its use or structure is not an entry.

Matrices

A matrix is two-axis: both axes are declared, and every populated cell is an entry row carrying its own value. The seeded standard has one matrix type, the Stakeholder Map (stakeholder × concern, Phase A, PSA). A matrix with an undeclared axis is a draft, and an empty cell is an explicit absence rather than a missing row. The same entry shape serves catalogues and matrices, which is what makes a matrix joinable rather than a separate artefact model.

Diagrams

A diagram's row carries the building block, the elements and the viewpoint — the metadata and the viewpoint, not the pixels. The two live diagrams are the Principle Derivation Diagram (viewpoint "ArchiMate 3.1 / Motivation", elements benefit → principle) and the Principle Realization Diagram (viewpoint "ArchiMate 3.1 / Implementation", elements principle → enforcing code or gate). Their content is the entry rows: derivation records (B5 One model, P1, {relation: derivation, note}); realization records (P1, implementation, {relation: realization, evidence: ...}). A diagram without a viewpoint is a picture, not an artefact.

The honest gap: the repository holds the metadata, the cells and the evidence targets, but no image. There is no rendered drawing, no image store and no viewer; a reader reconstructs the diagram from its viewpoint and cells. That satisfies the standard's definition — the row is the record — and it is not a graphical artefact anyone can look at.

Links

Every artefact carries at least one typed link, created by architecture.artifacts_link. The four edge kinds are:

EdgeMeaning
derivationthis artefact derives from that one
realizationthis artefact realizes that one
reusethis artefact reuses that one
dependencythis artefact depends on that one without deriving or realizing it

The live Preliminary set carries two links: a derivation from the Principle Derivation Diagram to PF-1, and a realization from PF-1 to the Principle Realization Diagram. No reuse or dependency link exists yet — reuse will be exercised when a project's artefact reuses a programme artefact. Each diagram cell repeats its relation in value.relation, and the two agree with the edge kind. No link kind is enforced by the phase gate today: advance_phase_tx checks the profile's approved types and a live contract only, so a linkless artefact is a standards failure, not a mechanical refusal.

The repository is rows, not a file store. architecture.repository_search searches artefacts across projects, phases and plateaus, so reuse is a query rather than a memory, and architecture.artifacts_entries reads a single artefact's cells. Four gaps are recorded rather than papered over. First, the standard is seeded by seed_standard_tx in crates/store/src/architecture.rs, and none of the 26 architecture.* actions creates a type: artifact_type has one write path, so extending the standard is a code change and a release, not a repository act. Second, there is no XMI, XML or bundle export or import — interoperability is the API contract, not a file. Third, no rendered diagram and no image store, as above. Fourth, the standard is thin against the design: ten types, no SD-plateau type, and no type for phases E–H; the P0 artefact table is the target, reached by seeding more types.
