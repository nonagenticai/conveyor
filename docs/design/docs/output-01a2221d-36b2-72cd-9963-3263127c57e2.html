Architecture analysis — S04 action registry (retrospective, 2026-11-28)

Current state

Measured at the record, the slice declares its actions once and projects them four ways: the manifest, the OpenAPI operation, the MCP tool and the HTTP route. crates/actions-derive produces the specification from the declaration, crates/actions/src/resolve.rs resolves an action by name and binds its path, query and body parameters, and the invocation path writes the ledger and audit rows created by migrations/0003_action_registry.sql. docs/design/data/actions.json is the dump of the registry the design page reads, regenerated by the publish. The proof is executable: crates/actions/tests/parity_http_mcp.rs compares the 20 actions over both transports, crates/actions/tests/action_resolution.rs proves resolution and refusal, and crates/actions/tests/fixtures/external/openapi.json carries the external ingest fixture.

Options considered

  1. Per-transport registries — a route table, an OpenAPI file and an MCP table maintained separately. Rejected: three sources drift and the parity claim becomes unprovable.
  2. A runtime registry loaded from a configuration file, with routes generated at startup. Rejected: the boot path gains a parse step and a failure mode, and the compile-time checks (names, collisions, charset) move to runtime where they are discovered by a caller.
  3. The compiled declaration, chosen: one ActionSpec per operation emitted by the derive, with the projections generated and the boot checks compiled in.
  4. External actions — a generated client per external API versus an ingest of a declared OpenAPI document at the boundary. The ingest was chosen because it keeps one registry and refuses an external schema the closed set cannot express.

Risks

  • A schema change that one projection cannot express is refused at boot, not discovered by a caller after the fact.
  • The registry dump can lag the binary; the lock and the parity test are the checks, and the dump is regenerated by the publish rather than hand-edited.
  • External ingest is a trust boundary: the declared document is validated before a binding row is written, so a malformed document cannot create a callable action.
  • An action added outside the derive would be invisible to the projections; the boot check reads the registry, so the omission surfaces as a missing route rather than a silent bypass.

Dependency map

The record declares meta.depends_on: [S02, S03]: the store and governance surfaces those slices built supply the tenancy, the board and the audit rows this slice writes, and P0 supplies the programme definition. The slice is in turn a dependency of the tool platform (T13) and of the external-action consumers, which call through the same resolver rather than a second path. Inside the project the seven A–D artefacts carry the derivation chain — stakeholder map, driver/goal/ objective catalogue, requirements catalogue, solution concept, business capability map, data entity catalogue and technology standards — so each later artefact cites the one it derives from.
