Blueprint — the target architecture and operating model

Programme: conveyor buildout · Status: adopted by P0 · Date: 2026-11-15

The to-be the T0–T17 projects deliver. This is a synthesis of docs/SPEC_V2.md §4–§11 and the V1 contract (docs/plans/01-CONTRACT.md, docs/plans/02-DATA-ARCHITECTURE.md); where they differ, SPEC_V2 wins for V2 and the V1 contract stays binding for V1's slices.

1. One application, one database, one action registry

  • One Rust workspace. crates/domain (pure types and state machines), crates/store (the only SQL), crates/actions (one module per aggregate), crates/api (HTTP and the action invocation route), crates/auth, crates/bus, crates/render, crates/workflow, crates/pack; apps/server composes them. No service owns a second copy of a concept.
  • One Postgres database per service, one database user per service. Tenant isolation is a row-level policy plus the action layer's tenant check; a foreign key never enforces tenancy (docs/plans/01-CONTRACT.md §2).
  • Every operation is an action spec. A typed input, declared scopes, effect class, tenancy, timeout and gate behaviour; the same spec projects to HTTP, OpenAPI, MCP and the operator CLI. crates/actions/src/spec.rs is the derive; the served-spec lock is the drift gate.
  • One outbox and one event stream. A state change writes its event in the same transaction; the bus delivers; a consumer re-reads state rather than trusting the payload.

2. The aggregates

Organisation (docs/SPEC_V2.md §4)

industry → department → job → job_release → job_binding. A job release is immutable and pinned by a content hash; a binding pins a release for a tenant; a retired binding refuses 409 job_binding_stale. Knowledge kinds, packs, instructions, settings, toolsets and System-1 gates compile into the release. The catalogue is the conveyor's own; nothing is imported from the agent platform at runtime.

Work (docs/SPEC_V2.md §5)

programme → project → board → list → card, with wbs_node, project_baseline, project_register_item and project_dependency added by T1. A card is typed by a card type whose definition names its expected outputs; a card runs a process; a run has steps, gates, decisions and outputs. Documents carry the intermediate outputs: a Markdown body on the row, publishable and a version/ETag.

Decisions (docs/SPEC_V2.md §7)

decision/decision_option/decision_policy/decision_policy_refinement, laya_inference_config. The ladder is rule → laya → generation → human. Every decision row pins the policy, refinement and laya configuration versions; a generated draft cannot transition a card.

Tools (docs/SPEC_V2.md §11)

tool/toolkit/tool_binding/tool_call; the broker; effect classes; credential profiles; a tenant-prefixed storage adapter. The estate's services enter as versioned toolkits; a probe proves each published toolkit; a changed contract is a new version, never a silent patch.

Knowledge, memory, instruments

Capability → procedure → step → action|gate; knowledge sources and packs; memory records with independent evidence; eval/benchmark/hillclimb and the prompt audit; inference_call is the ledger. S17–S21 are built and stay binding.

3. The operating model

  • Positions receive work. A job release compiles the job's instructions, knowledge, tools and gates; a card routed to the job is worked by its bound executor.
  • Gates are explicit. A card type declares its gates; an approval is a row with a required decision count and a policy. A gate that cannot refuse is a defect (docs/SPEC_V2.md §14, R5).
  • Proof is recorded, not asserted. A run records the release hash it used, its steps, tool calls and outputs. A metric recomputes from rows (docs/SPEC_V2.md §13).
  • Improvement is a loop. Coach interruption → kata → development project → measure → adopt or revert; a lesson needs two independent evidence refs and a review (docs/SPEC_V2.md §6, T5, T8).
  • Self-development is gated. The conveyor changes itself through the same lane/PR/CI/deploy loop, but cannot change its own gates or instruments; merge and deploy are separate human decisions (docs/SPEC_V2.md §9.3, R6).

4. The deployment estate

One k3s cluster; one namespace per service; Flux owns the manifests; every service has its own database, user and secrets. The public programme site is a set of unauthenticated read routes on the conveyor service: /design/data/snapshot.js, /design/docs/outputs.js and /design/docs/output-<id>.html, served from Postgres for the tenant named by CONVEYOR_PUBLIC_TENANT, with ETag/304 and never a cached 404. The application itself is a static pack plus the same-origin action API; there is no second frontend runtime.
