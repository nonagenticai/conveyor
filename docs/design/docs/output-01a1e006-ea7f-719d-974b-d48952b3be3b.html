1. How to read the plan

  • A project is one part of the conveyor: a V1 slice (S##), a V2 slice (T##), or a cross-cutting unit (P0, SPEC-V2, DESIGN-PUBLISH, PLATFORM). Every project has a plan path, a brief, and two inception units (analysis, architecture) before its build units are claimed.
  • A tranche is the longest dependency path in the project graph, not a calendar phase. Two projects in the same tranche can run in parallel when their typed edges allow it.
  • Every unit of work is a GitHub issue; every issue is one branch and one PR (docs/plans/03-DELIVERY.md).

3. Sequencing

  • P0 gates T1–T17. No V2 delivery project starts until this definition set is accepted and its briefs are published (docs/plans/P0-programme-definition.md §1, §6).
  • The V2 spine is T0 → T1 → T2 → T3. T4 follows T3; T5 follows T2 and V1's S16–S20; T6 follows T5 and T13; T7 follows T2/T4 and T13; T8 follows T5; T9/T10 follow T1/T3; T11 is continuous; T12 follows all; T13 follows T2; T14 follows T13; T15 follows T13 and T6; T16 follows T2 and T13; T17 follows T16 and T3 (docs/SPEC_V2.md §12).
  • The first three months are T0–T3 plus T13. They install the organisation spine and the tool spine; everything else is a job that uses them (docs/SPEC_V2.md §12).
  • V1's remaining slices (S00–S21) run on their own dependency edges; they are not re-opened by V2. S14 is the cutover that retires fr, RM and Planka; it does not block V2's spine.

4. Definition of done, per project

A project is done when:

  1. its brief is published on the project (meta.category = project-brief) and carries the outcome, boundary, reuse sources, typed dependencies, acceptance with a Verify: line, capabilities and plan path;
  2. its analysis and (for V2) architecture are published on the project — the inception standard (docs/plans/P0-programme-definition.md §5);
  3. its build units are claimed and merged with the plan's gate green;
  4. its evidence is recorded on the project and the coverage instrument's measured status reflects it; a claim without evidence is not done.

5. Change control

  • The seed is the mapping of record. A new project is a seed change, a plan document, a brief, and an issue; a project is never invented in a session and left out of the seed.
  • A tranche change is a change to this plan and to seed/programme.json in the same PR; the coverage --check gate is the drift detector.
  • A project whose plan no longer matches the programme is marked archived in the seed with a reason; it is not deleted from the record.
