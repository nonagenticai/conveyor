02 — DATA ARCHITECTURE (binding)

Authority: this file fixes every schema decision for conveyor. S03 implements it. No slice may add a table that is not in §2, and no slice may change a column, key or index defined here without a CONTRACT-CHANGE REQUEST to 01-CONTRACT.md. Written: 2026-11-07, before the slice plans. Sources: docs/SPEC.md §4/§5.3/§6/§7, 01-CONTRACT.md, 02-source-map/50-schema-inventory.md (the total source lists), 02-source-map/{10,20,30,40}.

1. Principles

  1. One database conveyor, one runtime user conveyor_runtime (NOSUPERUSER NOBYPASSRLS), one migration role that owns the schema. One baseline + forward-only migrations, never edited after their slice closes.
  2. tenant_id uuid NOT NULL on every tenant-owned table, with ENABLE ROW LEVEL SECURITY and a FOR ALL policy tenant_isolation carrying both USING and WITH CHECK (tenant_id = current_setting('app.current_tenant', true)::uuid). Scope is set per transaction with set_config(…, true); a session-level SET is forbidden (PgBouncer transaction pooling).
  3. PKs are uuid v7. No external id is ever a PK or an FK target — no planka_card_id, no execution_id as a key.
  4. Every mutable aggregate has version bigint NOT NULL DEFAULT 1. Edits require If-Match and a zero-row UPDATE is 412, never a blind write; state transitions are status-guarded, not version-guarded — the transitions named in CONTRACT §3 take no If-Match and no version input, and a zero-row update is 409 with the current state.
  5. timestamptz everywhere, UTC, now() defaults. Never timestamp without a zone.
  6. The list is the state. A card's lifecycle is list_id + archived_at. There is no card.state.
  7. Flattening per SPEC §4: one revision, one catalogue_entry, one outline_node, one comment, one delivery, one identity. A derived value is a query, not a column — the two exceptions are tsv (a generated column that exists only to be indexed) and card.board_id (denormalised to carry the board index).
  8. No Postgres enum types. Every vocabulary is text + CHECK. Measured reason: ALTER TYPE … ADD VALUE cannot be used in the same transaction as an index on the new label (fr/backend/migrations/153_u3_approval_kinds.sql documents the failure), and the migration runner wraps each file in one transaction.
  9. JSONB holds only values read whole with their parent. Anything in a WHERE, ORDER BY, JOIN or UNIQUE is a column. §5 is the exhaustive list.
  10. event is written in the same transaction as the mutation and is the only fan-out source. audit_event is append-only by GRANT (SELECT, INSERT only). Neither is optional per slice.
  11. Names: lowercase singular tables, app_user (never user), position (never order).

2. Entity catalogue

Shorthand: nn = not null, d= default, uq = unique, ix = index, rls = row-level security, ret = retention. All uuid PKs DEFAULT uuidv7(). All tables carry created_at timestamptz nn d=now(); mutable aggregates also carry updated_at and version, and those columns are not repeated per table below.

The audit cadence has no table. After N executions is tenant.settings.prompt_audit {enabled, after_executions, surfaces, target_model}, set through the existing tenants.update_settings. The counter is therefore the ledger itself — there is no last_counted column that can drift, which is the failure mode a separate counter would have. The count excludes prompt_ref = 'prompt_audit@1', so an audit cannot re-trigger the cadence it is servicing; prompt_audit_auto_live_idx makes two calls crossing the threshold together insert exactly one event-created audit. target_model is required for an event-created audit; an enabled policy without one is not armed.

run_id / run_step_id / conversation_turn_id carry no FK, on purpose. A foreign key's RI check runs as the table owner and bypasses RLS, so it would accept another tenant's id — the same trap departments.create records. The engine resolves each id in the caller's tenant before it writes, and the inference_call_join_key CHECK is what keeps "whose call was this" answerable without one. prompt_audit_finding.audit_id is an FK (parent and child share the tenant by construction) and is still resolved in-tenant at insert.

ALTER TABLE approval ADD COLUMN eval_id uuid;
CREATE UNIQUE INDEX uq_appr_eval_pending
    ON approval (tenant_id, eval_id, gate) WHERE status = 'pending' AND eval_id IS NOT NULL;

4. Concurrency and access paths

Version / If-Match. Every mutating statement is UPDATE <t> SET …, version = version + 1, updated_at = now() WHERE id = $1 AND tenant_id = $2 AND version = $3 with RETURNING *. Zero rows is unambiguously either 404 or 412 — the handler re-reads once to distinguish, and returns the current representation in the problem body. Creation returns 201 + ETag: "<version>".

The card claim is one conditional UPDATE — no lease table.

UPDATE card
   SET assignee_id = $3, lease_expires_at = now() + $4::interval,
       lease_token = uuidv7(), claim_fence = claim_fence + 1,
       version = version + 1, updated_at = now()
 WHERE tenant_id = $1 AND id = $2 AND version = $5
   AND (lease_expires_at IS NULL OR lease_expires_at < now() OR assignee_id = $3)
RETURNING claim_fence, version;

Zero rows = not granted. There is no fallback arm and no granted: true on a DB error — the closed-degradation argument in fr/backend/migrations/100_card_phase_lease.sql §3.4 is carried verbatim as a principle: a lease that grants itself when the arbiter is down is not a lease. claim_fence is monotonic and never reset (the card row survives release), which is what lets a holder that slept past its TTL discover the card moved beneath it — the ABA window fr's card_phase_lease existed to close. Waiters are not a table: a blocked claimant enqueues job(kind='card.claim'), deduped on (tenant_id, 'card.claim', card_id).

Job claim — FOR UPDATE SKIP LOCKED, fenced:

UPDATE job SET status='running', lease_token=uuidv7(), lease_until=now()+interval '60 s',
               attempts=attempts+1
 WHERE id = (SELECT id FROM job
              WHERE tenant_id=$1 AND status='pending' AND run_after <= now()
              ORDER BY run_after, id
              FOR UPDATE SKIP LOCKED LIMIT 1)
RETURNING *;

A handler must present lease_token on completion; a stale token writes nothing. schedule materialisation runs under pg_advisory_xact_lock(hashtext('conveyor:schedule')) so two pods cannot double-materialise.

SSE replay. pg_notify('conveyor_event', seq::text) fires in the mutation transaction. A subscriber reads SELECT … FROM event WHERE topic = ANY($topics) AND seq > $last ORDER BY seq LIMIT 500, using the Last-Event-ID header. Replay is bounded by that LIMIT 500; a client whose cursor is older than the retained window (or ahead of it) gets resync, never a silent skip; a client further behind than the retention window is told to refetch, not silently skipped. The event seq is the only ordering authority — never a timestamp.

Cursor pagination. Cursors are base64 of (sort_key, id); they are opaque and never documented as stable.

The three access paths that must stay fast.

  • Board, 1,000 cards. One partial index on (tenant_id, board_id, list_id, position, id) serves the whole board as an index scan grouped by list; the API never sorts in Rust. Archived cards are excluded by the predicate, so board load cost is independent of history depth.
  • Run queue. run (tenant_id, status, created_at, id) WHERE status='queued' — a queue that is empty in steady state, so the index stays tiny and the claim is an index-only scan.
  • Search. gin(tsv) on card and governed_asset, plus pg_trgm trigram indexes on card.name, governed_asset.title and catalogue_entry.label for fuzzy prefix. S07's 0007 migration creates CREATE EXTENSION pg_trgm and the three trigram indexes (S02 §5 decision 5); S03 ships only the FTS indexes. FTS first, pgvector only after the S07 eval set proves an FTS baseline (R2). ⛔ These indexes do nothing unless two operators are LEAKPROOF — measured 2026-11-08: under FORCE RLS the planner will not use a non-leakproof qual, and ts_match_vq (@@) and word_similarity_op (<%) both ship proleakproof = false. The ALTER FUNCTIONs are a superuser step and live in scripts/db-roles.sql; see 01-CONTRACT.md §2. Without it the search runs at O(rows per tenant) and reports no error.

Board position. Planka's float position is replaced by numeric (exact, unconstrained scale) with a midpoint insert: a card between neighbours a and b gets (a+b)/2; a card appended to a list gets max+1024. There is no renumber job and no precision loss, because numeric is exact — a float implementation degrades after ~50 halvings and then needs the compaction job that nobody writes. Moves that touch more than one card (multi-select drag) take pg_advisory_xact_lock(hashtext('board:'||board_id)) and renumber the affected lists inside one transaction.

Every rule above now has a producer — with three exceptions, named honestly rather than implied: S16's two pruners are written into its slice plan (§6 there) but the slice is not built, so those two rows read planned; the benchmark tables are UNBOUNDED by design (the audit_event shape — a run is the evidence behind a score), so they have no producer and need none. A rule whose producer is planned enforces nothing today, and the table says so.

Two consequences are part of the design, not accidents:

  • approval is never pruned. 0012 re-created approval.run_id as ON DELETE SET NULL, so a pruned run detaches and the human decision — with approval_decision.note, which exists nowhere else — survives. A run_step row goes the other way: S11 must declare run_step.run_id ON DELETE CASCADE, and run.prune then carries the steps for free.
  • A run whose gate is still pending is skipped: uq_appr_pending is partial on (tenant_id, run_id, gate) WHERE status = 'pending', and a detached NULL run_id would defeat it.

Explicitly unbounded: audit_event, approval, revision for governed assets. model.prune never deletes the revision named by model.published_revision_id — a published snapshot is the governance record of a model in the same way a governed asset's revision is, and a retention rule that could delete it would make models.compare fail on the newest thing it compares.
