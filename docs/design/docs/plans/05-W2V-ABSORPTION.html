05 — The w2v absorption: disposition and the production layer

This plan complements 04-TOOL-ESTATE-INVENTORY.md; it does not replace it. Plan 04 holds the grouping decision, the sixteen-blueprint vocabulary and the destination count. This document holds what has actually shipped, one disposition per absorbed component, and the measurement that fixes the shape of the one family nobody has started.

Convention, inherited from plan 04 §5: components are named by public role. No private repository name, host name or address appears here — the repository is public and scripts/ci/no-private-refs.sh is a merge gate.

3. Why the production family is data, not services

Plan 04 §2 tabulates the sixteen blueprints. What it does not record is the measurement that makes the production family's shape non-negotiable.

Across the sixteen blueprint directories, the same stage primitives are re-implemented per blueprint:

Primitive Copies What it is
narrate.py 9 narration text to per-shot audio, via the speech model server
compile.py 8 shots to one encoded video, via ffmpeg
slides.py 7 a slide spec to rendered stills
script.py 7 the deliverable's narration script
record.py 7 a browser stepped through virtual time into a video
scan.py 3 a crawl/fetch pass feeding an audit
critique.py 2 the scored read over a scan
stitch.py 2 segments joined into one artefact
thumbnail.py 1 a poster frame

46 stage files are 9 distinct operations. Every blueprint's real content is the ordering and the parameters, not the stage logic. Two consequences:

  1. The production family needs one action per primitive, not one service per blueprint or per legacy service. produce.script, produce.speech, produce.still, produce.deck, produce.render, produce.qc cover all nine primitives (SPEC_V2 §10.4 already declares this set).
  2. A blueprint is data: an ordered phase list whose phases name registered actions. It is not a deployable, and porting 46 files as 46 modules would reproduce the sprawl inside one repository.

The two families divide exactly as plan 04 §2 says: nine blueprints produce evidence (the analyse.* side, mostly landed), seven produce an artefact (the produce.* side, not started).

5. The model-server boundary, verified

ADR 0007 keeps the model servers outside the repository as remote HTTP hosts bound as toolkits. That is no longer only a decision — it is the estate's actual condition, measured 2026-11-15:

  • The speech, transcription and vision servers on both serving hosts run Rust binaries (Mach-O arm64, Tokio symbols), alongside a vendored embedding/rerank server.
  • The one remaining Python model server is the image-generation host. It has no Rust equivalent and is explicitly outside this programme.
  • The legacy speech backend, the voice generator and the speech router have no running process and no service definition on either host.

So the boundary costs nothing to maintain: the Python the conversion would have had to remove is already gone, and what remains is one service with no rewrite path.

6. How to re-measure

Every number above is reproducible without cluster access:

  • Action families: git grep -hoE 'name = "[a-z0-9_.]+"' origin/main -- crates/actions/src, then count by namespace prefix. media.* must be 12 and produce.* must be 0 while this document's §1 is current.
  • Blueprint duplication: count basename matches under the orchestrator's stage directory, excluding its two library directories. 16 blueprint directories, 9 primitives, 46 files.
  • Group state: gh issue view <n> --json state for the executor, analysis and deck units.

If a count disagrees with this document, the document is stale — correct it in the same PR that changes the count, not later.
