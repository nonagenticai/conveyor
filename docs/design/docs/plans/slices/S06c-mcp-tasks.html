S06c — MCP tasks

Programme project: S06c · issues none yet

BUILT 2026-11-09. projects.execute (task-capable), the run ↔︎ task mapping in crates/actions/src/mcp/tasks.rs, the three hooks in mcp.rs, enable_tasks() in get_info, and migration 0023_s06c_mcp_tasks.sql — which holds the slice's two indexes: uq_run_project_live ((tenant_id, project_id) WHERE card_id IS NULL AND status live) and approval_project_idx ((tenant_id, project_id)), the project-scoped approval listing this slice reads. No table, no new event.

Build records / deviations, all deliberate:

  • The task id IS the run id. projects.execute is create-or-return and answers 200 on both paths (one representation); only the creating call enqueues run.execute and emits run.created.
  • run.execute needed no change: it was already card-agnostic (queued → running, never terminal). The REAPER did: store::run::reap_dead_runs_tx now requires r.card_id IS NOT NULL (trap 10).
  • tasks/update invokes approvals.decide — the gate's own state machine, events, run resume and the (approval_id, approver_id) unique index all apply. A repeated answer is a replay (decision_by_tx).
  • on_behalf_of is not resolved to a human: George's 2026-11-09 ruling says the conveyor need not know whether an answer is human or agent, so the decision records the authenticated agent principal (decided_by_kind='agent'). The _meta is accepted and ignored.
  • A blank-reason rejection leaves the gate open (proven); the slice's "sets statusMessage" is not persisted — there is no task table to persist it into, and the next tasks/get still reports input_required. Recorded as a deviation, not hidden.
  • One -32602 for non-uuid, unknown, cross-tenant, expired and card-scoped ids (trap 7).
  • Agent tools: projects.execute joins AGENT_TOOLS, plus runs.cancel/runs.finish (a task must be cancellable and completable by the platform that runs it). ⚠️ The build-order lines' cargo test -p conveyor-actions mcp_tasks matches 0 tests (it filters test NAMES, not binaries); the real target is --test mcp_tasks_contract. Tests: crates/api/tests/mcp_tasks.rs (the §7 property table over the real transport), crates/actions/tests/mcp_tasks_contract.rs (the wire seed and the single task-capable action), crates/store/tests/transitions.rs (create-or-return + the index).

Adds the MCP tasks extension (SEP-2663) to the conveyor's existing /mcp surface. S06b gives the agent a licence principal and a tool list; this slice gives it a durable task for a project that can run for days and stop to ask a human a question. mcp_server keeps its own task runtime for coding/care-bus/builder; the conveyor serves only its own lifecycle.

1. Objective

At the end, an MCP client that declares io.modelcontextprotocol/tasks calls projects.execute, receives resultType:"task", polls tasks/get through a project that waits on an approval, answers it with tasks/update, and reads a terminal result — with no Python service in the path and no new table.

2. Starting state

  • S04: /mcp (rmcp 3.9.0) serves the action registry; call_tool invokes the same engine as HTTP.
  • S06b: licence bearer → app_user(kind='agent'); every tool carries _meta.operation; approvals.request.
  • S06: run, approval, approval_decision; runs.create|start|finish|cancel, approvals.list|decide.

3. Scope

IN — enable_tasks(); get_task/update_task/cancel_task backed by Postgres; projects.execute; a project execution run; run↔︎task and approval↔︎input-request mapping; idempotent answers; cancel; TTL; actor provenance; the protocol tests.

OUT — the agent's client-side support for tasks on an external MCP server (separate plan: today its gate is auth_kind=none, agent/.../connectors/runtime.rs:743-757); decommissioning mcp_server; SSE/push; a progress percentage (none exists and none is added); any new table.

No tables. projects.execute is the only new action; there is no new event.

method request response
tools/call projects.execute {project_id} {resultType:"task", taskId:<run uuid>, status:"working", createdAt, lastUpdatedAt, ttlMs:604800000, pollIntervalMs:5000, statusMessage}
tasks/get {taskId} base task fields + inputRequests (one per pending approval, key = approval uuid) or result
tasks/update {taskId, inputResponses:{<approval uuid>:{action:"accept"|"decline"|"cancel", content:{decision:"approved"|"rejected", reason?, comment?}}}, _meta:{"ai.nonagentic/actor":…}} {resultType:"complete"}
tasks/cancel {taskId} {resultType:"complete"}

Status map, in this order: a terminal run maps directly (succeeded→completed, failed→completed with isError:true, cancelled→cancelled); otherwise a pending approval in the project → input_required; otherwise queued/running → working. failed is never emitted as a task status.

Every GetTaskResult also carries statusMessage from the run and, in _meta["ai.nonagentic/conveyor"], the project id, the run id and the last events on run:<id> — the shape the agent's relay already reads for fr projects, under the conveyor's own key. A terminal task carries the tool-shaped result instead: structuredContent {run_id, project_id, status, result, error}, with isError true for failed and cancelled.

8. Traps

  1. Terminal precedence. Check the run first; a stale pending approval must not revive a finished task.
  2. failed never on the wire. A failed run is completed + isError:true — the agent maps that to failure.
  3. uq_run_live does not dedupe NULLs. A project execution has card_id IS NULL, so the live-execution index must be its own partial unique index, not a check-then-insert.
  4. runs.create derives the project from the card. projects.execute writes the run directly; do not route it through the card path.
  5. Approvals are project-, card- or run-scoped. inputRequests lists by project_id, not run_id, or card-level gates are invisible.
  6. open_gate_tx needs a running run. It is for the engine's gate, not for approvals.request (S06b) or a project task's input.
  7. -32602 for every ownership failure. Non-uuid, unknown, cross-tenant, expired — one code, one message, no oracle.
  8. The client must declare the extension. rmcp refuses a task result to a client that did not; the test client must declare it at initialize, not just send the header.
  9. tasks/update is lenient. Unknown keys and terminal replays ack; a strict 4xx breaks the agent's retry.
  10. The reaper must skip project executions. run.execute reaps dead card runs to crashed; a project run is long-lived by design.
  11. _meta only. rmcp flattens a task and drops unknown top-level fields; ai.nonagentic/conveyor goes in _meta, never beside taskId.
  12. The protocol version is 2026-07-28. A client negotiating an older version does not get the methods.
  13. statusMessage is not progress. There is no percentage and none is added: the card list can be empty or reordered, so a computed percent would be a second, false state beside the run's.

9. Decisions closed here

  1. Task = project execution run. The run state machine is already the task lifecycle; no table, no second store.
  2. Input = approval. One primitive; the answer is approvals.decide, not a second response channel.
  3. projects.execute is the only task-capable action. Everything else returns a normal tool result.
  4. No decommissioning of mcp_server. It keeps its task runtime for other backends; the conveyor owns only its own project lifecycle.
  5. Polling remains the fallback. S06b's path still works when the client cannot run tasks; the methods are additive.
