S13 — Process engine, judge, map and care-bus

Programme project: S13 · issues #17

Gate (SPEC §8 S13): the execution-trace diff against the old flows, plus the run tree (a child under a live parent), the judge (a reject loops, a laya outage waits) and the bus (a Redis loss re-delivers without a double outcome). R4 binds this plan: the process model replaces the DAG as the executor, flows are re-authored as processes/handlers (never converted), and the engine never depends on an editor.

1. Objective

Make the conveyor execute processes, not n8n graphs. A process is an ordered list of steps — an agent task, a computed task, a gate, or a child call — stored as process/process_step (S11's tables, renamed by migration 0035). Every step has a procedure (SOP): definition of ready, definition of done, acceptance criteria and an inspection; the process declares its user-facing outputs. The step's output is judged by the SOP's judge (the laya decision model, an eval, or a checker): accept → done; reject → rerun with the judge's reason (max 2) → BLOCKED → coach; a laya outage waits.

A run is a tree: one live root per card, and a live parent may start a child (the coach, a cap.* call). Step work is carried by the care-bus (Redis Streams, ported from agent-api/src/runtime/bus.rs, itself from care-bus-agents@96c608c) with consumer groups and a dead-letter stream, while Postgres run/run_step/event remain the system of record.

The DAG returns only as the process map: a versioned, declarative process_map per project type whose nodes are processes, capabilities, phases or milestones — the user's view of what is happening, never the executor. The workflow engine is RETAINED (owner ruling 2026-11-09): crates/workflow, the workflow table, workflows.*/workflow_runs.* and the workflow.node/workflow.start job kinds stay as the tool-sequence executor — a process call step resolves child_process_key process-first, workflow-second — and there is no drop migration. What does retire is the hook seam: POST /api/hooks/{hook} and CONVEYOR_HOOK_SECRET are deleted. The five named legacy flows are absorbed: conveyor.start → projects.create; wip.pull → a card.moved handler; err.card → the run.failed handler; ask_fr and kata.open → processes.

5. Deliverables

5.1 Migration 0035_process_tree.sql

  • Rename procedure → process, procedure_step → process_step; rename the FK columns accordingly (run.procedure_id → run.process_id, run_step.process_step_id).
  • New procedure (SOP): {key, title, description, status, version, definition_of_ready jsonb, definition_of_done jsonb, acceptance_criteria jsonb, inspection jsonb, outputs jsonb}; one published per key.
  • New process_map: {key, title, status, version, project_type_id, definition jsonb} (nodes/edges); one published per (key, project_type_id).
  • run: parent_run_id uuid → run(id), step_id uuid → process_step(id), depth int NOT NULL DEFAULT 0 CHECK (depth BETWEEN 0 AND 3), CHECK (parent_run_id IS NULL OR step_id IS NOT NULL).
  • Drop uq_run_live and uq_run_project_live; recreate both root-only; add uq_run_child_live (parent_run_id, step_id) and uq_run_child_attempt (tenant_id, parent_run_id, step_id, attempt).
  • 0037_run_tree_workflow_step.sql (2026-11-10, W5): run.workflow_step_id uuid → run_step(id) and the workflow pair of child indexes; run_parent_step_check replaced so a child names EXACTLY one step kind (a process parent's process_step or a workflow parent's run_step). Before this, a workflow's procedure node could not start a child at all: step_id is FK-bound to process_step, and a root start 409s on uq_run_live against the parent. process_runs.start takes workflow_step_id; the workflow node passes its run_step id.
  • process_step: kind ∈ agent|computed|gate|call, actor ∈ process_agent|tool_agent|system|human, capability_id, process_agent_id, procedure_id, child_process_key, on_result.
  • process: capability_id, card_type_id, list_kind, project_type_id, outputs jsonb.
  • capability.kind ∈ system|tenant; capability_agent.role ∈ process_agent|tool_agent + process_key/toolset.
  • run_step.judge jsonb; event.bus_stream_id/published_at.

5.2 The process/SOP definitions and publish validation

  • One process per (card_type, list) — 70 × 4 = 280 — is the default catalogue, not a fixed system set; a tenant may instantiate, override or design its own (D29). As built (2026-11-10): 70 type files / 280 processes / 350 SOPs, loaded by crates/store/src/process_seed.rs (serde_yaml + include_dir; apply_all after migrate --seed, apply_type for the dev fixture's start process); seed/processes/manifest.yaml is the generated 280-entry index. The loader test applies the whole catalogue twice on a fresh database, proving publish validation and idempotency. The cap.* processes, ask_fr and kata.open are the same shape. project_management, kanban_coach and kata are the fixed system capabilities.
  • A step names its capability, worker (process_agent_id), tools, procedure_id (SOP), on_result and max_attempts (≤10). No predicates, no loop nodes, no expression language; a step's typed outcome is continue | fail | retry.
  • The step's action field (2026-11-10). An agent step stores the primitive it runs (agent.run, domain AGENT_STEP_ACTION) so run_step.action is truthful and publish/seed/executor read one value; a computed step stores its registered action; gate and call steps store none. Publish requires exactly that, the seed loader applies the same shape rule, and the executor dispatches on the step's KIND. Before this the validator forbade the action the seed wrote, which made every catalogue process un-republishable through the API.
  • An SOP has definition_of_ready, definition_of_done, acceptance_criteria, inspection ({kind: laya|eval|checker, threshold?, max_rejects?}) and outputs.
  • A process declares its user-facing outputs and is versioned; a run pins the process/SOP versions it used.
  • Publish validation refuses: no steps; duplicate/non-contiguous positions; a computed/tool step whose action is not registered; an agent step with no capability_agent(role='process_agent'); a step with no published SOP; a call to an unpublished process or depth >3; a map node that does not resolve; a reordering of a system capability's process.

5.3 The run tree

process_runs.start accepts parent_run_id plus the parent's own step kind — step_id (a process_step, for a process call) or workflow_step_id (a run_step, for a workflow's procedure node, 0037); naming both or neither is a 422. A child may start under a live parent on the same card, depth ≤3; one live child per (parent, step) and one row per attempt; cancel cascades; a child failure does not re-fire the parent's err.card. The root-only indexes are the enforcement; the store's live_run_for_card_tx filters roots, and next_attempt_for_card_tx counts per (parent, step). As built (2026-11-10): the root filter is uq_run_live ... WHERE parent_run_id IS NULL; a workflow parent's child is proven by call_step::a_workflow_procedure_node_starts_a_child_under_the_parent.

5.4 The step executor

process.step drives an attempt: load the run and step, write run_step, execute by kind (agent → agent.run with the resolved process agent; computed/tool → the action via the tool agent; gate → open the approval and park; call → start the child and poll), then judge the output, append the outcome and enqueue the next step. Retry appends an attempt; timeout is error_class=timeout; every write is idempotent on (run_id, position, attempt).

5.5 The judge

  • laya.judge is an external action against https://api.nonagentic.ai/laya, authenticated with the conveyor's laya licence by a typed client — never a plain unauthenticated HTTP call. Request: the step output, the SOP's acceptance_criteria and the card's measured facts. Response: {score, accepted, reason} — the confidence margin is the signal, not the label.
  • Reject → rerun the same step with reason added (at most 2 rejects), then the card goes BLOCKED → coach. Outage → wait; never fail open, never count as a reject.
  • The verdict is written to run_step.judge (decision, score/margin, reason, criteria, output hash) so acceptance is auditable and replayable. An eval inspection uses S19's eval_runs and records the same shape.
  • As built (2026-11-10): the judge is a step-executor seam over the registered laya.judge action and the checker/eval inspection kinds. A reject reruns the same position with the reason, bounded by the SOP's max_rejects (default 2); an exhausted budget fails the run (→ err.card → the coach); an outage parks the step and re-enqueues it.

5.6 The process map

process_map is a versioned document bound to a project type; nodes process|capability|phase|milestone, edges flow. It is declarative (no execution, no reordering). The API serves it (process_maps.get/list), the PM plans from it, and the UI overlays the project's live position (running/done/blocked) from the runs. A prescribed sequence of external API calls is a process whose steps are tool calls, not a second execution model. UI surface declared for S12: screen 7 (processes — steps, SOP, judge verdicts, user-facing outputs) and screen 22 (process map — the DAG with the live position).

5.7 The bus

Port the envelope {id, topic, from, correlation_id, procedure, tenant_id, job, payload}; topics work.requested|succeeded|failed, tool.call|response, dead.letter; groups process|tool; XADD/XREADGROUP/ XACK/XAUTOCLAIM; max_deliveries=5 → bus:dead. The relay publishes unpublished event rows by seq (woken by pg_notify), records bus_stream_id/published_at, and re-delivers after a Redis loss because the step's outcome in Postgres is the truth. FLUSHALL + replay must reproduce the same run state. As built (2026-11-10): crates/bus (envelope, groups process|tool, the relay and the DLQ) is in the workspace, and the process.step job is the Redis-absent fallback — a run still executes from Postgres with Redis down. CI starts a dind Redis from the archetype's redis_image.

5.8 The computed set (code, not processes)

projects.create creates project + board + start card in one transaction and emits card.created; the start card is project_start_request_analysis (intake). It starts a root run only when the tenant has published a start process — there is no universal seed, because a tenant may run accounting, marketing or human project management (owner ruling 2026-11-10). The move step is cards.move. wip.pull reacts to card.moved and keeps may_move as the guard. err.card runs on run.failed, moves the card to BLOCKED, comments and starts the coach root run. Approval routing is the gate resume. The hook route and CONVEYOR_HOOK_SECRET are deleted.

8. Traps

  • The bus is not the record. If a handler writes to Redis-only state, a Redis restart loses it. Every outcome is a Postgres row in the handler's transaction; the envelope is a nudge.
  • A child must not take the root slot. live_run_for_card_tx must filter parent_run_id IS NULL; otherwise runs.create 409s while a coach child runs.
  • A retry must not duplicate a side effect. Idempotency is the envelope id and (run_id, position, attempt); the action's own Idempotency-Key is uuidv5(run_id:step:attempt).
  • A judge reject is not a retry storm. The rerun budget is the SOP's max_rejects (default 2); an exhausted budget is a block, never an infinite loop. A laya outage is not a reject.
  • The map must not become the executor. It is a document; an edit to it changes no run. A process's order is its step positions.
  • The DAG must not become the process executor. crates/workflow is retained as the tool-sequence executor, and process.step never calls its graph planner: a call step resolves child_process_key process-first, workflow-second. Do not add a process step kind that runs a graph.
  • RLS FORCE. Seed/backfill as owner sees zero rows; every new table/column path stays tenant-scoped.
  • The 280 are a catalogue. The seed has 74 card-type codes and must filter to the 70 active pairs; a tenant's process is a row, not a code constant.

9. Decisions closed here

  1. Storage: process/process_step (renamed) + procedure (SOP) + process_map; migrations 0035_process_tree.sql and 0036_s19_output_grade.sql. The workflow engine is retained as the tool-sequence executor (owner ruling 2026-11-09); there is no drop migration.
  2. Step kinds agent | computed | gate | call; actor process_agent | tool_agent | system | human; no graph, no predicates, no loop nodes; continue | fail | retry bounded.
  3. The run tree: root-only live index, one live child per (parent, step), depth ≤3, cascade cancel.
  4. The judge is the SOP's inspection: laya (external action), an eval or a checker; {score, accepted, reason}; reject → rerun with the reason, max 2, then BLOCKED → coach; outage waits.
  5. The process map is a declarative DAG per project type; the UI renders it; nothing executes from it.
  6. System capabilities (PM, coach, kata) are fixed; the rest is tenant-defined; the 280 are the default catalogue.
  7. The bus is the care-bus port (Redis Streams); Postgres is the record; the outbox re-delivers.
  8. No delta: rows: the four named flows are absorbed, and the two remaining are processes.
