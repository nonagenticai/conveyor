Programme project: S06a · issues none yet

Sources: nonagenticai_mcp_server @ dd2cabf6, fr @ 6f7c5097. Authority: 02-source-map/30-rm-planka-mcp-n8n.md §3; emitter field set: 02-source-map/20-fr.md.

1. Objective

agent reaches its backend only through mcp_server, and that binding is two HMAC-signed HTTP endpoints. This slice makes the conveyor speak both byte-compatibly: same path, grammar and five response words inbound; same three events, fields and 204 contract outbound. D18 makes it permanent — the conveyor is one more backend behind mcp_server, so conformance is maintained, never proved once and retired — and the agent handles approvals and questions through the same primitive: a question is an approval. mcp_server changes only MCP_FR_BASE_URL and the secret; the conveyor's outbound destination is MCP_EVENTS_URL.

2. Starting state

  • S04: registry, POST /api/actions/{name}/invocations, RFC 9457 errors.
  • S05: projects.*; S06: approvals.decide, the channel dispatcher, approval, delivery, the approval.closed.emit job kind — every task input is an fr approval, questions included (src/external/adapter.py:55).
  • S02: outbox event, job, HTTP client.

3. Scope

IN — both directions verbatim: POST /api/webhooks/mcp/incoming (receiver) and POST {MCP_EVENTS_URL}/api/channels/fr/events (sender); HMAC; the five-command grammar (questions ride as approvals — no second concept); the five response words; the three event types; inbound 200/400/401/413/503, outbound 204/401/413/503; the emitter job; a stub receiver and a suite replaying Python-captured fixtures.

OUT — agent (untouched, SPEC §4.5); mcp_server's 48 tools, catalog, runs and 36 tables (it stays); the conveyor's own MCP surface (S10); every other fr caller (S13).

auth X-Channel-Timestamp + X-Channel-Signature: sha256=<hex>, shared secret FR_MCP_CHANNEL_SECRET
envelope {address, text, correlation_id} + optional job, on_behalf_of; compact JSON, sort_keys=True at the sender
grammar projects.create {json}, projects.get {"id"}, projects.close {"id"}, approve <approvalId> [comment], reject <approvalId> [reason]

Both write decided_by_kind='agent' and via = {channel:'mcp', agent_member_id, product} (the identities resolved above), so D18's provenance is on the row, not only in the SPEC
projects.create title + project_type required; passthrough description, problem_statement, desired_outcome, repository_url; project_type must match ^[a-z0-9_-]{1,128}$
text cap MAX_TEXT = 4000 characters (text.length, UTF-16 units, not bytes)
identity agent:<tenant_id> must equal the run's tenant, else error/actor_tenant_mismatch; it resolves through membership(meta.product) to that tenant's app_user(kind='agent'), which is the approver_id; the tenant's channel_binding(channel_kind='mcp') must exist and be active — the binding is tenant-level (uq (tenant_id, channel_kind, route_key)), not per agent; the decision is written with decided_by_kind='agent'. agent: is the only address scheme, in two forms — agent:<tenant> / agent:<tenant>:<product> (agent_members.address LIKE 'agent:%', measured); anything else, or unresolvable, is unknown-sender
response HTTP 200 {status, result.project_id?, approvalId?, code?}, status ∈ result | pending-approval | no-action | error | unknown-sender, code matching ^[a-z_]{1,64}$
transport errors 401 invalid_signature; 413 payload_too_large (> 65536 bytes); 400 bad_request (body not {address,text,correlation_id}, or text.length > 4000 — measured on fr); nothing else is a 4xx

The client must be able to map every answer: unknown-sender → actor_unresolved; no-action/error → sanitized code; pending-approval + string approvalId parks an input; result + string result.project_id starts. Non-JSON or non-object → external_result_invalid; 5xx → fr_unavailable.

5.3 Signing, byte-exact

canonical = ascii_decimal(unix_seconds) || "." || raw_request_body_bytes
signature = "sha256=" || lowercase_hex(HMAC-SHA256(key = secret_utf8, message = canonical))
  • Send X-Channel-Timestamp: <ascii digits>, X-Channel-Signature: sha256=<hex>, Idempotency-Key: <uuid4>; neither receiver validates the last.
  • Verify the raw bytes as received; parse JSON only after verification succeeds.
  • Header lookup is case-insensitive; values are not trimmed; the timestamp is ASCII digits only (no +, -, spaces, fraction).
  • Refuse when abs(now_seconds - timestamp) > 300; exactly 300 is accepted (Python uses >).
  • Compare in constant time; on failure answer the single word invalid_signature and log the discriminator (skew / mismatch / bad_shape) server-side only. An overflowing timestamp is a refusal, never a panic.

8. Traps

  1. Re-serialisation. A serde_json::Value round-trip reorders keys and changes spacing, so the MAC fails on a valid request; take Bytes, never Json<T>.
  2. Header casing. X-Channel-Signature arrives lowercased from some clients; Python lowercases the whole map. A hand-rolled map keyed by the literal name 401s every real request.
  3. Seconds vs milliseconds. as_millis() puts every timestamp ~56 years ahead and refuses everything, looking like a secret mismatch.
  4. The timestamp is inside the MAC. Sign ts "." body; on receive recompute with the received ts. Body-only verification lets a captured body replay forever.
  5. MAX_TEXT counts characters, not bytes. Match fr's text.length (UTF-16 units), not .len(); .len() rejects valid multi-byte text at a fraction of the real limit.
  6. A syntactically valid body of the wrong shape still gets 204. {"type":"approval.requested"} with no approval_id is accepted, logged and ignored. This endpoint has four status codes; a 400 on shape breaks the client's raise_for_status.
  7. The tombstone is per run, not per approval id. close(tenant, run, approval) closes one run's input; another live run of the same approval must still receive it.
  8. The secret has two names and one value. MCP_FR_CHANNEL_SECRET and FR_MCP_CHANNEL_SECRET; rotate both or both directions 401 with no other symptom. Keep it a secret reference, never in channel_binding.config.
  9. A 401 must not say which half failed. One body, one code, one timing path; the expected digest is never logged.
  10. 204 means no body — {} is a protocol violation the stub must reject.

9. Decisions closed here

  1. Verify-then-parse on raw bytes, both directions — no re-serialisation anywhere.
  2. approval.requested at creation, approval.closed from the 30 s job — one event per transition, keyed on the outbox event.id, so a re-drive cannot duplicate.
  3. Emit fr's full measured field set, including tenant_id, kind, impact_analysis — dropping a field fr sends is exactly what R11 forbids.
  4. The conveyor enforces agent:<tenant_id> server-side even though mcp_server pre-checks: a client-side check binds only that client.
  5. Channel failures are delivery failures, not command failures — a 401/503 lands delivery.state='failed' with last_error; the originating action is never retried because a notification failed.
  6. One deployment-wide secret, matching fr; not per tenant.
  7. The stub implements the receiver contract, not a mock — 204/401/413/503, tombstone and first-report-wins, so a wrong assumption fails here, not at S14.
  8. MCP_EVENTS_URL is the conveyor's own outbound var. It lives today on fr's backend as http://mcp.mcp.svc.cluster.local:8033/api/channels/fr/events (measured 2026-11-07); it moves to the conveyor unchanged. S14 repoints MCP_FR_BASE_URL (on mcp-external-driver) at the conveyor and rotates one secret.
  9. The agent decides as decided_by_kind='agent', and the channel's answer vocabulary is frozen at decision + comment/reason — it is an external contract (R11), so adding a word is a contract change.
