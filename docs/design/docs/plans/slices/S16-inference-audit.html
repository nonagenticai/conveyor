S16 — Inference ledger and prompt audit

Programme project: S16 · issues #20

1. Objective

Every model call the conveyor makes becomes a durable, tenant-scoped row carrying the prompt's identity, the token counts and the provider's prompt-cache classes, so "what did this cost and was it cached" is a query rather than a guess. On top of that record, a prompt audit inventories the three prompt surfaces the conveyor owns — procedure step templates, every action's description, and the copilot's system prompt — classifies them against the claude-api prompt-audit method's four anti-pattern groups, and reports findings with confidence and a proposed diff. Both are ordinary actions, so both are user-invokable over HTTP and machine-invokable over /mcp.

2. Starting state

  • The action engine already owns the external call and writes action_invocation + audit_event in one transaction (crates/actions/src/invoke.rs); the two model-call actions are completions.create (built, S10) and inference.chat (declared by S13, not built — it declares captures_usage when it lands).
  • inference-router already returns usage with both cache classes and already accepts X-Correlation-Id; the conveyor drops both on the floor.
  • S11's procedure/procedure_step/run_step and S10's conversation_turn exist and are the join targets.

3. Scope

IN. The three tables (§2.17); the engine capture seam; the eight actions; the two scopes and four events; the prompt_audit.run and prompt_audit.sweep jobs with the built-in prompt; the two triggers — a manual prompt_audits.start, and a configurable after N executions policy the sweep enforces against inference_call itself; the draft check that becomes part of publishing (prompt_audits.check, called by S11's publish); the two screens declared for S12.

OUT. Building any UI — the screens belong to S12 and are listed here so S12 may not invent them. Absorbing inference-router or billing_service: the conveyor reads neither database, adds no cache endpoint and emits no cost event (SPEC §4 still says never absorbed). A tenant-authored prompt store — prompt_ref stays the built-in versioned reference of CONTRACT §17. Any AI-driven fixing of prompts: the audit proposes, a person decides, and procedures.update applies. Kata-specific tables: kata's prompts are procedures and the kata domain stays outside this spec — kata consumes findings through prompt_findings.list, which is already on its allowlist. A configuration table or action for the cadence: the policy rides tenant.settings.prompt_audit through the existing tenants.update_settings, so the trigger is configurable without widening this slice.

8. Traps

  • sqlx::migrate! embeds the set at compile time — a new .sql is invisible until the crate rebuilds and the command exits 0 either way. Touch migrate.rs and verify by the ledger, never by the migrate log line.
  • Usage capture must never fail the call. The row is written after a 2xx; a response with no usage stores unknown, and a parse failure logs and continues. A model call that succeeded must not become an error because bookkeeping did — but it is in the same transaction, so a genuine DB failure rolls the call's audit row back with it. That is the honest trade: one transaction, no divergence, and the failure is visible as a missing row.
  • Derive cache_status from the response, never the request. The request says nothing about caching; a caller that asked for a cache breakpoint still misses on a cold prefix.
  • Do not emit cost. The router meters this same call into billing, whose billing_cost_events already carries both cache classes; a second emission double-counts a tenant's bill.
  • AGENT_TOOLS is a fixed-size array ([&str; 22]): adding six entries changes the type, the MCP allowlist test and /mcp's tools/list snapshot together.
  • The audit reads the live registry, not a copy. actions.list is the writer of record for a description; an audit against a checked-in copy would report findings about text that no longer ships, and would itself become the staleness problem it exists to find.
  • The join keys are not foreign keys, and that is deliberate. An FK's RI check runs as the table owner and bypasses RLS, so it would accept another tenant's run_id; the engine resolves each id in the caller's tenant first and the inference_call_join_key CHECK keeps the row answerable without one. Copying the FK idiom from conversation_turn_conversation_fk without this step is the defect.
  • prompt_audit@1 is versioned, not edited. Changing the audit prompt means prompt_audit@2; an audit row names the version that produced its findings, and rewriting v1 would make every past finding unreproducible.

9. Decisions closed here

  • inference_call is written by the engine, not by a handler — the call site already owns the response and the transaction; a handler-side writer would be a second path for the same fact. Contract-level: CONTRACT §18.
  • Cache is three states plus unknown, never two. A write is a deliberate warm priced above a miss's saving, so folding it into "miss" would make every optimisation look like a regression. SPEC D23.
  • The audit is a procedure with one bounded model call, not agent.run: it needs no tool loop, and D22's executor slot must not grow a further kind for a reporting feature.
  • Findings are decided by a person; the audit holds no write scope over its own surfaces. CONTRACT §18.
  • Screens are declared here and built in S12 — S12 may not invent a screen, action or table.
  • Contract change taken: three tables beyond §2.16's ceiling, with D23 (2026-11-09).
  • Two triggers, and the second one is configurable (George 2026-11-09): a manual prompt_audits.start, and an after N executions policy in tenant.settings.prompt_audit that fires as an event on the Nth captured call (owner decision 2026-11-09, §10 Q2 — the slice's original sweep default is superseded). inference_call is the counter — the rows since the tenant's last audit, excluding the audit's own call — so the trigger adds no counter column and cannot drift from the ledger it is counting. The policy names the target_model the event-created audit will call; without one it is not armed.
  • The cache report groups by prompt_sha from day one (George). The whole point is to see which prompt is cache-hostile; model and caller alone cannot answer the Group 4 finding it exists to evidence.
  • A draft is audited at publish, not on a cadence (George: "audit of a draft procedure should become part of the publishing of a procedure version"). procedures.publish runs prompt_audits.check; a high-confidence finding refuses with 422 procedure_audit_findings, and acknowledge_findings: true overrides it and is recorded on the publish's audit_event — a scoped, logged override, never a silent one.
  • The findings feed the kata-executor (George 2026-11-09): kata reads prompt_findings.list and starts audits with prompt_audits.start, both already on its allowlist. S16 adds no kata surface and no kata table.
  • Retention: 90 days (George) — a cache ratio over a month is noise, over a quarter it is a signal.

10. Open questions

# question answer (owner, 2026-11-09)
1 Is served_model ever different from model for our provider set? Store both, report on served_model, fall back to model.
2 Is the after N executions check a periodic sweep or an event on the Nth call? An event on the Nth call. The counter is still the ledger (rows since the last audit, excluding prompt_audit@1), so there is no separate counter to drift; prompt_audit.sweep is not built.
3 Does a high-confidence finding from prompt_audits.check block publishing of a first draft, or only of a version that replaces a published one? Both. A first publish is exactly where a dated prompt enters the system.

11. Build amendments (CCRs, 2026-11-09)

  1. prompt_audits.check takes procedure_id, not procedure_version_id — no such identity exists; publish already uses procedure_id.
  2. check is pure. A finding cannot be persisted without an audit (audit_id FK NOT NULL, target_model NOT NULL), so check returns CheckFindingViews and persists nothing. Only prompt_audit.run persists findings, under a real audit.
  3. Gate item 5's SQL is invalid (action_registry.scopes does not exist; internal actions are never rows there). Replaced by a compile-time registry assertion that no prompt_* action holds procedures:write.
  4. prompt_findings.list was not on AGENT_TOOLS despite §9's claim; S16 adds it plus the other five read/start tools (22 → 28 on S16's baseline).
  5. The event trigger needs a model: tenant.settings.prompt_audit gains target_model; without it the policy is not armed and the capture seam logs and skips.
  6. Reproducibility is asserted on the deterministic scan, not on the model call: an LLM cannot be bit-reproducible. prompt_audit.run is proved with the scripted model harness plus one live rehearsal.
  7. The actions surface is declared but empty: ActionSpec carries no authored description (the OpenAPI description is generated boilerplate). Procedure templates and the copilot SYSTEM_PROMPT are the audited surfaces until specs carry descriptions.
  8. note is not accepted on prompt_findings.decide: no column persists it, so it is refused rather than silently discarded.
