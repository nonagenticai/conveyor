S20 — Eval hillclimb

Programme project: S20 · issues #24

1. Objective

The eval-hillclimb and cost-hillclimb methods become a loop over one eval: a goal, a stopping condition, a fixed train/test split, and rounds that each propose a change, run the full set, and are kept or reverted on the held-out number. At the end a person has the winning version applied, a per-round table with train and test side by side, a paired delta with a significance test, two before/after transcript pairs, and the failures nobody could fix classified by cause rather than blamed on the model.

The loop is deliberately not autonomous. Every round returns to the caller, because the method's check-in cadence is a person's, and because a change whose effect sits inside the noise floor is kept or reverted by chance — spending a full pass to learn that is how a hillclimb burns a budget without moving the score.

2. Starting state

  • S19: eval/eval_version/eval_case/eval_metric, the case runner, the four grader kinds, eval_runs with variant, round, change_md, change_patch, summary, narrative_md, the report, the split and its digest, and eval_runs.report (mean, CI, noise floor, cost).
  • The split is drawn once by S19 and cannot move; eval_audit already computes the noise floor against the headroom and the smallest shippable delta.
  • Nothing spawns an analyzer: S19 has no notion of a proposed change, only of a run.

3. Scope

IN. One table (§2.20); the six actions, two events and screen 21 declared for S12; the round protocol (analyze → apply → run → record → keep or revert) as one action per round; the goal/guardrail model; the stopping conditions; the stall-triage round; the paired comparison with exact McNemar and its refusal rule; the cost-search mode and its adoption gates; the final report.

OUT. Any UI — screen 21 is declared here for S12. A model loop of its own: the analyzer is an agent principal over /mcp (D19/D22) or a person writing change.md directly — the conveyor hosts no second runtime. Automatic application of a change to production code: S20 writes change_patch and a snapshot into the round; applying it to a live procedure is an ordinary procedures.update a person makes. Editing the eval, its cases or its metrics mid-climb — that is a new eval_version, and a compare across versions is refused. Re-implementing the benchmark's McNemar (S17's is the same function; S20 calls it, it does not port it twice).

Part A — state and the round. Steps 1–4. Proves: a two-round climb on a real eval produces a kept round and a reverted one, with the reason recorded. Part B — comparison, triage, cost. Steps 5–8. Proves: a paired delta recomputes by hand, and a stalled loop produces a categorisation round instead of a fourth content round.

  1. 0027_s20_eval_climb.sql; touch crates/store/src/migrate.rs. rbuild -- run -p conveyor-server -- migrate and verify _sqlx_migrations version 27.
  2. domain::eval::climb — the loop machine, keep_or_revert (train up/test flat ⇒ revert; both up ⇒ keep; train down/test up ⇒ keep only if it repeats on a second run; tie ⇒ later round), the stopping predicate (plateau K≥3, rounds, manual) at a delta above the noise floor. rbuild -- test -p conveyor-domain eval_climb.
  3. store::eval::climb + eval_climbs.start/get/list/stop; the plan sign-off (gate='eval_climb_plan' carrying the goal, the will/won't-change table and the stop condition) is required before round 1. rbuild -- test -p conveyor-actions eval_climb_start.
  4. eval_climbs.round — writes eval_run (variant='v<N>', round, change_md, change_patch, summary.suspicious) and prediction, then starts the run; approve_each_round emits a gate='eval_round' approval and refuses the run until it is decided. rbuild -- test -p conveyor-actions eval_round.
  5. eval_climbs.compare — paired per-case delta, CI, and S17's exact McNemar; refuse when the two runs name different versions, graders, or splits (409 not_comparable). rbuild -- test -p conveyor-actions eval_compare.
  6. Stall triage — after two consecutive rounds whose test delta does not clear the band, round requires a buckets payload (artifact_gap | grader_disagreement | harness | structural | variance, counts, one line each) and writes it to change_md in place of a diff; a grader fix re-grades stored transcripts under a new eval_version and re-runs the comparison. rbuild -- test -p conveyor-actions eval_stall.
  7. Cost search — goal.target='cost_usd' with hold:[<quality metric>], the guide's search order as a state machine on eval_climb.goal, adoption gates registered before round 1, and the price screen computed from inference_call. rbuild -- test -p conveyor-actions eval_cost_walk.
  8. Final report: rewrite narrative_md (status table + the four-part summary), name the winner, declare screen 21's read model. rbuild -- test -p conveyor-actions --test eval_final.

8. Traps

  1. A split chosen by score. Hand-picking the worst cases for train guarantees regression to the mean and a flat test set. S19 draws it and locks it; a climb that could redraw it has no held-out signal at all.
  2. The analyzer reading test. The wall is data access (evals:approve), not an instruction. A round whose proposal cites a test transcript is void — record the transcript ids the analyzer was handed and refuse the round if any is a test id.
  3. A change too small to see. If the best case for a change sits inside the noise floor, the keep/revert decision is a coin flip. delta is set from the measured floor, and a proposed change that predicts a smaller gain is refused with the number.
  4. Stacking changes. One round is one hypothesis, even when its patch touches several places. Bundling makes a win unattributable and a regression impossible to bisect.
  5. Trusting an implausible jump. A judge-graded score that leaps further than the change can explain is a gamed judge until hand-checked; record summary.suspicious and show the outputs.
  6. Grinding content at a wall. Three rounds that do not clear the band mean the failure is the grader, the harness, the artifact's structure, or variance — not more content.
  7. A maintained spend counter. It drifts from the rows it counts. Sum the results.
  8. Re-grading without re-comparing. A rubric fix changes every variant's number; comparing a new grade against an old run is two scales. Re-grade every variant in place, then compare, and say how many cases moved.

9. Decisions closed here

  • A round returns to the caller. eval_climbs.round runs one round and stops, so the check-in cadence is a person's by default; approve_each_round additionally gates the change itself.
  • The split is not the climb's. It belongs to S19's version, is drawn once, and a climb that cannot redraw it cannot overfit to the number it reports.
  • Comparison reuses S17's McNemar. One implementation of the exact test in the estate; a second would be a silent divergence in a published number.
  • Stall triage is a round, not advice. After two flat rounds the next round must carry buckets; a fourth content round against the same wall is refused.
  • Cost search is a goal, not a mode of the loop. goal.target='cost_usd' with a quality guardrail reuses the same rounds and the same comparison; the search order is state on eval_climb.goal, so a resumed session does not restart at the top.
  • Applying the winner is a person's action. S20 names the version and ships the patch; it never rewrites a published procedure.

10. Open questions

# question default
1 Who proposes a change — an agent or a person? either: eval_climbs.round takes change_md/change_patch from the caller, so an agent principal over /mcp and a person use the same action
2 Are test traces retained per round? yes, under the eval's retention; the wall is the read scope, not deletion — the final report needs before/after pairs
3 Does a climb run unattended? only with approve_each_round=false and a signed plan; the default is one round per call
4 What happens when the goal plateaus but another metric has headroom? offer to change the target and run a round pointed at it under the constraint of not regressing what won — ask first, never silently retarget
5 Is a cost walk's winner promoted automatically? no — it is named in the report with its guardrail intact; promotion is a person's procedures.update
