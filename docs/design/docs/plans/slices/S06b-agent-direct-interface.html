S06b — Agent direct interface

Programme project: S06b · issues none yet

Supersedes S06a-mcp-server-channel.md (SPEC D18 → D19, 2026-11-08). S06a's HMAC channel, text grammar and shared secret are not built and are not carried forward.

1. Objective

The agent app operates the conveyor over the conveyor's own /mcp surface. At the end, one real agent task creates a project, reads its progress, answers an approval and closes the project — with the decision recorded as decided_by_kind='agent' — and no component called nonagenticai_mcp_server is in the path.

2. Starting state

  • S04: /mcp (rmcp streamable HTTP) serves the same action registry as HTTP, parity-tested (crates/actions/tests/parity_http_mcp.rs).
  • S05: projects.create|get|close, cards.get. S06: runs.list, approvals.list|decide, events.list.
  • S02: JWT/dev authentication, membership resolution, identity.

3. Scope

IN — the four gaps that stop the existing /mcp from being consumable by agent: the tool key, machine authentication, principal attribution, and an approval-request action. Also the agent-side registration contract (implemented in agent, gated here).

OUT — the fr toolkit in nonagenticai_mcp_server (retires with fr at S14); the agent's task/elicitation extension for external MCP servers (S06c; v1 polls until it lands); the conveyor's copilot surface (S10); every other fr caller (S13). No HMAC channel is built.

_meta.operation. The agent names an imported op from _meta.operation when it is a valid object.verb, and otherwise from the tool name as tool.<snake> (mcp_import.rs:199-211). Every conveyor tool must carry "operation": spec.name next to x-action-name.

Machine authentication. authenticate today accepts dev-auth or an OIDC JWT and then requires exactly one membership (authn.rs:41-65). Add a licence branch: a non-JWT bearer is verified against the licences service (GET /licenses/active?tenant_id=&app_key=conveyor is not it — the entitlement sync is S02's; this is introspection of the presented token) behind a short-TTL cache, resolving (tenant, app_key, subject). A JWT-shaped token that fails JWT verification is never retried as a licence token. Resolve the subject to an app_user(kind='agent') and a membership scoped to the tool list below.

Licence verification is on the request path, so it is cached and fail-closed. A verified licence is held for the licence's TTL, capped at 60 s; an unreachable licences service refuses (503 licence_unavailable, no principal) and never admits. The cache is keyed by the token's hash, never by tenant, so a revoked token cannot ride another tenant's entry.

S06d supersedes the list mechanism, not the capability. The names below became the MCP channel's compiled default in crates/actions/src/channel.rs (MCP_DEFAULT_ACTIONS); the tenant-admin may now add or remove them through channels.policy_set. The machine floor (ActionSpec::machine_forbidden) still refuses every eval sign-off, held-out read and administrative action, so a stored grant can never widen what this section calls the wall.

8. Traps

  1. _meta is the only channel — rmcp flattens task/result payloads and drops unknown top-level fields. The operation key must live in _meta, not in a sibling object.
  2. One membership — authenticate rejects 0 or >1 memberships. A licence that resolves to several tenants must choose the tenant from the licence, never from a header.
  3. JWT shape — a JWT-shaped token that fails verification must not fall through to licence introspection; otherwise a revoked credential becomes a valid one.
  4. open_gate_tx needs a running run — a standalone escalation with run_id IS NULL must use insert_approval_tx.
  5. uq_appr_pending includes run_id — nullable, so multiple standalone approvals do not collide; do not "fix" it by adding a second index.
  6. Tool scoping is the authorization — /mcp filters by role; an agent principal with admin would see every action. The membership role must be the scoped one.
  7. Do not rebuild the HMAC channel — if a later session finds S06a text describing it, that plan is superseded; the seam is /mcp.

9. Decisions closed here

  1. MCP, not REST. The wire, the import and the schemas exist on both sides; REST is a fallback only for a tool that cannot be expressed over MCP.
  2. The conveyor's /mcp is the agent interface. mcp_server remains the gateway for coding, care-bus and builder tools, and its fr toolkit retires at cutover.
  3. Licence bearer, introspected. One licence per tenant carries the tenant; an OIDC service account would hit the one-membership rule for every tenant it acts for.
  4. Polling is the fallback; S06c adds MCP tasks. The agent's task extension is platform-server-only (external.rs:8), so projects.get + approvals.list inside a durable job step ships first. S06c implements SEP-2663 in the conveyor (projects.execute, tasks/get|update|cancel) and the agent's external-task client; the polling path stays as the fallback for a client that cannot run tasks.
  5. Typed results, not _meta blobs. The fr-specific _meta["ai.nonagentic/fr"] shape is not reproduced.

CONTRACT-CHANGE REQUEST: 01-CONTRACT §8 states the two MCP surfaces "must never be conflated" and that "a token on /mcp is not a substitute for the signed channel". D19 makes /mcp the agent interface. Proposal: one surface, with the consumer boundary stated (agent = licence principal; other consumers = their own principal). No slice may act on this until the contract is amended.
