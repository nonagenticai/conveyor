S15 — Capability, knowledge and memory

Programme project: S15 · issues #19

Design authority: docs/KNOWLEDGE-MEMORY.md. This slice builds it.

1. Objective

A capability becomes an aggregate with a persisted executor spec, a versioned domain-knowledge binding and two memories. S15 builds the spec and its resolution, not a model loop: capability_agent is consumed by S13's agent.run (D22, CONTRACT §17). At the end, a card's run resolves its capability and executor, the capability's readiness is reported before the run starts, a cited passage is retrieved from a pinned strata pack, work-package memory is written, consolidated into strata_rag, and recalled by source_id.

2. Starting state

  • S03: card_type, card, run, catalogue_entry (including kind='capability', 17 seeded rows), approval.
  • S06: runs and approvals; S11: procedure, procedure_step and the action/gate validation.
  • S09: documents.ingest → strata_ingest; retrieval.query is an external action. Neither is a capability binding.

3. Scope

IN — the five tables, the columns on card_type/run/procedure, the ten actions, two events, one job kind, the strata_rag client (query + document write + source prune), and the migration that removes catalogue_entry(kind='capability').

OUT — the model loop: capability_agent is configuration (CONTRACT §17); the loop is S13's agent.run and S10's copilot is the interactive surface, so S15 builds neither. Also out: embeddings, model hosting, answer generation (knowledge.answer stays the executor's); a tenant-authored prompt store (v1 resolves built-in prompt_ref only); KAG (archived 2026-11-04); the copilot (S10); S08's project_capability ledger — ⚠️ dropped by migration 0011 on the S00 day-2 verdict (0 rows, no consumer), so S15's capability aggregate has no predecessor to reconcile with.

8. Traps

  1. Cross-source dedupe in strata_rag — identical text belongs to the first source; pruning that source deletes the shared document. The card-id header is the defence.
  2. Immutable documents — there is no update-in-place; consolidation is ingest-new + prune-old, never PUT.
  3. One document per request, embedded synchronously — never call strata per event; consolidate in a job.
  4. Pack targeting is explicit — a default query searches only the caller's tree; platform leaves must be named in leaf_ids.
  5. Null run_id and uq_appr_pending — nullable columns make multiple standalone rows legal; do not add an index to "fix" it.
  6. catalogue_entry(kind='capability') removal — the seed and any kind='capability' lookup must move in the same migration, or a card type resolves to nothing.
  7. RLS — every new table needs tenant_id and the policy; a table without it is a cross-tenant leak, not a bug.
  8. A second loop in S15. capability_agent is configuration (CONTRACT §17). If this slice finds itself calling a model, it is building S13's agent.run; resolve the spec, carry {capability_agent_id, prompt_ref, model_ref} into the step input, and stop.
  9. A prompt table invented to fill prompt_ref. v1 resolves a built-in <name>@<version>; a tenant-authored store is a later slice and would put an unversioned text blob behind an admin edit.
  10. Two retrieval paths. retrieval.query (S09) is the raw strata passthrough; knowledge.query is the capability-bound one and is the only one a run uses. Do not add a third, and do not let a capability call retrieval.query directly.

9. Decisions closed here

  1. Capability is a table, not a catalogue kind — it is an FK target and carries executable definition.
  2. One capability pack, not one per capability — a pack is one root and versions are immutable.
  3. Conveyor owns the binding, strata owns retrieval — no second knowledge plane in the conveyor.
  4. Hot rows are the record; digests are derived — strata is never the system of record.
  5. Maturity is computed, not stored — a projection over execution history.
  6. capability_agent is the persisted executor spec, not a loop — the run wiring stores run.capability_agent_id; the step executor resolves it into the agent.run input; S15 proves validation, resolution and recording (CONTRACT §17).
  7. prompt_ref is a built-in versioned prompt in v1 — <name>@<version>, no prompt table; the resolved id and model travel in the agent.run step input, so the invocation hash pins them.
  8. Readiness is pre-run, not a mid-run warning — 409 capability_not_ready with blocking[] before the first step; knowledge_degraded is the runtime case where a pack disappears after start.
  9. retrieval.query and knowledge.query are deliberately distinct — the first is a raw passthrough (S09), the second is capability-bound and is the only path a run uses.

Why five tables and not one. capability and capability_relation are the aggregate; capability_agent is configuration with its own lifecycle; capability_knowledge is a versioned binding that changes on a different cadence from the capability; work_package_memory is the only high-write table and must not share a row with configuration. Folding them would put a per-run write path behind the same lock as an admin edit.

Proposal: add S15's five tables (count 67 → 72) and two forward references (run.capability_id, run.capability_agent_id, added by 0020). No slice acts until amended.

13. Build record — step 12, readiness (2026-11-09)

Built and gate-green. crates/actions/src/capability/readiness.rs is the ONE computation: capability_readiness_tx collects domain::capability::Readiness blockers (the capability exists and is active; exactly one active capability_agent; that agent's prompt_ref is an active catalogue pin; every allowed_actions entry is registered; every required knowledge pack resolves to at least one leaf). readiness_fields maps the blockers to FieldError once, and both surfaces use it: capabilities.get returns {ready, blocking[]}, and procedure_runs.start's ensure_start_ready refuses 409 capability_not_ready with the SAME array in errors[].

  • The empty-leaves defect is fixed. pack_leaves returns Ok(vec![]) for a published-but-empty pack and the old guard treated that as ready. CONTRACT §17's "no resolvable leaves" now blocks (pack_state, unit-tested, with the empty arm proved by reversal).
  • prompt_ref is a readiness concern, not a write refusal (row k amended above). Resolvability reads the tenant's catalogue (store::prompt::get_prompt_tx, S13's 0030): absent or retired is prompt_unresolved — the same code the executor's own refusal emits. capability_agents.create keeps refusing only the grammar.
  • CCR 1. CONTRACT §17 names blocking[] for both surfaces. The 409 keeps the API-wide errors[] envelope; the GET names its field blocking. Both carry the identical Vec<FieldError> produced by one function, so there is no second vocabulary to drift.
