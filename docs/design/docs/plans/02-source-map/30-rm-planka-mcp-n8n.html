HMAC (exact). Canonical string is <unix-seconds-timestamp>.<raw-body-bytes>, HMAC-SHA256 keyed by the shared secret, hex, prefixed sha256=. Headers: X-Channel-Timestamp (ASCII digits) and X-Channel-Signature: sha256=<hex>; the sender also sets Idempotency-Key (a uuid4) but this receiver does not validate it. Tolerance is ±300 s (SKEW_SECONDS = 300). The body is verified as raw bytes as transmitted — re-serializing breaks it; header lookup is case-insensitive. Secrets: fr side FR_MCP_CHANNEL_SECRET, mcp side MCP_FR_CHANNEL_SECRET; base URL MCP_FR_BASE_URL.

Inbound (mcp → fr). POST {MCP_FR_BASE_URL}/api/webhooks/mcp/incoming. JSON envelope {address, text, correlation_id} plus optional job, on_behalf_of, serialized compact and sort_keys=True. Grammar (text, max 4000 chars, fr MAX_TEXT): projects.create {json} (title and project_type required; passthrough description, problem_statement, desired_outcome, repository_url), projects.get {"id"}, projects.close {"id"}, approve <approvalId> [comment], reject <approvalId> [reason]. Identity is the envelope address: an agent:<tenant_id> address must equal the run's tenant (else actor_tenant_mismatch).

Response vocabulary — HTTP 200 body status ∈ result | pending-approval | no-action | error | unknown-sender; plus result.project_id, approvalId, code. Client mapping: unknown-sender → actor_unresolved; no-action/error → sanitized code (^[a-z_]{1,64}$); non-JSON or non-object → external_result_invalid; 5xx → fr_unavailable; other HTTP → fr_rejected.

Outbound (fr → mcp). POST {MCP_EVENTS_URL}/api/channels/fr/events, same signing. ⚠️ The outbound URL is MCP_EVENTS_URL, not MCP_FR_BASE_URL — the latter points at fr itself, so a sender built on it has no destination. Measured 2026-11-07: fr's backend deployment carries MCP_EVENTS_URL=http://mcp.mcp.svc.cluster.local:8033/api/channels/fr/events. Body type ∈ approval.requested | approval.closed | message; all three also carry type and address. Measured from the emitter (fr/backend/src/domain/engagement/adapters/mcp.ts:34-67, pinned 6f7c5097): approval.requested carries approval_id, project_id, tenant_id, correlation_id, kind, description, change_summary, impact_analysis, proposed_answer, proposed_answer_note, allowed_decisions, deblock_actions, expires_at, text (change_summary/impact_analysis/proposed_answer/proposed_answer_note/deblock_actions optional; allowed_decisions is ['approved','rejected']; text is the numbered menu every channel sends); approval.closed carries approval_id, project_id, tenant_id, correlation_id, final_status; message carries correlation_id, kind (approval-request | action-result | action-error | text | report), text and meta (approvalId, actionName, result.project_id, outcome). The mcp receiver reads only approval_id, expires_at and project_id/correlation_id (the last two via _runs/_record); the remaining fields are carried for parity, not consumed.

204 + idempotent close. Every accepted event answers 204 with an empty body — including malformed JSON and unknown type. Errors are 413 (payload_too_large, >64 KiB), 503 (channel_unconfigured), 401 (invalid_signature). Close is idempotent in both directions: inputs.close_everywhere(approval) fans out and a per-run tombstone means a late approval.requested for a closed approval is ignored; _record is a conditional UPDATE that only writes when external_ref has neither project_id nor start_outcome — first report wins. A start approval closed as rejected/expired/voided records start_outcome; an approved start records project_id.

Cutover changes are exactly two values: MCP_FR_BASE_URL and the secret. Nothing else in mcp_server changes.
