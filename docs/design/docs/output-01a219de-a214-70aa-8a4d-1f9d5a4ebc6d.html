Project brief — T18 The real V2 UI (retrospective, 2026-11-24)

Outcome

After T18 a signed-in tenant drives every V2 destination from the conveyor's own application — portfolio, programme, project and work package; organisation, release and binding; procedures intake and publish; tools call and ledger; improve, kata and adoption; operations incident and postmortem; and the ADM phase rail — while the programme measures those screens from the app's real route table and Playwright specs instead of the static design mock. At the snapshot the construction is partial: eight of the ten V2 destination routes render real screens, tools and architecture remain honest gates, and the SPEC_V2 §12 gate is not yet met.

Boundary

In scope: the application shell and navigation, the route registry, the V2 destinations of SPEC_V2 §10.5 plus the execution room, the L1–L4 delivery view, one Playwright spec per destination, and the V2 coverage instrument measured from real routes. Out of scope: new tables, actions, events or ports; SSR, a mobile app or a second router; retiring or redesigning the design pack, which stays the public programme site at /design/ and the reviewed reference (D64); the V1 routes, which are linked and not re-implemented; and any live tenant write or production fixture inside a pull request.

Reuse sources

Reuse apps/web/src/app.rs (router, sidebar and top bar), api.rs (If-Match, Idempotency-Key and approval-id request shapes), auth.rs (OIDC PKCE with an in-memory token), state.rs (tenant, me and manifest signals), sse.rs, components.rs and palette.rs; the existing screen modules and V1 specs; the e2e harness (fixture.ts, dev-server.mjs, playwright.config.ts) and web.yml; the compiled action registry of SPEC_V2 §10.4; docs/design/v2.js and STUDIO-SPEC.md as the reviewed design reference; and the programme, work and measure read models exposed by the owning slices.

Inception units

The project starts from the inception analysis at docs/plans/T18/inception-analysis.md and the architecture design at docs/plans/T18/architecture-design.md. The analysis measures the starting state at main@490ad555: 31 routes, 25 screen modules and 31 specs, all V1, and no /portfolio, /programme, /organisation, /procedures, /authoring, /plan, /improve, /operations, /tools or /design/adm route. The design fixes the destination read and write contracts, the D64/D65 decisions, the single-writer router constraint and the rule that a missing backend capability is a typed dependency, not a local fetch.

Dependencies

Construction is blocked-by T0, T1, T2, T3 and P0 — the model and contracts, the plan spine, the decision ladder, the PM job and the programme definition. Acceptance is blocked-by T4, T5, T7, T9, T10, T11, T13, T16 and T17, because each destination's live scenarios wait on its owning slice, and by T12, whose organisation loop is driven from the UI as the final spec. Issue #526 is related: its generated record is rebased and regenerated, never hand-merged. While a slice is absent the destination renders not yet live and names the owner rather than inventing a fetch.

Acceptance

The SPEC_V2 §12 T18 gate requires that every destination route exists with its Playwright spec; that a signed-in tenant drives the portfolio → programme → project → work-package, organisation → release → binding, procedures intake → publish, tools call → ledger, improve → kata → adoption, operations incident → postmortem and ADM phase-rail paths from the app; that every destination spec asserts empty, error, happy and one refusal; that the V2 coverage record reports exists only from a real route and its spec; and that no production screen renders a fixture. acceptance/programme/T18.toml carries the fifteen gate checks, including project, baseline, contract, review, WSJF, demo credits, coverage, artefact-standard and rework resolution.

Capabilities

The tenant operator who runs the portfolio, programme, plan, organisation, procedures, authoring, tools, improve, operations and architecture surfaces owns the outcome, with the PM, kanban-coach, kata, development and operations jobs those destinations serve. The UI is their surface, not a new job: it exposes the action families that T0–T17 own, and the seven nav groups are trimmed to destinations that exist and gated by has_action. The delivery view gives the sponsoring group and the SRO one L1–L4 line from portfolio to work package, with spend read from the ledger rather than fabricated.

Plan

The project is held to docs/plans/T18-real-v2-ui.md, SPEC_V2 §10.5 (the real-UI route table) and §12 T18 (the gate), with ADR 0013 recording that the real UI is the app and not the design pack. The five sequenced units are issues #562 (shell, route registry, portfolio, programme and the delivery view), #563 (organisation, jobs, agents, decisions, project types, plan and validation), #564 (procedures, capabilities, authoring, execution and run history), #565 (tools, metering, operations and improve) and #566 (architecture, system architecture, knowledge, measure and the T12 acceptance). #565 and #566 remain open at this snapshot.
