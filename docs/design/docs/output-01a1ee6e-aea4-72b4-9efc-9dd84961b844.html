Design

The design is platform-first: V2 extends the one Rust application and one Postgres V1 runs, adding tables and actions only — same binary, namespace and port; no Redis, no hosted model, no new runtime. Every action is one ActionSpec served over HTTP, MCP and OpenAPI (§10.4, §10.6). The units are job, card, approval and run, reusing V1's board, document and event primitives (§2).

The conveyor-owned catalogue — industry, ordered departments, job — compiles into an immutable, content-hashed release carrying charter, bindings, prompt recipe, knowledge and memory pins, tool grants, decision options, limits and gates. A tenant-scoped binding pins one release and one executor; nothing is imported (§4.1–§4.4), and jobs are curated from the derivation chain rather than mass-generated (§4.3).

Two implementations of one Executor contract: a deterministic procedure, and an internal agent prompted from knowledge, episodic memory, the PDDL request and the curated tool list (§4.5, §7.7).

The portfolio is a computed read model; the programme carries shared configuration and the dependency graph; project types are templates over WBS nodes and gates; one register serves six kinds (§5.1–§5.5). Meta-jobs are ordinary catalogue entries with charters, closed decision sets and data-driven authority (§6). Options, policies and refinements are rows; laya decides, and the LLM drafts only through a gated action (§7.1–§7.5).

Five tool definitions have one owner each — tool, toolkit, binding, grant, call; the broker is the only call path, with effect classes and a ledger (§11.1–§11.4). There is no second tool control plane (§11.7); bytes go directly to tenant-prefixed shared storage (§11.10).

Constraining decisions: D28–D63 (§15.1) — D33 ownership, D38 pinned bindings, D41/D44 one tool path, D46/D61 the executor seam, D49–D51 configuration, D53 PKO separation, D57 storage, D62–D63 the MSP and TOGAF implementations; D61–D63 remain proposed.
