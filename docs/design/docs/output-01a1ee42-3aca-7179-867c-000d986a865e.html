Context and boundary

T17 turns a tenant's chat brief and documents into reviewed, published tenant assets. Downstream of T0, T2, T3, T13 and T16, it owns intake, drafts, the publication orchestrator, a template store and an inert tool request. It does not own published assets' tables (§10.1), SOP/RDF/BPMN conversion and PKO (T16, #85, OPEN status:blocked, absent), the tool model (T13, #76, OPEN status:claimed, absent), or policy evaluation (T2). Publication calls the owning aggregate's action in one transaction; a missing action refuses, never degrades.

Decisions

D1 — new draft aggregate. Alternative: extend governed_asset. Consequence: a typed target per proposal for one table; the alternative overloads a lifecycle whose kind CHECK (migrations/0044_plan_spine.sql:governed_asset) already carries fifteen kinds, and it cannot carry a typed organisation, procedure or policy target.

D2 — review reuses approval. Alternative: authoring_review. Consequence: one record per fact and the existing self_approval machinery; depth becomes approval_policy rows (P11).

D3 — publication delegates. Alternative: write target tables. Consequence: release-hash, ETag and RLS invariants cannot be bypassed; cost is a dependency on T16/T13.

D4 — authoring is an ordinary job. Alternative: a hard-coded wizard. Consequence: a job_binding on an internal_agent release (P6), measured like any job; intake cannot transition a card (P2).

D5 — tool requests are inert. Alternative: auto-create a T13 draft toolkit. Consequence: no authoring path can grant a tool; a request goes to T13's gate, costing a second review.

D6 — dependency ordering enforced. Alternative: sorted advice. Consequence: depends_on is refused at publish (asset_not_published); a batch publishes bottom-up.

D7 — first wave. The gate's four kinds first; templates and tool requests follow in the same slice (P10).

Acceptance

Gate, verbatim: "a tenant supplies a short brief plus documents, and a reviewed catalogue of departments, jobs, procedures and policies is published; no asset can publish itself or widen a tool grant".

Scenario 1 — brief + documents produce a reviewed catalogue. Given a tenant supplies a brief and two documents; when intake drafts the four kinds and each is approved; then authoring.publish creates departments, jobs with published job_release rows carrying a release_hash, and policies through approval_policies.set with the tenant's self_approval unchanged; procedures are asserted only once T16 exists (blocked on #85). job_catalogue.list and approval_policies.list return them. Verify: crates/actions/tests/authoring.rs::a_chat_brief_drafts_the_org_and_job_catalogue and ::a_reviewed_catalogue_publishes_with_its_decisions (to create, #87).

Scenario 2 — no asset publishes itself. Given the principal that authored a draft; when it publishes it or decides its own approval; then both are refused and no target row exists. Verify: crates/actions/tests/asset_review.rs::the_authoring_job_cannot_publish_its_own_asset (to create, #87); default self_approval='forbidden' (migrations/0050_approval_policies.sql:approval_policy).

Scenario 3 — no asset widens a tool grant. Given a tool_request draft; when it publishes; then exactly one tool_request row exists, no tool/toolkit/tool_binding/tool_call row is written, and no approval_policy row naming a tools.* action changes. Verify: crates/actions/tests/asset_review.rs::an_asset_never_widens_a_tool_grant (to create, #87); precondition git grep 'CREATE TABLE tool_binding' origin/main -- migrations returns nothing.

Solution concept (diagram; viewpoint: delivery lead; question "how does a document become a published asset without authority?"). Intake records provenance and orders a draft set; each enters the approval gate; an approved draft publishes by calling the owning action; T16 conversion is invoked, not rebuilt; tool requests stop at an inert row. Links: derivation → R1–R7; realisation → D1–D7.

Migration and rollout

One migration (the next free number at build time), forward-only: four tables (authoring_intake, authoring_draft, asset_template, tool_request), RLS forced with same-file policies (mirroring migrations/0050_approval_policies.sql), named constraints, version columns, unique (tenant_id, content_hash) on drafts. No backfill; seed rows are inputs. Order: migration → ActionSpecs → job release and binding → first intake. While T16 or T13 is absent, intake refuses 409 authoring_not_ready, so tables ship dark. Rejected drafts are retained; retirement never cascades. Acceptance is the three scenarios, then one tenant intake with accepted/rejected and revision counts.
