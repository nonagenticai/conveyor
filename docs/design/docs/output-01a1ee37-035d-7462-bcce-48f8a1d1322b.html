T10 — Architecture design

Project: T10 — SAFe cadence and MSP tranches · Track: v2 · Tranche: 4 · Plan: docs/SPEC_V2.md §12 Unit: #82 (this design is dependency-shaping work; blocked-by T1, T3 and P0) Measured at: main@61edfcf8, 2026-11-18 · Project row: active, meta.depends_on = ["T1", "T3", "P0"]

Context and boundary

T10 is the V2 Work capability the blueprint calls "programme cadence": P0 adopts the plan, T1 supplies rows, T3 the PM job, T10 the execution. It runs under P0's live architecture contract, and its artefacts satisfy AS-1: type, phase/plateau, common metadata and one typed link.

T10 owns the cadence execution actions (PI materialisation, demo gate, retro composition, refinement read), the benefits authoring and realization read (strategy, realization plan, realized versus planned), and one nullable column that ties a backlog item to the cadence that planned it.

T10 must not duplicate: WSJF arithmetic (crates/domain/src/spine.rs:wsjf); tranche and review persistence or refusals (T1, migrations/0044_plan_spine.sql:programme_tranche); the lesson aggregate (T8); kata (T5); metrics and never-refused flagging (T11); TOGAF artefacts (T9); or the board, card, run, approval, document and governed_asset lifecycles. The blueprint's intermediate state is T0–T17; T10 is tranche 4 and may run parallel with T9.

Built events: programme_cadence.created|updated|deleted, programme_tranche.reviewed, benefit_profile.*, benefit_transition.*. New (to create), in the action's transaction: programme_cadence.planned, .demoed, .closed, .refined.

Materialisation. cadences.plan (to create) reads open wbs_node rows ordered by (business_value + time_criticality + risk_reduction) / job_size descending, resolves WIP from the target project's list wip_limit (pattern: crates/actions/src/board/pull.rs), creates one card per selected item within the remaining cap, sets planned_cadence_id, and raises one plan approval for a person. The score is computed, never written; a second call refuses planned items, so idempotency is by planned_cadence_id.

Demo. A deliverable is demonstrable only when its card is in a done list and wbs_node.evidence is a non-empty array. cadences.demo (to create) validates every completed deliverable, then records one approval with gate='demo' and the evidence refs; a missing evidence array refuses the whole demo. "No demo, no credit" is an approval outcome, not a status written onto the card.

Retro and refinement. cadences.retro (to create) composes T8's lessons.propose and T5's kata action, records their ids and closes the cadence. cadences.refine (to create) returns stale backlog items (derived from updated_at against the period) and emits programme_cadence.refined; it stores no stale flag.

Decisions

  • D-T10-1 — the backlog is wbs_node. Alternative: a new backlog_item table. Consequence: one WSJF store and one backlog; SPEC_V2 §12 T10, carrying D-T1-4.
  • D-T10-2 — planning records wbs_node.planned_cadence_id. Alternative: a cadence_card join table or an id array in meta. Consequence: one nullable column and a partial index; an item cannot silently move cadence; D-T1-11 names cadence materialisation as T10's boundary.
  • D-T10-3 — WIP is list.wip_limit. Alternative: programme.shared_config.wip. Consequence: the board remains the only cap; a multi-project programme must resolve WIP per target project (open question 1). SPEC_V2 §8.2.
  • D-T10-4 — a demo is an approval row. Alternative: a cadence_demo table. Consequence: one gate primitive, evidence in meta.evidence[], no new aggregate. SPEC_V2 §5.4, §8.2.
  • D-T10-5 — the retro owns no lesson or kata row. Alternative: T10 builds the lesson table. Consequence: acceptance-blocked-by T8; the brief's dependency list is incomplete; P10 forbids the duplicate.
  • D-T10-6 — stale is computed, never stored. Alternative: wbs_node.meta.stale. Consequence: refinement returns the list and emits an event; no second truth. P6.
  • D-T10-7 — strategy and realization plan are governed_asset rows. Alternative: new tables. Consequence: the existing lifecycle and publication gate apply; T10 adds authoring actions, not a store. migrations/0044_plan_spine.sql:governed_asset_kind_check.
  • D-T10-8 — no new scheduler. Alternative: an in-process cron. Consequence: cadence work is an ordinary run on the existing queue, staffed by seed/organisation.json:programme_manager (seeded draft). SPEC_V2 §10.6.
  • D-T10-9 — realized is reachable only through a transition. Alternative: accept benefits.update(status). Consequence: T10 adds the guard at the update path or routes realized through benefits.report; without it §8.3 has a bypass.

Acceptance

Migration and rollout

0052_cadence_execution.sql (to create, forward-only) adds nullable wbs_node.planned_cadence_id uuid with a foreign key to programme_cadence(id) and a partial index, and a UNIQUE (tenant_id, programme_id, kind, period) index on programme_cadence for the one-row-per-period invariant. No state CHECK: state is free text today (migrations/0044_plan_spine.sql:programme_cadence) and cadences.update writes any string, so the state machine is validated in the action, not by a constraint — open question 6 is answered this way. The unique index is checked against live rows before it is applied; if a duplicate exists, the migration refuses and the cleanup is a separate, owner-approved step. The actions are additive with portfolio:read and portfolio:write scopes. No new port, binary or database (SPEC_V2 §10.6).

Sequence: migration, domain rules, actions, tests, docs/design/data/actions.json, then the read models the Portfolio and Programme screens consume (§10.5). Apart from the unique index, rollout changes no existing behaviour, so no flag; rollback disables the actions and ignores the nullable column, with no rewrite. Events are written in the action's transaction. P0's first-tranche authorisation remains the owner's act; T10 does not publish tranche-review.
