SPEC V2 — conveyor: the organisational operating model

Repo: nonagenticai/conveyor · Host: conveyor.nonagentic.ai · Port: 8930 (existing; no new port) Date: 2026-11-11 · Status: draft for review · no V2 code written Relationship to SPEC.md: V1 (2026-11-07) remains the build record and stays binding for the slices it defines. V2 extends it — it adds the organisation that works the conveyor and the work hierarchy that organisation needs. V1 decisions D1–D27 stand unless a V2 decision explicitly extends or amends them (Appendix B). No V1 slice is re-opened by this document.

In one paragraph. V2 turns the conveyor from a work system into an organisation. Jobs are configured positions (industry → department → job) that receive cards, decide with rules and laya, generate with LLMs behind gates, and prove their work with runs and instruments. PM, kanban coach, kata, development and operations are jobs, not code. TOGAF/SAFe/PMP artefacts are rows, gates and evidence. Every cluster service a job may call is a versioned, bound, audited tool. The conveyor develops and operates itself under the same gates it imposes on any work. The conveyor owns its whole model and is as self-contained as possible: it reuses ideas — and where useful, code — from the agent, w2v, fr and care-bus applications, but holds no runtime dependency on any of them and treats the agent platform only as a user-interaction front end over MCP.

1. Context

1.1 What V1 built

V1 built one Rust application to replace fr, RM, Planka and procedure_management — the app is live; the old applications remain until the S14 cutover. It built the machine that can carry work: projects, boards, lists, cards, runs, approvals, procedures, capabilities, capability agents, knowledge and memory bindings, an inference ledger, a native SWE-bench harness, evals, evals' hillclimb and the compiled-prompt pipeline.

The V1 build record's last whole-tree checkpoint (2026-11-09, docs/plans/00-INDEX.md) measured 83 tables and 243 actions; S19–S21 lanes moved the registry past 290 served-spec ops that same day, so those numbers are a floor, not a live figure. The app is live at conveyor.nonagentic.ai on main 85487a04, 3 pods, /health and /health/ready 200 on :8930 (deploy record 2026-11-10).

V1 answers how work is carried. It does not answer who the organisation is: there is no industry, no department, no job, no programme cadence, no PM/coach/kata role, no self-development project and no operations perspective. A project is created by a person; a card is typed by a person; the improvement loop exists but nothing staffs it.

1.2 The three convergences

V2 exists because three independently built things have arrived at the same shape:

  1. agent is a user of the conveyor over MCP. D19/D21 made the conveyor's own /mcp the interface: the agent creates a project, starts one durable task (projects.execute), answers its approvals as task input requests and receives the terminal result (the agent-side plan of 2026-11-08). It is a front end — a conversation surface like Telegram — with its own autonomy configuration; it is not a catalogue, an executor or a system of record for conveyor work. The live end-to-end proof is the S06b/S14 gate, not a claim about today's deployment.
  2. The organisational hierarchy is proven. The agent platform's KH (D106–D115; its §4 rollout record of 2026-10-23 reports agent#72 e47c92e deployed, migrations 0132–0139, seed v3 applied) demonstrates the model the conveyor now implements itself: every job one industry, one or more ordered departments and an optional region; a job compiles base → industry → department archetype → job (with region after its parent) into an immutable release, with knowledge kinds, packs, instructions, settings, toolsets and System-1 gates. The conveyor reuses the ideas, not the implementation — it is self-contained (D33).
  3. The conveyor has the work and the proof. Capability → procedure → step → action|gate is the procedural knowledge; run/approval/action_invocation/event is the procedural memory; capability_agent is the executor configuration; inference_call is the ledger; benchmark, evals and prompt audit are the instruments.

The missing piece is the organisation: the conveyor already carries work and proof, and V2 gives it its own catalogue, immutable release, binding and inference configuration. The join is internal — no manifest is imported from another system.

care-bus-agents remains the standalone customer-interaction demo; it is not part of the organisational runtime. Customer care is not conveyor work (D48): the conveyor is built for project, continuous-line and line-management work, starting with a real IT department's development and operations, and later any capability in any industry.

1.3 What the field does, and what it does not

As of the sources fetched 2026-11-11:

  • CrewAI is a strong ergonomic layer for a crew: agents with roles/goals, tasks with expected outputs, and a Process that is either sequential or hierarchical (a manager agent delegates and validates). Memory is one unified Memory class over embeddings and a vector index. Typed control lives in Flows, not in the Crew abstraction; no runtime human-approval gate is documented on the Crews page. It is excellent at starting a small collaborative process and says nothing about portfolios, phase gates, evidence, budgets or an org chart.
  • ChatDev has moved to ChatDev 2.0 (DevAll, released 2026-01-07), a zero-code multi-agent platform; its 1.x "virtual software company" (CEO/CTO/programmer/reviewer/designer, design→coding→testing→documenting) remains the mental model. It demonstrates role specialisation and visible handoffs; it does not attempt an operating model.
  • n8n is the best deterministic workflow engine we have used: a node graph with per-execution state and error branches. Its weakness is the one we measured in our own estate — 348 workflows, 280 of them the generated card-type × list matrix, each carrying its own error exits. A flow engine gives you execution, not a process model.

The gap is consistent: the field builds agent conversations; real organisations run on positions, work products, gates, baselines and evidence. That is the gap V2 fills, with the rigour the owner asked for — TOGAF for architecture, SAFe for project/programme management, PMP artefacts — implemented as executable rows and gates, not as documents.

2. The thesis

An organisation is a set of positions making decisions and doing work under governance.

Four units, and only four:

Unit What it is Where it lives
Job a position: a capability + a procedure + an inference configuration + an authority conveyor (catalogue, release, binding)
Card a work package: one unit of assigned work with an owner, a state and evidence conveyor
Approval a decision: the one human-escalation primitive (a question is an approval) conveyor
Run one attempt at a card through an executor, recorded conveyor

Everything else is a view or an instrument. Departments, programmes and portfolios organise jobs and cards; knowledge, memory and tools configure a job; evals, benchmarks and the inference ledger measure it; TOGAF/SAFe/PMP supply the process grammar. The differentiator is not multi-agent conversation — it is that every handoff, decision and claim is a durable row with an owner, a state and a proof.

First principles the spec is built on:

  1. An organisation is a decision system, not a chat system. Agents do not need to talk to each other; they need to exchange typed work products through a governed process.
  2. Most decisions are not language problems. They are choices among configured options. A small calibrated model (laya) is cheaper, faster and more auditable than an LLM for that.
  3. Generation is the LLM's only job. Text, code, plans and reports are generated; they become drafts; applying a draft is an action behind a gate.
  4. Trust comes from instruments, not from confidence. A change is adopted because a held-out eval or benchmark moved, not because an agent says it improved.
  5. The system must be able to build and run itself under the same gates it imposes on any work — otherwise the process is theatre.

4. The organisational model

4.1 The hierarchy

V2 adopts the KH hierarchy — proven by the agent platform (D106–D115) — as the conveyor's own organisation spine. The concepts are reused; the implementation is the conveyor's (D33).

industry 1 ── * department (ordered, primary first)
                    └── * job
region?  ── optional sub-layer of any layer (folds immediately after its parent; no region content seeded yet)
  • A job sits in exactly one industry and one or more departments of that industry, ordered, primary first (D106/D115). A department from another industry is 422 department_industry_mismatch.
  • Knowledge is layered base → industry → department archetype → each department in declared order (with its region sub-layer) → job. Kinds are declared at every layer; a kind is required or optional; required can only be tightened downward. Sibling departments that set one key to different values are a compile error (department_conflict), resolved only by a job-layer row.
  • The job release is immutable and pinned. A run records job_key + release_hash; a release change is a new binding and a gate, never a silent update. There is no live design → 409 job_not_live; no resolvable required knowledge → 409 release_not_ready naming the kind and department.

The catalogue is the conveyor's own data (industry, department, job_catalogue, job_release); the release compiles from the same layers and is stored as an immutable artefact with a content hash. No manifest is imported from another system, and no other system is asked to validate a release.

4.2 Job anatomy — the configured position

A job is configuration, not a loop. Its release carries:

One author: the conveyor. A job is one record with one owner (D33). Every field below lives in the conveyor's catalogue or its immutable release; nothing is authored in another system for a conveyor job.

Field Meaning Author
job_key stable position key, e.g. software.delivery.backend_engineer conveyor (job_catalogue)
placement industry, ordered departments, optional region conveyor (job_catalogue)
charter purpose, outcomes, non-goals, escalation path conveyor (release layer instruction)
capability binding one or more capabilities conveyor (job_binding)
procedure_ref published procedure version(s), each pinning its PKO release conveyor (procedure)
executor procedure | internal_agent (V1 D22, amended by D46) conveyor (job_binding)
model_ref, params inference-router model and parameters conveyor (release)
prompt_recipe compiled-prompt recipe (prompt_ref@version) conveyor (release)
knowledge pins layer kind pins + capability pack versions conveyor (release)
memory policy recall scope, hot/cold, write rules conveyor (release)

Rule: a job may lower a limit at run time, never raise it. The resolved {job_key, release_hash, procedure_ref, model_ref, allowed_actions} travels in the run's input hash, so the record pins what actually ran.

4.3 How jobs are derived

Jobs are authored, not invented at runtime. The derivation method is the use-case chain the agent platform proved (D106–D115); the conveyor applies it to its own catalogue:

industry / department / job
  → business model (axis selection)
  → customer or internal journey (themes → stages)
  → stage = capability column
  → activity (customer | company)
  → activity-information objects (objects × DO | REQUEST | OBSERVE)
  → use case → context space + procedure
  → job draft

A draft catalogue may be generated from the chain; a person curates it into published jobs. V2 explicitly does not auto-generate a thousand live jobs from an ontology — that is how the v4 generator produced four wf_* types that "serve nothing". The catalogue grows by evidence: a missing job is opened as a kata or a PM request, authored, bound, measured, then published.

4.4 The job binding — position, release, executor

job_binding
  id, tenant_id,
  job_key, release_hash,
  capability_id?, procedure_id?, executor_kind,
  status ∈ draft|active|retired, version,
  meta { department_scope[], authority, limits_override? }
  • A card names a binding (card.job_binding_id), not a free-text role.
  • A run records the binding and the resolved release it actually used.
  • A binding is tenant-scoped; the same job_key can be bound to different capabilities in two tenants.
  • Retiring a binding does not rewrite history: existing runs keep their pinned reference.
  • A binding pins one immutable release. A new release is a new binding and a gate (D38); it never rewrites a live binding. A run request naming a retired binding, or naming a release that is not the binding's pin, is refused 409 job_binding_stale before any model call; the refusal names the binding's release hash and the requested one. The check is internal — no catalogue call, no external caller-declared hash.
  • The binding stores the release's content hash and its frozen configuration snapshot (release_hash + release_snapshot JSONB). It is a pinned artefact, like a lockfile, not a live mirror; a new release is a new binding and the old snapshot is never refreshed in place.
  • Every binding also pins executor_kind and either a conveyor procedure_id (for a procedure executor) or the release's capability_agent_id (for an internal-agent executor). A binding with neither is refused at creation.

4.5 Executor kinds

V1 D22 is amended by D46 (and by D61, once accepted): a run has one executor, and there are two live kinds behind one internal Executor contract; the kind is to be an extensible enum.

Executor When Config source
procedure a deterministic sequence of steps; no model of its own conveyor procedure
internal_agent a step needs generation over a compiled prompt conveyor capability_agent + the release

A procedure is a sequence of prompt parts. Each step is an action — a PDDL action, a tool call, or a gate — and the sequence is the plan. Deterministic steps execute directly; a step whose action needs generation hands to the internal agent.

The internal agent receives a dynamically engineered prompt assembled at run time from four sources:

Source What it contributes
Knowledge domain knowledge (pinned layer kinds and packs) and procedural knowledge (the capability/procedure/PKO)
Memory episodic memory: the run's prior steps, the card's hot memory and the consolidated digest
Request the action the agent must perform — the procedure step written in PDDL
Tools the curated list of tools bound to this job, with their closed schemas

The generation contract (§7.4) still applies: the output is a draft; applying it is a gated action.

The executor seam (D61). Both kinds are to implement one internal Executor contract (T0 builds it); executor_kind is to be an extensible enum, not a branch through the run path. Adding a kind is a new implementation plus one enum value, never an edit to the run loop. There is no external executor today, and an external runtime — the agent platform or any harness — is an explicit non-goal until all four hold: a generic work-packet ingress that returns per-step evidence the conveyor can verify (not outcome-level); governance at the boundary (a produce-only runtime, the conveyor ships); separate owners and roadmaps; and it beats the internal agent on the conveyor's own benchmark. The agent platform is a front end, not a runtime for conveyor jobs; if it is down, no conveyor run pauses.

4.6 Scope and the first departments

The conveyor is for project work, continuous-line work and line-management work. It is a general engine for intelligent work execution with configurable human-in-the-loop: a tenant configures how much autonomy each job and gate has, and may offload human interaction to the agent platform over MCP. It does not do customer care (D48); customer care remains the agent platform's own product.

The first tenant is nonagentic; the first industry is software; the first department set is a real IT department — development and operations — because the conveyor must develop and operate itself before it can be trusted with any other industry's work. Two further tenants are in scope from the same model: AHTAPol (industry health-technology-assessment) and w2v (industry media), each with its own departments and jobs (D60) — the proof that the model is not software-specific. Nothing below is hard-coded — each row is a job in the catalogue.

Department Jobs (initial) First work
delivery product owner, architect, tech lead, backend/frontend/data/platform engineer, reviewer, release manager, technical writer deliver conveyor features and dependency-repo changes
verification QA engineer, security reviewer, performance engineer independent verification, red-team, eval authoring
operations incident commander, SRE/on-call, platform operator k8s/git incidents, runbooks, postmortems
project office PM, programme manager, portfolio analyst charters, WBS, baselines, cadence, change control
improvement kanban coach, kata facilitator, measurement engineer interruptions, systemic fixes, instruments

The first real job to instantiate is conveyor maintenance — the system's own upkeep — followed by feature delivery and then operations. Self-development is not a later phase; it is the first proof (§9).

Scale is a catalogue property, not a process property. A department's jobs are grouped into families (product, architecture, engineering, verification, release, operations, knowledge); a family can hold dozens of specific jobs (backend-rust, frontend-leptos, postgres, security-review, release-manager, …). The catalogue is searchable by code/capability/department and paginated; a tenant activates the subset it needs. Thousands of jobs are thousands of rows and bindings, not thousands of processes (D39).

5. The work model

5.1 The hierarchy

V1 already ships programme and project.programme_id. V2 completes the hierarchy:

tenant
  ├── portfolio   — computed: every project and programme in flight for the tenant (no row)
  └── programme   — a set of projects with shared configuration and project-level dependencies
        └── project — may also stand alone, outside any programme
              └── WBS / deliverable → work package (card) → run → step / attempt

Owner definition (2026-11-11, D49). A portfolio is all projects and programmes in flight for a tenant; a programme is a set of projects with shared configuration and project-level dependencies. The portfolio is a read model over programme and project (P10 — no row); the programme is a real aggregate carrying shared_config and the project dependency graph.

Level Meaning State
Portfolio every project and programme in flight for the tenant — a computed view, never a row none (read model)
Programme a set of projects with shared config and project-level dependencies; carries the budget and cadence active | paused | closed
Project a temporary endeavour with a charter and a baseline draft | active | paused | closed | archived
WBS node phase, deliverable, work package or milestone; a tree under the project open → accepted / cancelled
Work package the card: one assignment, one owner, one list list + archived_at (V1: the list is the state)
Run one execution attempt queued → running → waiting_approval → running → succeeded | failed | cancelled
  • Portfolio membership is derived: a project or programme is in flight when its status is in the tenant's configured in-flight set (default active and paused); closed and archived work is history and is not listed.
  • Programme shared config is inherited by its projects: knowledge pins and packs, default job families, approval-policy defaults, budget envelope and cadence. A project overrides a key only when the programme does not declare it locked; the lock set is tenant policy.
  • Project-level dependencies are edges, not prose: project_dependency(from_project, to_project, kind ∈ blocks | needs | supersedes | informs, status), inside or across programmes. The PM reads them when sequencing the WBS; a cycle is refused at creation.

5.2 Project types

project.project_type_code selects the phase template, the gate set and the default job family:

Type Template Gates
delivery charter → plan → build → verify → release → close (PMP) design (conditional), merge, deploy, close
architecture TOGAF ADM phases A–H (§8.1) per-phase contract gate
improvement (kata) six Gets (§6.3) hypothesis, adoption

The project type is a template, not code: its phases are WBS node kinds, its gates are approval rows with the gate name and evidence refs, and its artefacts are governed_asset rows (V1's one lifecycle for requirements, principles and ADRs, extended to charter/contract/closure/postmortem).

5.3 Plan, state and execution are different things

Three separations are load-bearing and are the V1 fixes carried forward:

  1. Project lifecycle ≠ card state ≠ run state. A card can move without answering its approval; a completed run does not close a project.
  2. Baseline ≠ forecast. A baseline is a frozen, approved snapshot; a forecast is computed from current rows. A change to scope/schedule/cost is a change request (project_register_item.kind='change') with an impact analysis and a person's decision; existing runs keep their pins.
  3. Plan ≠ evidence. A WBS node is accepted when its acceptance criteria are met by an artefact/run, not when its checkbox is ticked.

5.4 Gates, evidence and dual control

  • One primitive: approval. A gate is an approval row with gate (phase/DoD name), kind, required_decisions, meta.evidence[] (run ids, artefact ids, eval ids) and an optional expires_at (default: never expires).
  • Dual control is required_decisions ≥ 2 and distinct approvers; the executor/assignee/requester cannot be an approver for the gate that judges their work.
  • A gate with no evidence is refused (422 gate_evidence_missing) unless the gate explicitly allows an override; the override is recorded on the approval and counted in the override metric.
  • Definition of Done lives on card_type.definition and is checked by the domain layer before a card can enter a done list; an approval can override with a reason, which the coach reads.
  • No gate that cannot fail. Every gate ships with a negative test (a run that must be refused). A gate that has never refused anything in a full programme cycle is flagged by the governance audit — that is a broken gate, not a healthy one.
  • Approvals are tenant-configurable and default to human. Each gate names an approval_policy row: required decisions (1 by default; ≥2 for dual control), the approver kind (human by default; a tenant may authorise a job or agent only for a gate it explicitly declares non-governance), and an expiry. The policy is itself a gated change; a gate whose policy is automatic is flagged in the governance audit. Human-in-the-loop may be offloaded to the agent platform over MCP, which presents the approval with its own autonomy configuration; the conveyor still records the decision and decided_by_kind/via.

5.5 Registers and change control

One generic register replaces five PM tables (the V1 lesson: RM's pm_* tables measured zero usage and were dropped):

project_register_item
  id, tenant_id, project_id, kind ∈ risk|issue|assumption|dependency|benefit|change,
  code, title, body, owner_job_id, status, severity, probability, impact,
  links jsonb {cards[], requirements[], decisions[]}, meta, version
  • A change request references the baseline it changes and requires a scope/schedule/cost/risk impact block; the approval records the person's rationale.
  • A risk can open a mitigation card; a dependency can link two projects or an external system; a benefit is measured at closure (planned vs realised).

5.6 Procedure authoring and SOP ingestion

A procedure is the executable form of a standard operating procedure: an ordered sequence of steps, each an action (PDDL), a tool call or a gate. Procedure design and management is a first-class conveyor feature (D47):

  • SOP intake. A tenant supplies SOPs — PDF, web URL or another document — singly or as a batch. A customer document is untrusted input: it enters as a governed_asset(kind='sop_source') with provenance, never as instructions to the system.
  • Conversion. The intake job harvests and curates the domain knowledge the SOP implies, then converts the SOP into procedural knowledge (the Procedural Knowledge Ontology, PKO) and a procedure draft whose steps are written in PDDL. The conversion job uses the web/research tools, and lean4_prover where a claim needs formal checking.
  • Two spaces, never mixed (D53). The action space is the procedure step written in PDDL — actions with preconditions and effects over typed facts. The procedural knowledge space is the PKO — the ontology of tasks, steps, roles, artefacts and constraints. A step references PKO terms; a PKO entity never contains an executable step.
  • PKO storage and ingestion. The PKO is relational, conveyor-owned and tenant-editable: an immutable pko_release pins pko_entity (name, label, kind, attributes, synonyms) and pko_relation (subject, predicate, object, cardinality) rows, layered base → industry → department → job. RDF/OWL/Turtle documents are ingest material — a converter turns them into draft rows behind the review gate; the conveyor runs no RDF store and no reasoner. The old procedure_management OWL/Turtle files import this way once (owner, 2026-11-11).
  • Process documents. BPMN 2.0 XML, Visio and draw.io exports ingest on the same path: the diagram becomes a procedure draft (activities → steps, gateways → gates) plus PKO rows. The diagram is a source document; the procedure is the executable artefact, and the same review gate applies.
  • Design reuse. The same pipeline designs capabilities, agents and jobs: an SOP yields a capability, a procedure, a job draft and its knowledge pins; a person reviews and publishes.
  • Knowledge pairing. The domain knowledge harvested for an SOP is stored as a pinned knowledge pack in strata_rag and paired with the procedural knowledge; the procedure's release names both. The conveyor uses strata_ingest and strata_rag at least to the extent the agent platform already does — document ingestion, pinned-leaf retrieval, pack storage and consolidation — and never hosts embeddings.
  • Gates. Every SOP-derived artefact is a draft behind a review gate (default: human, tenant-configurable). The ontology and the procedure are versioned and measured like any other procedure change (P5); a batch never publishes itself, and no SOP can grant a tool or widen an effect ceiling.

5.7 Tenant asset authoring — from chat and documents (draft)

Owner concept, 2026-11-11 (D55); the first-wave asset matrix is an open question (T17). The same intake pipeline that converts an SOP is the general authoring path: a tenant supplies chat input and documents, and the conveyor drafts every tenant-scoped asset it needs.

Input Produces (draft)
Chat (web or the agent front end over MCP) organisation draft (industry, department, job catalogue), project templates, gate/approval policies, tool requests
SOP (PDF, URL, document) capability, procedure (PDDL), PKO rows, knowledge pack, job draft
BPMN / Visio / draw.io procedure (activities → steps, gateways → gates), PKO rows
RDF / OWL / Turtle PKO entities and relations
Existing policy/procedure exports procedure or policy drafts

Rules:

  • Every output is a draft behind a review gate (tenant-configurable, default human); publication is a release and a gate. A chat message or a document can never grant a tool, widen an effect ceiling, approve its own artefact or change an approval policy.
  • Asset order is dependency-ordered: industry → department → job/capability → procedure/PKO → knowledge pack → policies/templates → tools. The authoring job refuses a draft whose referenced asset is unpublished.
  • The authoring job family is ordinary jobs on the two executors (§4.5); the pipeline is a procedure, not a hard-coded wizard.
  • Instruments: drafts accepted vs rejected, revisions per artefact, time from intake to first published job. An authored catalogue is measured by use — an asset no procedure uses is retired (P10).
  • The chat surface does not decide. Chat input is a request; rules/laya route it; the LLM drafts; a person approves. Tenant asset creation is subject to the same decision ladder as any work (§7).

The detailed asset matrix, review depth per asset type and the first wave ship with T17; nothing above widens a tool grant or a gate policy without its own approval.

6. The roles — meta-jobs as ordinary jobs

Each role is a job_key with a charter, a procedure, an authority matrix and metrics. They run on the same card, run, approval and event primitives as any other job, on the conveyor's two executor kinds — a procedure or the internal agent (§4.5).

6.1 PM — project management

6.6 Collaboration protocol — handoffs are cards, not messages

  1. A job that needs work from another job creates and assigns a card. It does not message an agent. The card names the job binding, the inputs (artefact ids), the acceptance criteria and the due date.
  2. A handoff is an action (cards.assign / cards.move + comment/artifact.attach) producing an event. The receiving job's queue is its board/list; the PM's plan is the WBS.
  3. A question is an approval (V1 D18/D19). If a job needs a human decision, it opens an approval; if it needs a decision from another job, it opens a card assigned to that job, optionally with a gate.
  4. Memory is written at handoff. The sender records what the receiver must know (memory.remember), so a job does not depend on a conversation transcript that may be compacted.
  5. Every card has one live run (uq_run_live); retries create attempts on the same run where the state machine permits, otherwise a new run with the previous as a link.
  6. Escalation is bounded: a card may escalate to its parent WBS owner, then to the PM, then to the programme; the coach can escalate to a human at any point. No unbounded agent-to-agent loops.

7. The decision ladder — laya first, LLM last

7.1 The four rungs

Rung Mechanism Used for Record
L0 Rule deterministic Rust over typed facts state transitions, WIP limits, WSJF arithmetic, thresholds, policy checks, acceptance the row + action_invocation
L1 System-1 (laya) calibrated choice/score/noul over a finite option set triage, routing, job/capability selection, remedy selection, severity, priority band, gate pre-check decision row with the answer, probabilities where the question type provides them, and confidence
L2 Generation (LLM) text/code/plan/report synthesis drafts, answers, patches, narratives, candidate procedures/prompts inference_call + a draft artefact
L3 Human approval every gate; every override; every irreversible action approval + approval_decision

The hard rule: L2 has no path to a state transition. A generated output is stored as a draft artefact (governed_asset, document, or a code patch); applying it is an action, and the action's gate is L1/L3. The Rust type system enforces this: the generation result type is not accepted by any transition function.

7.2 The laya contract

POST /v1/systemone {model, state, questions} — state is the task text and questions is keyed by qid; each question is {type: noul|choice|score, instructions, criteria} and the response carries answers.<qid>. noul is a scalar answer, choice picks one of 2–255 labelled options, score is a 2–10 ordered scale; probabilities are carried for the types that provide them. The estate's laya is live on pgx behind a Jev-compatible bridge (:9210), ~17–21 ms per request (measured 2026-10-10).

V2 rules:

  • Options are rows (decision_option), authored and versioned, never free text from a prompt.
  • Questions are rows (decision_policy), with fire_when, min_confidence, fail_policy ∈ closed|open and action ∈ handover|block|annotate. Safety gates fail closed; routing/quality gates fail open to a human or a note.
  • Configuration is per tenant, per case (D51). A platform decision_policy defines the case; a tenant's decision_policy_refinement overrides the threshold value (or the whole rule), the fail action and, optionally, the laya inference config. Refinements are versioned; changing one is a gated policy change. The shape mirrors the agent platform's proven job_gates.threshold + job_gate_rule_refinement, reimplemented by the conveyor (D33).
  • Laya inference is tenant-scoped. laya_inference_config pins model_ref, params and timeout_ms per tenant (provider kind laya, default jev-latest), optionally overridden per case. Every decision row records the policy version, the refinement version and the laya config version it used.
  • Every decision is recorded with the option set version, the answer, probabilities where the type provides them, confidence, policy, latency and input hash. A decision is reproducible from the row.
  • Below threshold is an outcome, not an error: escalate (approval) or refuse per policy. Unavailable is gate_unavailable and follows the fail policy; it is never silently treated as a pass.
  • The conveyor owns every question and option set its jobs evaluate, including the internal agent's per-step gates. The agent platform owns only the questions its own conversation runtime evaluates — its product, not conveyor work.

7.4 The generation contract

A generation call is an inference_call (V1 D23) whose result is bound to a draft artefact. The artefact carries prompt_ref, prompt_version, prompt_sha256, model_ref, usage, cost (derived), and the trust order of its sources. It becomes applicable only through an action with a gate.

Allowed generation: draft answer, draft charter/WBS, draft procedure, draft prompt/patch, code patch, status narrative, postmortem narrative, lesson draft. Forbidden generation: tool selection, routing, state transitions, gate decisions, scoring a submission, approving.

7.5 Budgets and the ledger

9. Self-development and operations

9.1 Development projects — the conveyor builds itself

The organisation's first real job is to change its own substrate. A development project is an ordinary project with a development type and a stricter gate set:

  1. Charter names the repo, the lane, the scope and the acceptance evidence.
  2. Design note for structural changes (architecture contract, migration plan, rollback).
  3. Lane branch (lane/<slug>), one branch, at most one PR for the unit's life (house rule).
  4. Implement through coding jobs; the executor cannot merge.
  5. Verify: CI-equivalent locally first (fmt, clippy -D warnings, the full suite), then the pipeline; gitleaks; the relevant eval/benchmark if the change touches a measured surface.
  6. Review: an independent reviewer job; the reviewer cannot be the implementer.
  7. Merge gate: a human (or an earned auto-merge policy) approves; red CI is a refusal, never a retry-until-green.
  8. Deploy and verify live: rollout by image digest, /health, the slice's own acceptance check; a rollback plan exists before the deploy.
  9. Close: the closure record links the PR, the pipeline, the deploy evidence and the acceptance.

Dependency repos are in scope. A dependency change is a development project against that repo, with the same gates; the conveyor's own dependency bump is a linked project, not a side effect. A dependency is in scope only if its own change protocol permits an agent project; shared infrastructure (cluster control plane, ingress, DNS, registry) remains a human-run change, never a development project.

9.2 Operations — the platform perspective

The operations job family closes the loop on the substrate:

  • Incident is a card type with service, severity, detected_at, mitigated_at, resolved_at and a link to the run/evidence. Detection is an alert/webhook/schedule; a person can also open one.
  • Runbook is a published procedure whose steps are k8s/git actions with gates. The first runbooks: pod crash-loop, rollout stuck, dependency/DB down, certificate expiry, disk pressure, queue backlog, stale lease storm.
  • Read-first: diagnose with read actions (pods, deployments, events, logs, metrics, Flux status, git/CI). Write actions (restart, scale, rollback, flag flip) are ops:write, dry-run first, approved under the tenant's configured policy (default human dual control), and audited. The full write set ships in v1; autonomy is a tenant configuration, not a reduced feature.
  • Least privilege: the ops connector uses a namespace-scoped service account, never cluster-admin; the action registry declares every verb.
  • Postmortem is a governed_asset; a systemic finding becomes a kata candidate; a one-off becomes a runbook improvement. Blameless, evidence-linked, due within the policy window.
  • The andon cord (V1/fr) is an incident-class action: stop new runs for a tenant/programme, keep the record, alert the on-call; only a person releases it.

9.3 Guardrails — the system cannot grade its own homework

  • A development project cannot modify the gate set, approval policy, eval instrument or benchmark suite that judges it. Those are changed by a separate architecture/governance project with a different approver set.
  • A kata cannot approve its own adoption; a kata that changed the instrument is void for that measurement.
  • The merge gate and the deploy gate are separate decisions; a green CI is evidence, not an approval.
  • Auto-merge is earned, policy-scoped and revocable: the conditions (track record, revert count, path scope, reviewer requirement, expiry) are tenant configuration rows, not constants in code; one revert revokes it and opens a kata. The default is off; the database model, the UI and the code all read the policy, never a hard-coded number.
  • Rollback is mandatory for deployable changes; a deploy without a tested rollback is refused.
  • The benchmark harness and eval versions are frozen per measurement (V1 D24–D26); a change to an instrument creates a new version and voids its sign-offs.

9.4 The improvement loop, end to end

alert / failed run / eval delta / prompt finding / coach escalation
  → coach card (one interruption, closed remedy set)
  → if systemic: kata (six Gets, evidence, candidate)
  → development project (code) or procedure/prompt/knowledge change (config)
  → measurement (benchmark / eval / run outcome, held-out)
  → adoption gate (person; dual control)
  → production (new procedure/job/binding version)
  → monitoring + lesson

This is one loop, not four. The kata-executor's inputs are the prompt findings and eval deltas V1 already produces; the coach's escalations are cards; the PM's closure record is evidence; the operations postmortem feeds it back.

10.6 Deployment and scale

11. The tool estate

The claim. A job is only as capable as what it may call. V2 makes the tool estate a first-class, versioned, governed surface: every cluster service that offers a typed operation is a tool, tools are published in immutable toolkit versions, a job's access is a binding with an effect ceiling, and every call is a ledgered row. The conveyor owns the catalogue, the broker and the ledger. It does not route through nonagenticai_mcp_server (D44), and it does not reach a backend by an ad-hoc HTTP call from a procedure or an agent.

11.3 The broker — one call path

tools.call is the only way a conveyor-internal run reaches a job backend. The executor's own knowledge and memory rungs are not tools: the compiled prompt's knowledge.query and the per-card memory.consolidate (§7.6) stay where they are. A job that explicitly searches — rather than the executor grounding its prompt — uses the retrieval toolkit like any other tool. (V1's twelve external actions — S09 Part B added eight, including coding_jobs.create|get, retrieval.query, artifacts.list, billing.summary — are the seed of this registry and migrate in T13: the backend operations onto toolkit operations, artifacts.list onto the storage adapter (§11.10). They do not run beside it as a second path.)

  1. Resolve the binding and the pinned tool version; missing binding or version fails closed (409 tool_not_ready) before any network call.
  2. Check effect against the binding ceiling and the job authority (403 tool_effect_forbidden); check spend budget (429 tool_budget_exceeded).
  3. Validate the input against the closed schema (422 tool_input_invalid) — additionalProperties: false, enums, patterns, bounds.
  4. Resolve the credential from the sealed secret store by alias. The broker injects it; the prompt never carries it and the tool_call row never records it.
  5. Call the destination alias. The base URL is registered and reviewed at publication; no caller-supplied URL at call time (SSRF rule). BYO destinations are tenant-allowlisted at registration.
  6. Normalise and redact: the result envelope is {status, data, checks[], next[]} with ok | precondition_failed | check_failed | pending | backend_error; declared fields are redacted and the response size is capped.
  7. Record and emit: one tool_call row (input hash, status, latency, bytes, cost) and one tool.called event. The call is never a card transition.

Long operations are bounded. Every poll has a fixed budget; on timeout the tool returns pending with a resume_token, and the matching status tool continues from it. A timeout never fails silently.

Writes verify themselves. A write tool returns read-back checks[] and a verdict; a write with no verification path cannot be published. Writes take an idempotency_key. These two rules are borrowed from the proven nonagenticai_mcp_server tool contract and are not negotiable in the conveyor's registry.

A binding's ceiling narrows only: a job may lower its effect class at run time, never raise it. The mapping is data on the tool version; it is not inferred from the HTTP method.

Tool selection is not an LLM decision. In a procedure run the step names its tool; a step that must choose among tools uses L1 over the bound option set. In an internal_agent run the release's grant set bounds what the agent may choose, and every choice is recorded; the broker never widens the grant.

11.5 BYO tools (D42)

A tenant may bring two kinds of tool and only two:

  1. OpenAPI toolkit — an OpenAPI 3.1 document imported as a draft toolkit: operations, closed schemas, mappings, effect class per operation (default read), a destination base URL and a credential alias. Publication needs tenant-admin approval and a contract test against a recorded replay.
  2. Remote MCP server — a streamable-HTTP MCP endpoint; the conveyor discovers its tools, binds a credential and exposes only the bound subset to the tenant's jobs (binding-scoped discovery).

Never: uploaded code, arbitrary container images, caller-supplied URLs at call time, or a tenant credential in a prompt. The conveyor never executes tenant code; a tenant that needs executable logic runs its own service and registers it. A tenant toolkit stays tenant-scoped; promoting it to the platform catalogue is a kata/development project with a platform review, never an admin toggle.

11.6 Tools that generate tools (D43)

Development projects already act through the coding toolkit. Three generation paths, all governed:

  1. Spec → toolkit. An OpenAPI document (a new service, or one being changed) is imported as draft operations, contract-tested, then published.
  2. Service → toolkit. A new service is scaffolded from template-rust-service, deployed, and its OpenAPI is registered — the tool is the new service, not a wrapper around it.
  3. Missing operation → tool request. A procedure step that needs an operation with no tool opens a tool-request card; a development job implements it, publishes the version, and the step is rebound to that pin.

The pipeline is a governed-asset lifecycle: governed_asset(kind='tool_draft') → validation (schema, effect, egress, credential scope) → security review (a destructive tool needs a named approver) → tools.publish (immutable version) → binding. A tool cannot be published with wildcard egress, a free-form input schema, or a write effect without an idempotency declaration. The tool that publishes a tool is itself a tool bound to the authoring job — and cannot grant itself a wider effect ceiling.

Tool code lives in the conveyor monorepo (D58). A new tool is a crate or service inside the conveyor workspace, registered from its own OpenAPI; a migrated tool joins the workspace on the day it is rewritten in Rust. An external service stays bindable as a toolkit meanwhile. Nothing is imported from nonagenticai_mcp_server's toolkits/ (coding, fr) — those are read as reference only (D44).

11.7 Relationship to nonagenticai_mcp_server (D44)

Concepts borrowed (measured 2026-11-11): the catalog shape — mcp_services/mcp_sources → mcp_tool_versions/mcp_toolkit_versions → mcp_bindings with mcp_credential_profiles → mcp_tool_call_audit; immutable version pinning; the closed Draft 2020-12 schema subset; binding-scoped MCP discovery; the credential broker; the result envelope; write-verify. Not adopted: ephemeral Kata execution — BYO is declarative only, so the conveyor never runs uploaded code.

Dependency refused. The mcp server is a second control plane: Python, its own Postgres queue, its own catalog and runner. The conveyor already owns actions, secrets, entitlements, audit and a durable job queue. One repo, one schema, one queue (owner direction, 2026-11-11). The mcp server remains the agent platform's gateway for its own backends; it is that platform's own roadmap, and the conveyor never routes through it. Its coding toolkit (repo provisioning, verified writes, PRs) is the reference for the conveyor's coding toolkit. The fr toolkit retires with fr at cutover (V1 D19).

Two paths, permanently (D59). There is no planned convergence: the agent platform keeps its own gateway, and the conveyor broker is not exposed to it. "One audit path" is explicitly not a V2 goal; the conveyor's ledger covers conveyor jobs only (§15.2 #11).

Per tool: calls, success rate, p95 latency, error classes, cost. Per job: tool-budget usage. 11.10 Object storage — direct MinIO, tenant-separated (D57)

The conveyor does not depend on artifact_service :8556 or storage-api :8391 for its own bytes. Credentials are sealed broker credential profiles; a job never sees an S3 key. artifact_service and storage-api keep serving their existing consumers; the conveyor keeps no compatibility shim by default — whether V1's artifacts.list callers are migrated to the adapter or routed through a shim is settled in T13 (§15.2 #17).
