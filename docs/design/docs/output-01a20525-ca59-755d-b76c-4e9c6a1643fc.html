Project Context Diagram — T13 Tool platform

The context is the tool spine's boundary as the architecture design states it: what T13 owns, what it consumes, and which parts of the organisation and estate its calls touch.

Context

T13 sits in delivery tranche 3. It is the path T6 (the development project), T7 (operations) and the estate toolkits (T14), BYO tools (T15), ingestion (T16) and authoring (T17) build on. A job's run step calls a tool through tools.call; the broker resolves the binding, the pinned toolkit version and the ceiling, validates the input, dispatches, writes one tool_call row and emits tool.called. T13 owns the four tool tables, the tools.* family and the storage key discipline; it does not own credentials, approvals, the model, backend health or the card/run state machine.

Affected organisation

  • Delivery jobs — coding and operations runs stop calling backends directly; their only path becomes the broker, and their tool grants become bindings.
  • The platform team — publishes toolkit versions, binds them to jobs, and reads the tool-call ledger to retire or justify a toolkit with no calls in a cycle (B2).
  • Tenants and their approvers — a destructive tool call consults the tenant's existing approval_policy/approval_decision; no second approvals model is introduced.
  • The programme board — the tool estate census is a B2 evidence source at each tranche review.

Affected systems

  • The conveyor run/step executor — carries the binding and the run/step ids the broker resolves.
  • The secret store (secret) — holds the sealed credential a binding's alias names; the broker opens it, the prompt never sees it.
  • The approvals model (approval_policy, approval_decision) — gates a destructive call.
  • MinIO object storage — tenant-prefixed, server-side encrypted, content-hashed keys under tenant/<tenant>/project/<project>/run/<run>/<name>; no bucket administration, no S3 key in the prompt.
  • The eight V1 external backends — workers.list, providers.list, graphs.list, artifacts.list, billing.summary, coding_jobs.create, coding_jobs.get, retrieval.query; they stay where they are and their addresses move into toolkit operations.
  • The event/audit ledgers — tool_call, event and audit_event carry the call evidence.
  • nonagenticai_mcp_server — reference only (D44); never a runtime dependency.
