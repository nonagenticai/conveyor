Outcome

The claude-api build-eval and eval-audit methods become an ordinary product surface: a person defines one flow, builds an input set, signs off the inputs, chooses metrics and a grader, signs off the grading, runs a pilot and then a baseline, and reads a report — all against rows, not a .claude/hillclimb/<flow>/ directory of results.jsonl, traces/ and report.html.

Boundary

IN. The ten tables (§2.19); the approval.eval_id column and uq_appr_eval_pending index; the thirty-three actions, three scopes and seven events; the four jobs; the three built-in versioned prompts; screens 15–20 declared for S12. Parts A (define, inputs, sign-off), B (run, grade, capture) and C (report, audit, interop).

OUT. Any UI — screens are declared here so S12 may not invent them. Building a model call of its own: the runner invokes a registered action and never reconstructs a request, which is build-eval.md's "reimplementing the app" failure. Hosting a model, embeddings or a second runtime (D22). The hillclimb loop and the cost search — S20.
