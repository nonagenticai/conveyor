How the checks were run

Two lanes, and they are deliberately different:

  • The corpus and the renderer's exact output were checked by running lake env lean <file> inside the prover's own pod, against its own lake project, with the file streamed in and removed afterwards. That is the same command the prover's runner issues, so "valid" here means the same thing the API would answer — without going through the HTTP layer.
  • The engine path (the declared lean4.check external, the sealed credential, the persisted invocation, proofs.record and proofs.reverify) is proven by integration tests against a real PostgreSQL 18 and a stub prover: crates/actions/tests/proofs_record.rs, proofs_reverify.rs, pm_gate_proof.rs.
  • The live drills (§ Live on the released engine) run that same engine path against the deployed engine and the real prover, through the public API, with a real tenant bearer.

The renderer's own emission format was checked the same way, once per kind: a rendered slice, a rendered programme bundle and a rendered package manifest each exit 0, including the checks := [("name", true)] pair list. The negative runs are what stop the corpus being vacuous: a model that is not a model, a slice missing its evidence, a bundle missing a leaf, and a bundle that reuses one certificate for two slices are all refused by the kernel, not by us.

Earlier on the same day, through the prover's HTTP API with a licence token, the same shapes measured: model 1 466 ms, slice 1 462 ms, package 1 598 ms, 20-leaf bundle 6 149 ms, and the same four negatives refused. The HTTP answer agreed with the kernel answer in every case.

What the certificate says, and what it does not

A certificate is an instance proof over canonical facts plus a universal proof over a hand-written model. It proves that the facts, as recorded, satisfy checkSlice / checkProgramme / checkPackage, and that a closed item is terminal with an accepted path always carrying evidence.

It does not prove that the engine's facts describe what actually happened in the database. That refinement is assumed, and every certificate names the assumption, the specification digest and the model digest. README.md in docs/spec/lean/ states this in the same words a reader of a certificate would need.

A prover defect this exposed

A check that fails returns valid: false with diagnostics: [] and Lean's message in stdout: apps/lean4-prover/src/runner.rs parses only stderr (three call sites). Certificates are unaffected — valid comes from the exit code — but the diagnostic channel is empty for every failure. Worth its own fix; it is not #746's.

What this still does not prove

  • That the facts in a certificate describe what actually happened in the database. That refinement is the assumption every certificate names (see docs/spec/lean/README.md); proving it is Verus/Kani work, not part of the corpus.
  • The self-service mint path: the credential above was minted and sealed by an operator, and --mint still needs the dedicated client and the licence-app decision (#776).

At the default recursion depth, N = 400 and N = 444 both fail in 2.5–2.9 s with maximum recursion depth has been reached; N = 200 passes untouched. The first run of the session was a smoke theorem at 825 ms; the 10 242 ms cold figure above is the pod's first run after a restart and was not re-measured (the live pod was not restarted).

The negative controls — two branches, two PRs, a draft PR, three CI runs, merged with the issue pending, merged with the branch live, unknown branches — each exit 1: the kernel refuses checkLedger [bad] = true, it is not a render refusal. An empty ledger is also exit 1 (the !isEmpty guard). A String.startsWith "issue/836-" probe under decide exits 1: startsWith is not kernel-reducible in this toolchain, so prefix checks must arrive as derived facts, never as Lean computation in the checker.

One lean4.check at N = 200 through the deployed engine was attempted with a machine principal minted in the conveyor pod. It answered 403 action-forbidden: the principal lacks the integrations:read scope the action declares. That is a principal/grant result, not a prover result — the direct runner path above is the command the prover issues. A2 must run with a principal holding integrations:read (the check) and approvals:write (the record). A conveyor rollout replaced the pod during the first attempt; the 403 is from the new deployment.

Decision. Certificate chunk = 200 units. At 200 the source is 32 530 bytes against the 100 000-char cap (3× headroom) and the warm maximum is 2 239 ms against the 120 s prover timeout (53× headroom); with the 10 242 ms cold start the worst case is ≈ 12.5 s. The full 444-unit ledger would fit one certificate (65 348 bytes, ≈ 2.7 s) but needs set_option maxRecDepth 4000; 200 is chosen so a failing chunk is bisected cheaply and the default recursion depth stays in force. The ledger window is therefore all merged PRs in the window plus the unit issues — about three chunks. The renderer refuses more than 200 units per source unless it emits the option.

Same assumption as every certificate: the kernel certifies facts ⇒ verdict. The collector's rules, hashes and committed payloads are what a reviewer checks against reality.
