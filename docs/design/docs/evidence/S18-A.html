What was built

benchmark_runs.trend (crates/actions/src/benchmark/trend.rs) — internal, benchmarks:read, read-only, idempotent:

  • input {suite_id, arm?, limit?} → output {baseline_run_id?, points[]};
  • each point is a succeeded run of that suite: run_id, arm, subject_kind, subject_id, subject_version, label, started_at, n_graded, n_resolved, rate, control_ok, direction, vs_baseline;
  • rate is n_resolved / n_graded, and absent when nothing was graded — never 0.0 for "no data";
  • vs_baseline is CompareView, the exact type benchmark_runs.compare already serves.

One comparison, two callers. benchmark_runs_compare's body was extracted into benchmark::compare_two_tx (crates/actions/src/benchmark/mod.rs) and the compare handler now calls it too. A trend point can therefore never disagree with what a person reading benchmark_runs.compare gets — the McNemar call, the suite rule, the missed-control rule and the oracle/prompt rule have exactly one owner.

S18 §9.4 is enforced before any number is computed. vs_baseline exists only when the point and the promoted baseline are both conveyor runs and the baseline itself reached succeeded. A gold/empty/baseline point, a non-conveyor baseline, a partial baseline, a different oracle or prompt, and a control that missed all produce a point that is displayed with comparable:false and the reason — never dropped, never averaged. That refusal is the whole instrument: plotting a control against the capability baseline is the visual form of the comparison CONTRACT §19 refuses.

Deviations from S18 §5, each deliberate

  1. direction is a sibling of vs_baseline, not a member. CompareView is the compare action's own type and gains no field; the screen reads point.direction (candidate_better | baseline_better | unchanged, absent when not comparable) instead of re-deriving it from a_only/b_only.
  2. subject_id / subject_version are optional. A suite subject has no id. More sharply: subject_version is always absent today, because benchmark_run has no version column and nothing writes one at start. A live join would report a capability_agent's current optimistic-concurrency counter — which any edit bumps — as if a past run had measured it. subject_id is the pin; the version number is step 1's to record.
  3. Only succeeded runs are points. A queued/running run has no number; a failed one has a partial denominator that would read as a regression never measured.
  4. limit is capped at 100, below the shared envelope's 200: each point costs three queries inside one 30 s transaction.

What step 1 must decide (carried, not guessed)

  • Where the conveyor arm's patch lives. domain::run::Run has no output field, and a patch is a run product, not a run state. S18 §3 requires the producer to be a consumer of the public surface, so the patch needs a home an action writes and another action reads — an S09 document is the obvious candidate, and it is the shape benchmark_case.log_document_id already uses.
  • Where the improvement job records keep | revert | inconclusive. benchmark_run has no verdict column and S18 ships no table and no event, so today there is nowhere honest to write it. A column on benchmark_run (a migration) or an benchmark_run.changed payload the plan forbids are the two real options; this needs an owner ruling, not an implementation choice.
  • The run must pin the subject's version at start, so subject_version can stop being absent.
