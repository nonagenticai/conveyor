What the service is

The service is the system of record for human judgement in an evidence review. It owns a protocol-locked review, reversible deduplication, two blinded reviewers, append-only decisions, conflict adjudication, a derived PRISMA flow ledger, and an inclusion-set export sealed with a canonical hash. Its stated scope is ER-001..ER-005 plus the OUT-001 export contract. XLSX import, automatic exclusion ranking, the proposal lane, appraisals and any regulatory canonical surface are deliberately absent, and no route below restores them.

Three invariants hold across the whole service. A machine cannot decide: the actor seam refuses a caller that presents a tenant but no subject, so no code path writes a decision without an authenticated human (src/actor.py; the screening decision body deliberately has no reviewer field). Reviewer B cannot see reviewer A: six layers, any one of which alone leaks — FORCE ROW LEVEL SECURITY with a non-owner runtime role, one blinded read function (application/services/blinded_reads.py::visible_decisions), a queue over the caller's own assignments, cursors over assignments rather than records, 404 never 403, and flow.require_no_owed_decisions on every route that derives an aggregate. History is append-only: BEFORE UPDATE OR DELETE triggers raise in the database, there is no is_current column, and "current" is the tail of a supersession chain made linear by partial unique indexes.

RLS with FORCE

Every one of the 47 tables is put behind row-level security by a per-migration helper: alembic/versions/0002_er_m002_reviews.py::_tenant_rls, 0003_er_m003_imports.py::_tenant_rls, 0004_er_m004_deduplication.py::_tenant_rls, 0005_er_m005_screening.py::_tenant_rls, 0017_er_m017_a_research_object_has_identity.py::_tenant_rls, 0018_er_m018_accepted_evidence_names_its_basis.py::_tenant_rls, 0019_er_m019_domain_outbox_commits_with_the_state.py::_tenant_rls, 0020_er_m020_a_long_job_survives_the_worker_that_ran_it.py::_tenant_rls, 0021_er_m021_a_snapshot_says_exactly_what_a_run_may_read.py::_tenant_rls, 0022_er_m022_an_event_can_finally_leave_the_service.py::_tenant_rls and 0025_er_m025_an_artifact_ref_is_never_a_storage_key.py::_tenant_rls. Each helper emits both ENABLE ROW LEVEL SECURITY and FORCE ROW LEVEL SECURITY; screening_decisions is the one explicit pair because its policy is the blinding policy (0005, lines 338-339). 0009 deliberately lifts FORCE on screening_assignments and corpus_versions for a backfill and restores it at lines 157-159; the lift is bounded to the migration and is not a runtime property. The application runs as a non-owner role, which is what makes FORCE bind the table owner too.

Append-only triggers

The append-only guard is a reusable PL/pgSQL function that raises on UPDATE or DELETE: 0002_er_m002_reviews.py::_append_only_trigger (state history), 0004_er_m004_deduplication.py::_append_only (resolutions and survivorship fields), 0005_er_m005_screening.py::_append_only (assignments, decisions, conflicts, adjudications, unblinding events, inclusion exports), 0015_er_m015_the_ledger_inputs_are_append_only.py::_append_only (import batches, import rows, duplicate clusters and cluster members), and 0018_er_m018_accepted_evidence_names_its_basis.py::_append_only (the accepted-evidence identity and version tables). 0011_er_m011_review_stages_append_only.py::review_stages_append_only adds the one table that was described as append-only but was not guarded. 0025 guards artifact_records. The guards are database constraints, not application convention; the service's own tests disarm each one inside a rolled-back transaction to prove the refusal is not vacuous.

Supersession chains

No table carries a mutable "current" flag. Linearity is a partial unique index: one un-superseded head per subject and one successor per superseded row. Measured names include 0003_er_m003_imports.py::uq_record_version_supersession_linear and ::uq_corpus_version_supersession_linear; 0004_er_m004_deduplication.py::uq_resolution_supersession_linear and ::uq_resolution_one_head_per_cluster; 0005_er_m005_screening.py::uq_decision_one_current_per_reviewer, ::uq_decision_supersession_linear, ::uq_adjudication_one_current_per_conflict and ::uq_adjudication_supersession_linear; 0017_er_m017_a_research_object_has_identity.py::uq_research_object_version_supersession_linear; 0018_er_m018_accepted_evidence_names_its_basis.py::uq_extraction_dataset_supersession_linear, ::uq_observation_supersession_linear, ::uq_research_assertion_supersession_linear, ::uq_acceptance_one_chain_per_subject and ::uq_acceptance_supersession_linear; and 0021_er_m021_a_snapshot_says_exactly_what_a_run_may_read.py::uq_snapshot_one_chain_per_review, ::uq_snapshot_supersession_linear and ::uq_snapshot_one_per_job. A merge is undone by inserting a new split row, not by editing or deleting the merge row.

The canonical-hash seal

The seal has two halves. In the database, corpus_versions.member_manifest_hash is checked at insert and on any membership change by 0003_er_m003_imports.py::corpus_versions_verify_seal and ::corpus_versions_verify_seal_on_version, which recompute the hash from the member rows and raise when it differs. inclusion_exports carries both canonical_counts_hash and manifest_hash, with ck_export_hashes_are_distinct ensuring the manifest is not merely a copy of the payload digest (0005_er_m005_screening.py, lines 387-428). 0006_er_m006_export_seal_mode.py::SEAL_MODES records which algorithm sealed each row (content_hash, canonical_sha256 or the historical unknown), because an export sealed through a narrower fallback must remain legible rather than silently upgraded. In the service, src/application/services/flow.py::EXPORT_SCHEMA_REF names the released manifest contract, ::_seal_manifest prefers compute_content_hash and falls back to RFC 8785 canonical_sha256, and ::seal_mode reports the mode. The verify route recomputes both hashes from the stored bytes; the supplied hash is never trusted.

The classification rule

Every row carries exactly one state and, when dropped, exactly one reason. The reason literals are the same three the analysis capture uses; the ground each one requires is fixed here so a row can be checked rather than believed. First match wins:

  1. ported — a Rust entry point exists today. The ground cell names it. This capture has no ported rows: P3 and P4 do not exist yet, so inventing one would make the table lie.
  2. dropped: transport — the operation's subject is the service's own plumbing: liveness, readiness, metrics. Conveyor already owns that surface. A transport row must name the conveyor surface that replaces it; here every one is conveyor:liveness, the fleet probe-and-scrape surface. A row that cannot name one is not transport.
  3. dropped: deferred — a domain operation the port plan owns. The ground cell names the part of issue #319 that requires it: part: P3 (routes, actor seam, blinding layers and the review domain) or part: P4 (the inclusion-set export and its seal). A deferred row may also name a measured caller as caller: <path:line>, but this capture uses the part form for every domain row because the port is not built yet. P5 owns the served contract and the parity gate, not an operation, so no row is deferred to P5.
  4. dropped: no consumer — analysis-shaped, with no replacement and no owning part. This capture has none. An absent caller is not treated as a retirement decision here: issue #319 assigns every domain operation to P3 or P4, so a missing caller is recorded in “Consumers” rather than used to drop a row. The one deliberate consequence is that the no consumer literal does not appear.

Columns: method | path | operation_id | tag | state | reason | ground | evidence | request_ref | response_ref. evidence is the handler's own work read from the pinned source, not a restatement of the reason. tag is the router's declared FastAPI tag verbatim; health and metrics are the router areas because those two modules declare no tag. request_ref is the declared Pydantic body model, object for a free-form body with no model, and - for no body. response_ref is the declared response model, application/json for a handler that returns a JSON object with no named model, and text/plain; version=0.0.4 for the Prometheus scrape. - means the source declares nothing in that position; it is never used in the reason column of a dropped row.

Deviations, recorded rather than hidden

  1. Revision. The issue names 5e3a868 (2026-11-17); this capture reads bac4f6612b2632621c7f6e2650259257fa17f877 (2026-11-18T00:07:13+01:00). The diff is uv.lock only, so routers, migrations and table definitions are unchanged. Both dates are recorded because a reader who checks the issue will find a different revision and should know why.
  2. Table count. The issue and the source README say 26 tables. The migration head at this pin defines 47. The 26 is the retired production database measured on 2026-09-02, before migrations 0019 through 0028; the README's claim that no migration created domain_outbox, durable_jobs or job_attempts is contradicted by 0019 and 0020 at this pin. P2's acceptance criterion must either adopt 47 or state the subset it means; this document records the measured head.
  3. No served-document capture. Unlike the analysis capture, no OpenAPI JSON is committed beside this table and no live request was issued. The operation list is read from the route decorators and handler signatures at the pin. A later part that wants the analysis capture's digest-pinned contract check must capture the served document at P5; this table alone supports coverage and wiring claims, not semantic parity.
  4. /metrics has no operation_id. The route is include_in_schema=False and declares no operation_id, so the function name metrics is used. The health routes declare operation_ids but no tags; health and metrics in the tag column are therefore area names, not declared tags. The declared tags elsewhere are capitalized (“Reviews”, “Accepted evidence”, “Exports”, “Flow”, “Review jobs”, “Imports”, “Screening”, “Evidence snapshots”); if the P5 parity test normalizes to lowercase, this column is the input to that normalization, not a served-document tag.
  5. Port disposition. Every operation in P3/P4 is ported in this unit — 55 of the 60, each row naming the module that serves it and the check that proves it.
