The defect this work found

The port declared X-Capture on the completions route and served the capture read, but nothing ever wrote the capture columns. After cutover the capture route and the replay surfaces it feeds would have been dead — silently, because the read answers 404 not_captured.

It was found by building the shadow harness and recording a call through it: the call answered captured=false on a live process while the source looked complete.

Fixed at 7c139b8:

  • apps/inference-router/src/ledger.rs — the row now carries request_json (the fingerprint plus model), response_json, request_text and response_text; the insert writes them. The stored request minus model re-hashes to request_sha256, which is what the read's request_sha256_verified checks.
  • apps/inference-router/src/router/completions.rs — capture_allowed: X-Capture: full from an allowlisted X-App-Id. A refused capture serves the request normally and stores hashes only. A streamed row never captures (the reference forces it false on that path).
  • apps/inference-router/tests/capture_write.rs — 3 tests: the allowlisted store→read round trip (both integrity flags true), no header stores nothing and the read answers 404 not captured, and an unlisted X-App-Id stores nothing.

The success path is not in the golden set: the captured internal_capture case is the 403 refusal, and the oracle harness cannot arm its allowlist yet. The behaviour is pinned by the tests against the reference's source, and the limitation is stated rather than hidden.
