Which revision the served document is

The working copy of the service's repository on this machine sits on a branch that no longer exists upstream, at fad3856, which is not an ancestor of origin/main. The classification rule

Every row carries exactly one state and, when dropped, exactly one reason. The reason literals are the issue's; what each one is allowed to mean here is fixed so that a row can be checked rather than believed. First match wins:

  1. ported — a Rust entry point exists today. The ground cell names it, and the ported assertions live in crates/analysis/tests/parity.rs.
  2. dropped: transport — the operation's subject is the service's own plumbing: liveness, metrics, job/batch/schedule ledger rows, progress streams, artefact and export bytes, logo bytes. Conveyor already owns that surface, so porting it would be a second copy of the platform. A row may only claim this reason if its ground cell names the conveyor surface that replaces it (conveyor:liveness, conveyor:job-engine, conveyor:scheduler, conveyor:artefact-store). A row that cannot name one is not transport.
  3. dropped: deferred — an analysis core the port plan owns. The ground cell names the measured caller (caller: <path:line>) or the part of this issue that requires it (part: P5, P6).
  4. dropped: no consumer — analysis-shaped, and neither 2 nor 3 holds. This is the issue's default for an operation with no measurable consumer; the scope of the consumer search is stated under “Consumers” below so a later reader can repeat it.

Columns: method | path | operation_id | tag | state | reason | ground | evidence | request_ref | response_ref. evidence is what the handler's own work is, read from origin/main — the phrase that makes the reason checkable, not a restatement of it.

- means "nothing declared": no request body, no response model, or no ground. It is never used in the reason column of a dropped row.

What this corrects

  • The issue's "46 operation_ids across 9 domains" is stale. Measured: 92 operations across 12 domain tags plus health. This document is the measurement; the issue body is not.
  • The issue's open question 1 ("which of the 46 captured operations has a measured consumer?") is answered per row: 16 of 92 have one, each with a file and line below.
  • P5's analyse.brand comparison is compare_brands, which has no production caller — it is required by part P5.2, and the row says so rather than pretending a caller exists.

Deviations, recorded rather than hidden

  1. No live request was issued. Around two thirds of these operations mutate production rows (create, cancel, delete, batch, schedule). The pair per row is the contract pair read from the committed served document — request schema, response schema, declared success status — not a recorded transaction. This capture therefore supports coverage and wiring claims, not semantic parity. Behavioural samples, where a later part needs them, come from the source's own tests.
  2. One pin for the document, not one per row. Repeating a digest 92 times is noise; each row addresses its pair by schema name into the committed document, which is pinned once.
  3. The gitops manifest does not match the pod (see the pin). Deployment drift is out of scope for this unit; the capture records what runs.
  4. The P3/P4 port was written from the stale checkout. The SEO scanner on origin/main has moved since: geo.py (+111 lines), schema_coverage.py (+97), eeat.py and internal_linking.py (±14), and the check-id set changed at the edges (+seo-robots-txt-errored, +seo-sitemap-errored, −seo-keyword-intent). The scoring kernel did not move — the group weights, the decay, the floor, k and the severity weights are identical, and composite.py only adds unmeasured-bucket handling, which does not apply when every group runs. The ported row's ground carries this footnote; re-porting geo and schema_coverage is an owner decision, not a silent edit inside P1.
