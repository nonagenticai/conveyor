S13-PROCESS — the process engine, judge, bus and catalogue, as built

Receipt for lane/s13-process-engine (2026-11-10). It records what is on disk, not what was planned; the plan is docs/plans/slices/S13-n8n-engine.md.

The executor model — the engine is RETAINED

Owner ruling 2026-11-09: the workflow engine is retained. crates/workflow, the workflow table, workflows.*/workflow_runs.* and the workflow.node/workflow.start job kinds stay. It is the tool-sequence executor. There is no 0034 drop migration and run.workflow_id is not removed. The process is the top-level executor; the workflow engine is never a second one.

The call step is wired (2026-11-10). A call step names child_process_key; the executor resolves it process-first (process::published_by_key_tx) and workflow-second (workflow::get_published_by_key_tx). Both starts happen on the executor's own transaction: process_runs.start (the same action an external caller uses) or start_published_tx with its parent: Option<(run, step)> branch, which inserts a CHILD workflow run instead of a root. The child's id is written to the parent run_step.output in that same commit, so a crash leaves either no child or a pollable id — never an orphan and never a duplicate. Polling re-reads the child by id under the call dedupe tag and a polls counter of its own; a succeeded child's last succeeded run_step.output is judged against the step's SOP, and a failed/cancelled child takes the step's ordinary on_result (continue → skipped, retry → a new child, fail → the run fails). A child never fires err.card; a cancelled parent cancels its live descendants.

The workspace has 11 members — crates/bus is added and crates/workflow stays. CONTRACT §1's earlier "crates/bus replaces workflow, the count stays 10" is superseded.

What is built

  • The bus (crates/bus): envelope {id, topic, from, correlation_id, procedure, tenant_id, job, payload}, groups process|tool, 5 deliveries → bus:dead; the relay publishes from event by seq and records bus_stream_id/published_at. The process.step job is the Redis-absent fallback. CI starts a dind Redis from the archetype's redis_image.
  • The judge, inside the step executor: checker/laya/eval. A reject reruns the same position with the reason (the SOP's max_rejects, default 2) → an exhausted budget fails the run (→ err.card → the coach); an outage parks the step and re-enqueues it. run_step.judge records the verdict. The park is bounded: after JUDGE_MAX_PARKS (64) the step fails CLOSED with judge_unavailable, which takes the ordinary on_result path (fail — the default — fails the run, so the card goes BLOCKED and the coach is notified; continue skips the step). It never accepts an unjudged output and never spends a reject.
  • The call step (see above): process-first, workflow-second, child poll, on_result, depth ≤3 enforced by insert_child_run_tx. runs.cancel and cancel_run_tx sweep descendants; enqueue_run_failed_trigger_tx is root-only, so a child's failure is its parent step's business.
  • The computed set: projects.create creates project + board + start card (project_start_request_analysis, intake) in one transaction and emits card.created, and starts a root run only when the tenant has published a start process; err.card runs on run.failed (BLOCKED lane + comment + coach root run); wip.pull reacts to card.moved. The hook route and CONVEYOR_HOOK_SECRET are deleted.
  • ⛔ No universal tenant seed (owner ruling 2026-11-10). The 280 + 53 catalogue is software-development content, installed only by migrate --process-catalogue --tenant <slug>; migrate --seed never installs processes. A tenant may run accounting, marketing, software development or human project management, so the process a project starts is tenant content — its absence is not an error.
  • The default catalogue: 70 type files / 280 processes / 350 SOPs, loaded by crates/store/src/process_seed.rs (serde_yaml + include_dir); apply_all runs after migrate --seed, and apply_type applies the dev fixture's start process. seed/processes/manifest.yaml is the generated 280-entry index. Tenant-defined processes/SOPs/maps are rows (D29), not code constants.
  • The process maps: seed/processes/maps.yaml carries 3 phase DAGs — it, kata, py2rust — one per project type whose seed/catalogue.json entry declares phases and card types. The loader resolves the project type, validates every node against MapFacts (published process keys, capability codes, that type's meta.phases, milestone_kind codes) and publishes version 1; a second apply inserts nothing. kaizen, meta_procedure, meta_prompt and program declare zero phases and zero card types, so no map is derived for them rather than inventing one.

Outstanding (stated plainly — do not claim these)

  • No live laya.judge/inference.chat call has been made. The token path is built and tested against stubs; a live call needs a tenant row filled (upstream-token --token-stdin) or the licences bundle-token-minter role granted to the secure-apps conveyor-backend client (not granted as of 2026-11-10). The laya request shape remains the first-live-call pin.

  • workflow_step_id is not on RunOut. The column and the tree enforcement exist; the public run projection still exposes only process_step_id, so a workflow child's edge is visible in the database and in the node's output, not yet in the API read.

  • A live call child has no deadline. The parent's poll backs off but never expires: a child parked on its own gate may legitimately wait for a person, and the judge bound covers judge outages only. A child that can never finish is a run-level problem (its live-run slot is the signal), not this step's.

  • The tool-sequence workflows/ files. No coding_jobs/workspaces action exists in this repo (the registry has repositories.* only), so a shipped sequence could not name a registered action. The workflow-second call limb is proven by a test-created workflow, not by seed YAML.

  • The n8n trace fixtures — the historical recordings are not in this repo; the trace export/diff runs over run_step, which is the record that exists.
