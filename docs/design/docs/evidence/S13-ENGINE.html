Corrections this session made to its own plan (recorded, not hidden)

  1. "One loop per cycle" cannot mean "one loop node per SCC". Nested loops put every loop of the nest in one SCC, so the literal reading forbids exactly the nesting §5.2 permits (cap 3). The implemented rule: remove the loop nodes and the remaining graph must be acyclic — every cycle passes through a loop, and any number of nested loops is legal. A loop's body is its each-reachable region (the engine resets that region each iteration), and loop_nesting counts loops by body containment. Proven by nested_loops_publish_up_to_the_cap_and_no_deeper (3 publishes, 4 is refused with depth: 4).
  2. A loop's entry edge and its return edge must be told apart by the body, not by the SCC. L1.each → L2 enters the inner loop; L3.done → L2 returns to it. Both are "into a loop in the same SCC". Counting both as returns gave the nested document three start nodes (measured: MultipleStarts { count: 3 }). The rule now: an edge into a loop is a cycle-closing return iff its source is inside that loop's own body.
  3. Template validation is roots-only (validate_template(template, usize::MAX)). A graph's execution order is not fixed at publish time — a loop repeats its body, a branch may skip one — so steps.<n> cannot be checked against a static position. S11's positional check stays where it belongs (procedure_step, fixed order). A genuinely forward reference fails typed at run time, not at publish. Recorded as a scoped deviation, not as a gap to "fix" by inventing a positional rule for graphs.

Decisions and deviations, stated plainly

  • The action's handler refuses; the executor drives the loop. [HandlerCtx] carries no pool and an internal action already holds the invocation transaction, so a handler cannot invoke the model or a tool. Every executor in this codebase (procedure.step, workflow.node, /mcp) is the layer that invokes outside a transaction, so workflow.node special-cases agent.run. Consequence recorded, not hidden: S11's procedure.step does not special-case it yet, so a procedure step that names agent.run reaches the refusing handler (typed 409) until S11 adopts the same seam. Workflow nodes — S13's surface — are complete.
  • The renderer is this lane's, per CONTRACT §17 (the step executor resolves). S15 step 5 only reads store::capability; s15-capability-crud-actions confirmed no writer collision.
  • The built-in prompt catalogue does not exist. A resolved executor with prompt_ref set and no system message in the node input is refused 409 capability_not_ready / prompt_unresolved — fail-closed, rather than calling the model without the configured prompt. The explicit-input path is the whole gate (S13 §5.3 "Sequencing"); a node can supply its system message today.
  • Idempotency: model and tool calls are keyed under the node attempt's key (…:turnN / …:toolN), so a node retry replays stored responses instead of buying a second round of effects.
  • Tool allowlist: the resolved tools array is the allowlist; a call the model names but the executor did not declare is refused before execution as action-not-found and fed back to the model — never audited after the fact.
