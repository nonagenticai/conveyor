It did check(&served(), ROUTES).expect_err("the port is incomplete by construction in slice 1"); with 60 of 60 operations served, check returns Ok(()), so it panicked: the port is incomplete by construction in slice 1: ().
  • tests/reconcile_route.rs::the_lock_check_never_names_this_route — the expect_err assertion at :524 (the test function begins at :530) panicked: the port is incomplete by construction: ().

Both encoded the slice-era state in which --check-lock HAD to fail. Resolved in a0e757b: the contract test is now the_lock_check_accepts_the_complete_port (asserts check returns Ok) and the reconcile-route test calls check(...).expect("the served contract equals the capture"). The crate's test command is green after that change; the remaining DoD gate is the full workspace suite at the PR head, recorded in the PR.

Recorded deviations

  • Guarded request-path invariants. apps/licenses/src/router/internal_ensure.rs:573,650-652 and apps/licenses/src/auth.rs:653 use expect/unreachable! after a check that makes the bad state impossible; disclosed for completeness. The only added .unwrap()s are test-only (db/tokens.rs). There are no todo!(), unimplemented!(), panic! or #[ignore] in the crate.
  • Shared transport change. This lane also extends crates/auth/src/service.rs with with_timeout/delete for the billing client's transport; the licenses billing tests exercise both. The crates/auth crate has no unit test of its own for the two methods.
  • Offering markup and access refusals. Both failures answer the reference's 502 and restore the prior posture; pinned by tests/tenant_offerings.rs::a_rejected_markup_restores_the_posture_and_answers_502 and ::an_access_refusal_restores_the_prior_posture_and_answers_502.
  • CLI JSON is compact. serde_json::to_string, not the script's json.dumps spacing; key order is the sorted order the scripts used (sort_keys=True). The refusal usage line names the Rust binary (conveyor-licenses <subcommand>) because that is the program being invoked; the reference printed the script's basename.
  • axum versus FastAPI on query-parameter syntax. FastAPI rejects some malformed/repeated query parameters with a 422 HTTPValidationError; axum's extractor can answer 400. The schemas are aligned to HTTPValidationError.detail where a body is validated, and the split is documented per route; it is not claimed that every extractor-level rejection is byte-identical.
  • Implemented but untested. The app-create unique-key race (lost_race) and the byo-mode 503 byo_mode_unresolved fault path are implemented; no test drives either fault at this head.
  • Forwarded-token arm. It uses the service verifier's configured trusted issuers (KEYCLOAK_TRUSTED_ISSUERS/KEYCLOAK_URL); it does not add a second, forwarded-token-specific trust list. A caller whose issuer is not in that list is refused on both arms.
  • released_by_revoke_of records the subject UUID itself, not the subject:<uuid> spelling.

None of these is hidden behind a tolerance: tolerances.json is empty, so every one is either a difference in a field a golden case would compare or an arm with no case yet.
