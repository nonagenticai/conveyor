Live rollback across a migration boundary (2026-11-27, #669)

Issue #669. The rollback fix (#672, a8c22f8e) is proven live: a binary that embeds migrations through 0080 ran against a database that carries 0081, became Ready, and served — both digests and /health 200 at each step.

What the run proves

  • The runtime migrator tolerates a newer applied schema. A 0080-max binary's migrate init container ran against schema 81, the pods became Ready, /health and /health/ready answered 200, and a database-backed action served. Before #672 the same state failed in the init container (VersionMissing), so the prior digest never served at all.
  • The rollback is durable against the image automation when the setter comment is removed, and the restore is a plain revert once the setter is back (the automation then owns the line again).
  • The service stayed available throughout: replicas 2 with maxUnavailable: 0, worker 1, a PDB; the window from suspend to restored-and-ready was 2 m 45 s, and no step served fewer API pods than the rolling update allows.

Two defects in the sanctioned rollback script (found en route)

scripts/rollback-image.sh (the deployment repository) could not be used as written:

  • it matches the setter as "$imagepolicy": "flux-system:<name>" — with a space after the colon — while the conveyor manifest carries {"$imagepolicy":"flux-system:conveyor"} without one, so the script finds no target. The spaced form is the tree's majority (60 lines); conveyor's five lines are the unspaced form written by the image automation.
  • its registry probe uses HTTP Basic auth; GHCR answers 401 (it requires the Bearer token exchange), so the script refuses any ghcr.io image before it reaches the rewrite.

This run followed the script's procedure by hand — suspend, bare-digest pin with the setter removed, reconcile, verify, re-enrol — and the same pin and revert are the record above. The two defects are reported here, not fixed in this unit.

Scope

No application code changed. The only shared-state changes were the temporary pin and its revert in the deployment repository (both named above), plus the suspension and resumption of the image-update automation.
