Publication wave

toolkits.publish published the embedded catalogue: coding/speech/transcription/image_gen to version 2 (version_bumped), scientific created at version 1 as published (its manifest status was changed from draft because the gate names it), retrieval/webscraper/lean4 created as draft. 39-publish-idempotent.json is the second run, showing unchanged for every toolkit.

Product defects the live gate found (fixed on this branch)

  1. The outbound Idempotency-Key was never forwarded. The coding service refuses a create without the header; the engine claimed the key for its own dedupe and sent nothing. The external dispatcher now forwards the caller's key (crates/actions/src/invoke.rs) and the admin CLI can carry one (--idempotency-key). The coding call above is the proof.
  2. scientific was not publishable (manifest status: draft) although the gate names its probe. Status changed to published.

Blockers that are not code

  • Tenant licences — a production licensing act, by the programme's own rule. speech/ transcription need a sealed licence.token for the audio services; scientific needs a licence its service accepts. The staging record holds only the conveyor app licence, and the production tenant's sealed licence.token was created after the record copy was taken. The programme already ruled on this class in docs/evidence/S21-RUN.md:100: minting a licence for a non-production tenant is a production licensing act, so these calls are deploy-bound proofs taken with the production credential on the deployed engine — not something the pre-merge record can or should mint for itself.
  • Object storage in the local engine. image_gen renders but cannot store its document without MinIO; the deployed pod has it. This receipt is likewise deploy-bound.

Both are named, measured refusals — not silent gaps. Until the deployed proofs exist, T14's live-call clause cannot be claimed, and the project stays open.
