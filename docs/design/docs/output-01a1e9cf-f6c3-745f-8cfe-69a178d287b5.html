Architecture principles

Programme: conveyor buildout · Status: proposed for P0 acceptance (drafted 2026-11-17) · Date: 2026-11-17 · Owner: the programme architect (architect, job catalogue) · Reviewer: the Architecture Board (charter proposed here; the board is convened when T9 lands — see Application) · Artefact: PF-1, principles_catalog, plateaus PSA/HLD/SD.

Principles

Each entry is a statement, its rationale, and the implications a project must design under. The evidence column names where the principle is already enforced; a principle the code does not yet enforce says so.

P1 — One model, one store, one action registry

Statement. A programme, its projects, their work, their decisions and their evidence are rows in one Postgres database written through one action registry. A concept has one table and one set of actions; it never has a second system of record.

Rationale. docs/SPEC_V2.md §10 and docs/decisions/0005-absorption-sequence-and-repo-scope.md: the estate's pain is not missing services but distributed fragments of one model. One registry makes permission, audit and replay uniform; the registry is compiled, not configured, and its exact set is asserted by its own test (crates/actions/tests/registry.rs), so a new action cannot appear unseen.

Implications. A new capability is a table plus actions in this workspace, not a new service. A service that must run separately is absorbed behind an action (ADR 0005's sequence), and its data joins the one store. No feature may keep a private file or cache as its record of truth.

Evidence. crates/actions/src/lib.rs (the registry), migrations/*.sql, the S04 registry tests; the console's action manifest is generated from the same registry.

P2 — Every mutation is an action; the database is not the API

Statement. A write goes through an action, with its scope, tenant, precondition and event. No handler, UI or script writes rows by SQL; the operator CLI calls the same actions the HTTP surface calls.

Rationale. RFC 9457 errors, If-Match/_version preconditions, revision history and audit all hang off the action envelope (crates/actions/src/invoke.rs). A SQL write bypasses every one of them and produces a row no event describes.

Implications. A new write is an action with a schema, a scope and a test. Read-only probes on the primary are allowed and must be BEGIN READ ONLY; anything else is a defect. The CLI's bulk content path (documents.compose with publishable: true) is still an action and is gated like the console.

Evidence. crates/actions/src/invoke.rs (dispatch, precondition, error shape); the registry test committed_action_dump_matches_the_registry.

P3 — Tenant isolation is structural, not a filter

Statement. Every tenant-owned table has RLS enabled and forced, and every query runs under the tenant's scope. A cross-tenant id resolves to 404, never to a filtered row or a 403 that confirms existence.

Rationale. docs/SPEC_V2.md §5.4; migration 0001's app_current_tenant() and the tenant_isolation policies; the store's begin_scoped is the only path that sets the GUC.

Implications. A new table ships with its policy in the same migration. A test that proves a foreign tenant's id is 404 accompanies the aggregate. A session-level GUC is forbidden through a transaction pooler (it leaks to the next client — measured 2026-09-22); a read-only probe uses BEGIN READ ONLY or a direct primary connection.

Evidence. crates/store/src/scope.rs; crates/actions/tests/registry.rs's a_foreign_tenant_parent_id_resolves_to_404_never_to_a_write.

P4 — Publication is a decision, never a side effect

Statement. A row is public only when an admin's publish decision makes it public. The public window serves publishable AND status='active' rows; an author's write never publishes, and an author's raw HTML is never executable on the public page.

Rationale. docs/SPEC_V2.md §3 P4 (the executor never approves its own work); the document aggregate keeps publishable separate from content, and documents.publish is the only action that moves it. conveyor_render::markdown neutralises raw HTML and refuses non-http(s)/mailto schemes.

Implications. A new public surface filters on the public bit and carries the tenant. A publish transition is reversible (unpublish is free) and versioned. A preview uses the same renderer as the public page, so an author cannot be promised markup the public page would refuse.

Evidence. crates/actions/src/documents/revisions.rs (documents.publish, documents.request_publish, documents.return); crates/render/src/markdown.rs.

P5 — Every output is versioned, attributable and reversible

Statement. A text output carries its author, a content hash and a revision history; every edit is versioned, and a restore copies a version forward rather than rewriting the timeline. The public page is served from the same Postgres rows the console edits.

Rationale. The programme is judged on its intermediate work products; a published output a reviewer cannot trace back to its author, version and evidence is not auditable (docs/SPEC_V2.md §8.5's trace chain).

Implications. A new aggregate that holds work products reuses the document model or carries the same provenance. Deletion is a tombstone, not a disappearance, and a purge is a job with its own record.

Evidence. migration 0042; crates/store/src/document.rs (write_document_revision_tx); crates/api/tests/document_workflow.rs.

P6 — Programme truth is computed, never hand-written

Statement. A project's status, its units, its dependencies and its expected outputs come from measured sources — the slice plans, migrations, the compiled registry, the console and GitHub — and are regenerated by scripts. A checklist is derived from the standard, not typed into a document.

Rationale. docs/design/data/coverage.json is built by scripts/build-coverage.py from the slice frontmatter, the migrations, the action dump and v2.js; the output standard generates every project's meta.expected_outputs. A hand-written status is the first thing to rot.

Implications. A new programme fact gets a generator and a --check gate. A document may explain the truth; it may not be the only place the truth lives.

Evidence. scripts/build-coverage.py, scripts/build-programme-seed.py, scripts/check-output-standard.py; the design-pack CI job.

P7 — Gates refuse; a gate that never refuses is broken

Statement. A quality gate is a refusal with an actionable reason, exercised by a test that proves the refusal. A gate that has never refused in a full cycle is treated as broken, not healthy.

Rationale. docs/SPEC_V2.md §3 P3/P4 and §8.3's rule; the estate's measured history: the projects.create gate and the output-incomplete gate exist because a publish without evidence happened.

Implications. A gate names what is missing and offers the next step (edit, return, kata). A refusal is covered by a test at the boundary the caller uses (HTTP, CLI), not only by a unit test. A gate that cannot refuse for a category or a path is a gap, not a default.

Evidence. crates/actions/tests/authoring_standard.rs (the seven authoring-standard boundary tests, most of them refusals); the programme gate's 409 blocked_by; crates/api/tests/document_workflow.rs.

P8 — Typed dependencies, explicit gates

Statement. A dependency between projects is typed (blocked-by, acceptance-blocked-by, blocks, related) and the programme gate enforces the blocking kind. A tranche review is a programme decision on evidence, not a demo.

Rationale. docs/SPEC_V2.md §8.3; T1's plan spine (project_dependency, programme_tranche); the process_runs.start gate answers 409 blocked_by naming the open dependency.

Implications. A project's inception names its dependencies and the contract it sits under. A deviation from the blueprint is a decision record; a slip names the benefits put at risk through the benefits map.

Evidence. migrations/0044_plan_spine.sql; crates/actions/src/spine/; crates/actions/tests/plan_spine.rs; the run gate's 409 blocked_by (crates/actions/src/programme.rs).

P9 — Secrets never leave their boundary

Statement. A secret is write-only: no action returns its value, a sealed form is the only stored form, and no secret, token or private host enters the public repository or a published output.

Rationale. S09's secret aggregate and scripts/ci/no-private-refs.sh; the repository is public, so a leak is permanent.

Implications. A credential is referenced, never printed. A test asserts the manifest has no reveal action. A public output and the snapshot are scanned before publication.

Evidence. crates/actions/src/documents/secrets.rs; scripts/ci/no-private-refs.sh; .github/workflows/ci-public.yml (secret-scan).

P10 — The estate is one deployable service per concept, absorbed not duplicated

Statement. A service the organisation depends on is either this workspace's own code or an absorbed, contract-tested module behind an action. A second deployment of the same concept is retired, not maintained.

Rationale. ADR 0005 (the absorption sequence ends at #45; the V2 spine is unblocked) and the measured estate: the absorbed services are modules in this workspace, and the public repository cannot carry a hidden dependency on a private host.

Implications. A new integration adds an action and a client in this workspace; it does not add a runtime hop the programme cannot test. A retired service's data is migrated, not forked.

Evidence. docs/decisions/0005-absorption-sequence-and-repo-scope.md; crates/actions/src/ops/; apps/inference-router/.

Approval

The principles are proposed for P0's definition-set acceptance; the sponsor's acceptance is the adopting act. The Architecture Board charter — membership, commissioning authority and decision limits — is proposed for adoption with this catalogue; the board's rows and its board.decide action are T9's deliverable (issue #81, proposed). Until the board is convened, a principles change is a decision document on P0 with the programme architect and the SRO as reviewers.

Open gap (kata). The board is a charter here, not rows: T9's governance_body, architecture_contract and architecture_waiver tables are not built. A deviation cannot yet be waived as a row; it is recorded as a decision, and the waiver discipline (accepting owner, reason, cost, risk, reassessment date) is applied by hand. The gap is recorded as a kata candidate on the kata project.

Application

Every delivery project's architecture inception cites the principles it applies and names any deviation. A deviation is a decision document with the alternative and the consequence; when T9 lands, the same deviation becomes an architecture_waiver row with an accepting owner and a reassessment date, and a delivery design gate that resolves against a live contract refuses a project with no contract.

The principles are reviewed at each tranche review (P0 §7): a principle that no project applied, or a gate that never refused, is evidence that the principle or the gate is wrong.
