Vision and mandate

Programme: conveyor buildout · Owner: George · Status: adopted by P0 · Date: 2026-11-15

Purpose

The conveyor is the operating model for an organisation's work. It carries work as positions, projects, boards, cards, runs and approvals; it carries proof as runs, evidence, decisions and instruments; and it makes the organisation itself explicit as industry → department → job, with immutable releases and tenant-scoped bindings. It is one Rust application, not a fleet of services that each know a fragment of the model (docs/SPEC_V2.md §1, §2).

The programme exists to finish that model and to run it. V1 built the machine that carries work; V2 adds the organisation that works the machine. The last whole-tree V1 checkpoint measured 83 tables and 243 actions, with the registry past 290 served operations as S19–S21 landed (docs/SPEC_V2.md §1.1). Those are a floor, not a live figure.

Outcomes

  1. One model, one store. A programme, its projects, their work, their decisions and their evidence are rows in one Postgres database with one action registry, not concepts imported from other applications (docs/SPEC_V2.md §10).
  2. Jobs, not code paths. PM, kanban coach, kata, development and operations are configured positions that receive cards, decide with rules and laya, and generate with LLMs behind gates (docs/SPEC_V2.md §6).
  3. Every decision is auditable. A rule, a laya choice and a human decision produce the same decision row, pinned to the policy, refinement and configuration versions that produced it (docs/SPEC_V2.md §7).
  4. Every tool is governed. Each cluster service a job may call is a versioned, bound, audited toolkit; every call is ledgered; a destructive call without the tenant's configured approvals is refused (docs/SPEC_V2.md §11).
  5. The conveyor develops and operates itself under the gates it imposes on any work — with the gates that judge it outside its own reach (docs/SPEC_V2.md §9).
  6. The public can see and challenge the design. The repository is public, the programme site reads Postgres, and every published output has a stable URL; input arrives as GitHub issues and design pull requests, never as an in-app public account.

Boundary

  • Not a conversational agent. The agent platform is a user-interaction front end over MCP; it holds no runtime dependency and is not a second system of record (docs/SPEC_V2.md §1.2, D33).
  • Not customer care. care-bus-agents stays a standalone demo; the conveyor is for project, continuous-line and line-management work (docs/SPEC_V2.md §1.2, D48).
  • Not a document manager. The public outputs are the programme's intermediate work products; engineering documentation stays beside the code in docs/.
  • Not a rewrite of V1. V1's built slices are not re-opened; V2 extends them (docs/SPEC_V2.md, preamble).
  • Not an in-app community. Comments, accounts and moderation are out of frame; the public conversation is GitHub.

Who it serves

First, the organisation that builds it: the owner, the maintainer sessions and outside contributors working the programme in this repository. Then, opt-in tenants: a tenant that does not use a V2 aggregate does not ship it (docs/SPEC_V2.md §12, P10). The licensing frame is per-tenant and opt-in; there is no per-app delegation.

Mandate and success

P0's definition set is the programme's mandate: the programme does not start T1–T17 until this set is accepted and its briefs are the contracts those projects are held to (docs/plans/P0-programme-definition.md §1, §6).

The programme is succeeding when:

  • T12's one-organisation loop runs end to end, audited and within budget (docs/SPEC_V2.md §12);
  • a gate that never refuses is flagged as a defect, not celebrated (docs/SPEC_V2.md §14, R5);
  • every V1 and V2 project has a brief, a published inception analysis and architecture, and its build evidence is recorded on the project;
  • the programme site shows the measured truth — projects, expected outputs, published outputs and gaps — without a hand-maintained status.
