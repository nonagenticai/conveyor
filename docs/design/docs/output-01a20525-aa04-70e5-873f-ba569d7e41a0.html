Candidate Solutions — T13 Tool platform

The options were assessed against the tool spine's criteria in the inception analysis; the selected option is the one the architecture design implements.

Candidates

  • A — A broker-mediated tool spine. Four tables (tool, toolkit, tool_binding, tool_call), one tools.* action family, and seven broker steps: resolve binding → pinned version → ceiling → schema → dispatch → ledger → event.
  • B — Keep V1's eight external actions and wrap them. Each action keeps its direct dispatch and gains a thin audit wrapper.
  • C — Adopt nonagenticai_mcp_server as the runtime tool plane. Bind jobs to the MCP server's tools and let it own dispatch.
  • D — Per-job integrations. Each job calls its backend with its own client and credentials.

Criteria

  1. One control plane: no path to a backend bypasses the binding, the ceiling and the ledger.
  2. The effect ceiling is data, narrowed by the binding, never raised by the caller.
  3. Credentials are sealed and named by alias; no key, token or URL enters the compiled prompt.
  4. Input validation is closed (additionalProperties:false plus pattern and bounds) before dispatch.
  5. Object storage is tenant-prefixed and content-hashed, with no bucket administration.
  6. The path is guardable: a test can prove no handler calls a service directly.
  7. Migration cost is bounded: the V1 targets move in the same change, forward-only.

Options rejected

  • B (wrapper) — fails criterion 1: the direct dispatch remains a second control plane; the wrapper observes but cannot refuse. Rejected for the bypass risk the inception analysis records.
  • C (MCP runtime) — fails criteria 1–3 and D44: the server owns dispatch and credentials, the conveyor cannot write one ledger row per call or enforce its binding ceiling, and it would be a runtime dependency the programme forbids. It stays reference only.
  • D (per-job) — fails criteria 1–5: no pinned version, no ceiling, no shared ledger, credentials per job, and every integration is a new unaudited path. Rejected.

Selected: A. Its seven steps are the architecture design's "seven broker steps"; its scenarios are the T13 acceptance table (tool_platform.rs), including the direct-handler guard and the no-S3-key prompt check.
