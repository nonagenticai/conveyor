Context and boundary

T1 gives a project four things it does not have today: a baseline that does not move, a change request with an impact block and a person's decision, a WSJF score recomputed from four typed inputs, and a portfolio view of the in-flight set. It adds the dependency graph that the programme gate can read and that refuses a cycle at creation. It also adds the MSP programme-definition rows — tranches, benefits, benefit links, transitions and stakeholder profiles — so that a benefit is a measurement record and a tranche review is an approval with evidence.

The boundary is the T1 row of SPEC_V2 §12 and issue #72's Out of scope:

  • In: the tables and actions above, the requester/executor exclusion on approvals, the ten T1 acceptance scenarios, and the tests that prove them against real Postgres.
  • Out: the decision ladder (T2), the PM job (T3), cadence materialisation and PI planning (T10), the benefits-realization procedure (T10), metrics (T11), and any migration or retirement of the V1 outline tree. The Portfolio page's WSJF-backlog, cadence and capacity tabs stay fixtures; only the in-flight set becomes live.

The engine already provides the pattern every new action follows: a declared ActionSpec, a tenant-scoped transaction, If-Match on edits, an outbox event, and the generated HTTP/MCP/OpenAPI surface (crates/actions/src/spec.rs, crates/actions/src/invoke.rs). T1 adds rows and actions; it does not add a second execution path.

Architecture artefacts

The Preliminary-phase PSA set at inception:

Principles applied. P1 (one record per fact: the edge table is the dependency source, the gate's fallback is bounded), P3 (no transition without an action; every new state change is an action), P4 (the executor never approves its own work; the requester exclusion), P10 (no portfolio row), P11 (the in-flight set and approval policies are tenant rows, not code constants).

Requirements. §5.3 (baseline ≠ forecast; plan ≠ evidence), §5.4 (gates and dual control), §5.5 (the register), §8.2 (WSJF arithmetic), §8.3 (MSP rows and refusals), §10.3 (the tables) and §12 T1 (the slice gate).

Stakeholder map. The programme's sponsoring group (tranche authorisation and benefit approval), the SRO (benefit ownership and the coherent capability), the BCM (each benefit and its transition), the PM (WBS, baseline, change control) and the project delivery teams (the WBS rows they accept). The conveyor's own buildout runs under the same positions; T1 makes those positions rows, not prose.

Driver, goal and objective. The driver is a programme that cannot answer what it promised, what changed and which benefit the work serves. The goal is a plan spine where the promise is frozen, the change is controlled, the priority is arithmetic and the benefit is measured. The objective for this project is the ten-scenario gate above.

Solution concept. Reuse the engine's aggregate/action/tenancy patterns; add one migration set, one plan-spine action family, the dependency edge table and the MSP rows; change only the approval decision rule; prove every scenario locally against Postgres. No new subsystem, no external service, no engine run.

HLD/SD status at inception. This is the High-Level Design. The detailed design (column-level constraints, the recursive CTE, the baseline snapshot's exact payload, the console screens) lands in the T1 build units; the decision record above is the boundary this design must not cross. The project operates under the live blueprint and T0's contracts; a deviation is a decision record (§8.1), not a silent fork.
