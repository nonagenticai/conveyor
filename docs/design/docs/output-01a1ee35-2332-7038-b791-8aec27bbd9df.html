T4 — Architecture design

Project: T4 — Kanban coach · Track: v2 · Tranche: 4 · Plan: docs/SPEC_V2.md §12 Unit: #75 (this design is dependency-shaping work; blocked-by T3 and P0) Measured at: main@61edfcf8, 2026-11-18 · Project row: active, meta.depends_on = ["T3", "P0"]

Context and boundary

T4 owns the path from one interruption to one bounded response: capture from the existing failure handler, one coach card, a triage decision over closed sets, at most one remedy, escalation to a human when the same signature repeats, and a kata candidate when the class is systemic. It is an ordinary job under SPEC_V2 §6, not a subsystem: its authority and scope are data on its binding, not branches in code.

It must fit the blueprint: one Rust application split into pure domain types, one SQL store, per-aggregate action modules, and HTTP/API/auth/event/render crates assembled by apps/server; every mutation is an ActionSpec projected to HTTP, OpenAPI, MCP and the CLI; events are written in the same transaction as the state change; no new port, same binary, same Postgres database (SPEC_V2 §10.6).

It must not duplicate:

  • the run state machine — run already exists (migrations/0002_domain.sql:run);
  • the decision ladder and its policies — T2 owns their semantics; T4 consumes a decision row;
  • PM charter, gates and closure — T3;
  • the six-Gets kata — T5; T4 only emits a candidate through the existing kata.open process;
  • lessons (T8), flow metrics (T11) and operations remedies (T7).

Decisions

D-T4-1 — Triage and remedy are one ladder decision over two closed sets, not prose and not an LLM choice. Alternative: the coach agent selects the remedy, which is V1's open rung and measured "0 of 22 blocks" (SPEC_V2 §6.2). Consequence: the build seeds five class options and six remedy options and a decision policy; below-threshold confidence produces ask. Trace: SPEC_V2 §6.2, §12 T4.

D-T4-2 — The signature is deterministic and stored; uniqueness is a partial unique index on (tenant_id, source_card_id, signature) where status = 'open'. Alternative A: an LLM-derived signature — non-deterministic and unindexable. Alternative B: counting coach runs per card, which is today's COACH_CHAIN_MAX and was evaded to 278 runs (crates/actions/src/board/pull.rs:err_card). Consequence: a migration adds the index; the existing cap remains as a second, coarser guard. Trace: SPEC_V2 §6.2 recursion guard, §12 T4.

D-T4-3 — The coach card is a child of the interrupted card on that card's own board, in the board's waiting lane, with a coach_interruption card type. Alternative A: a dedicated coach board — refused because board.project_id is NOT NULL (migrations/0002_domain.sql:board) and the organisation seed carries no board schema, so a coach board would require a new tenant-wide project. Alternative B: a root run only — refused by "exactly one coach card". Consequence: the measured unreadable board is prevented by the per-signature uniqueness (D-T4-2) and by excluding coach_interruption cards from flow and WIP reads, not by a separate board. Trace: SPEC_V2 §6.2.

D-T4-4 — A repeat same-signature interruption escalates to a human approval and opens no coach card; a coach about a coach is refused at the handler. Alternative: a second coach card, the duplicate-card failure. Consequence: escalation is approvals.request; the refusal predicate stays in err_card and keys off COACH_ERROR_PROCESS. Trace: SPEC_V2 §6.2, §6.6, §5.4.

D-T4-5 — A systemic class is handed to the existing kata.open process; six Gets remain T5. Alternative: implement kata in T4, duplicating T5 and breaking the tranche boundary. Consequence: today the seed calls kata.open unconditionally as step 2 of cap.kanban_coach.handle_error (seed/processes/named.yaml:cap.kanban_coach.handle_error); the seed release moves that handoff behind the triage decision — coach.triage starts the child run when the class is conveyor_defect or job_defect, and the unconditional child step is removed. T4 asserts exactly one kata child run per systemic interruption and none for the other three classes. Trace: SPEC_V2 §12 T4 and T5.

D-T4-6 — The coach's action scope is the remedy set only; the agent keeps read/narrate scope. Alternative: grant the agent write actions, which is the measured failed rung. Consequence: the remedy step is a system step after the decision, not an agent tool call; the agent attaches only the diagnosis narrative. Trace: SPEC_V2 §6.2 "never do the work", §6.7 authority matrix.

Acceptance

The project's measured gate is: "an injected failure yields exactly one coach card and one remedy; a repeat signature escalates; no coach card about a coach card; a systemic class opens a kata" (SPEC_V2 §12, row T4). Each scenario maps to one clause; (to create at ...) marks a check the T4 build unit adds. This design claims no test has run.

  1. Exactly one coach card and one remedy. Given a card whose run fails once, when the failure handler runs, then one open interruption row, one coach card and one applied remedy exist, and a redelivery adds none. Verify: cargo test --test coach_injected_failure (to create at apps/server/tests/coach_injected_failure.rs).
  2. A repeat signature escalates. Given a second failure with the same signature inside the window, when the handler runs, then no new coach card exists and one approval is open. Verify: cargo test --test coach_repeat_signature (to create at apps/server/tests/coach_repeat_signature.rs).
  3. No coach card about a coach card. The refusal predicate already exists at crates/actions/src/board/pull.rs:COACH_ERROR_PROCESS; the behavioural test is Verify: cargo test --test coach_no_self_reference (to create at apps/server/tests/coach_no_self_reference.rs); the structural check is rg -n 'no coach about a coach' crates/actions/src/board/pull.rs.
  4. A systemic class opens a kata. Given a triage class marked systemic, when the coach process runs, then exactly one kata.open child run exists. Verify: cargo test --test coach_kata_handoff (to create at apps/server/tests/coach_kata_handoff.rs). The seed wiring has a test at apps/server/tests/catalogue_install.rs:one_command_installs_a_runnable_tenant_from_a_fresh_database; it is not run for this design.
  5. The closed sets refuse. An unknown class or remedy is refused with 422 and writes no row. Verify: cargo test --test coach_closed_sets (to create at apps/server/tests/coach_closed_sets.rs).
  6. Uniqueness under concurrency. Two concurrent handlers for one interruption produce one row. Verify: cargo test --test coach_concurrent_signature (to create at apps/server/tests/coach_concurrent_signature.rs).

Architecture artefacts

The PSA set at inception

  • Principles applied. P2 — an LLM never selects, routes, classifies or approves: the triage class and the remedy are a decision-ladder record, never a generated choice. P3 — no work without a card, no transition without an action, no completion without evidence: each remedy is an action and each interruption carries its evidence. P4 — the executor never approves its own work: an escalation is an approval to a human, approver ≠ executor. P6 — the coach is an ordinary job on the same catalogue, card, run and approval primitives. P10 — no speculative aggregate: the one new table exists because this procedure writes it and the repeat/escalation measure reads it. P11 — the closed symptom sets, the escalation window and the chain cap are versioned tenant rows with platform defaults, not code constants.
  • Requirements. SPEC_V2 §6.2 (the coach role, the interruption taxonomy and the closed remedy set), §6.7 (the authority matrix: the coach never does the work), §9.4 (the kata handoff), §5.4 (gates and dual control), §10.4 (the action and event names), §12 row T4 (the measured gate).
  • Stakeholder map. The delivery team whose card was interrupted (the remedy must preserve its work); the PM (flow and WIP); the kata owner (a systemic class); the human approver (escalation); the programme's governance and audit (every remedy is an action with an event).
  • Driver, goal and objective. Driver: a failure with no bounded response either stalls the card or produces a serial chain of coach runs (278 terminal coach runs measured on 2026-11-15 because the live-run guard cannot see terminal runs — recorded at crates/actions/src/board/pull.rs:err_card). Goal: every interruption yields exactly one coach card and at most one remedy, and a repeat signature escalates instead of repeating. Objective: repeat interruptions convert into a kata candidate — a measured change — rather than repeated advice.
  • Solution concept. Capture at the existing failure handler; one coach_interruption row keyed by a deterministic signature; a triage decision over two closed sets through the T2 ladder; one remedy applied through existing actions; escalation as an approval; a systemic class handed to kata.open. No new runtime, port or store.

Migration and rollout

  • Migration 0052_t4_coach.sql (to create): coach_interruption with CHECK constraints on class, remedy and status; partial unique index (tenant_id, source_card_id, signature) WHERE status = 'open'; an index on (tenant_id, status, created_at). Additive only; card and run gain no column.
  • Seed: a new release of cap.kanban_coach.handle_error adding the remedy step after triage and removing the unconditional kata.open child step (D-T4-5); a new capability_agent release with read/narrate scope (documents.compose|get|list, cards.get|comment); a coach_interruption card type and the coach-card exclusion in the board reads. The seed never updates a published row — a change is a new release.
  • Actions: coach.* as ActionSpecs in a new crates/actions/src/coach/ module (to create), projected to HTTP, MCP and the CLI; no new route prefix.
  • Order: migration, actions, seed release, bind the coach job on a test tenant, inject one failure, verify the four gate clauses, then enable for other tenants.
  • Rollback: retire the coach binding so new runs refuse 409 job_binding_stale; in-flight runs finish; interruption rows remain as history. No new port and no second store (§10.6).
