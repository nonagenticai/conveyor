T13 Tool platform — architecture design

This design adds the tool spine to the conveyor: one broker, four tables, one action family, an effect ceiling that is data, a closed input schema, and a storage adapter a job can use without ever seeing a key. It is the design T14 (estate toolkits), T15 (BYO), T16 (ingestion) and T17 (authoring) build on, and the one T6/T7 jobs call tools through.

Context and boundary

  • Owns: the tool, toolkit, tool_binding and tool_call tables; the tools.* action family; the broker's seven steps (resolve binding → pinned version → ceiling → schema → dispatch → ledger → event); the storage adapter's key discipline.
  • Does not own: credentials (V1 secret, referenced by alias), approvals (the tenant's existing approval_policy/approval_decision and the destructive gate), the model (inference), the backends' health (their own probes), and the card/run state machine (a tool call never moves a card).
  • The one principle: a job's only path to a backend is tools.call. V1's eight external actions migrate onto toolkit operations; the externals_declared guard keeps a second control plane from reappearing.

The seven broker steps: (1) resolve the binding for the run/step; (2) resolve the pinned toolkit version and the tool; (3) check the effect ceiling and the tenant's approvals for a destructive call; (4) validate the input against the closed schema (422 tool_input_invalid, zero network calls); (5) dispatch to the destination alias with the credential from the sealed profile; (6) write one tool_call row; (7) emit tool.called.

Decisions

  • D44 — no runtime dependency on nonagenticai_mcp_server; its toolkits stay reference.
  • D57 — object storage is the MinIO instance directly, tenant-separated: every key is tenant/<tenant_id>/project/<project_id>/run/<run_id>/<name>, server-side encrypted, content-hashed, size-capped, with no bucket administration and no S3 key in the prompt.
  • No second control plane — the eight V1 external actions are moved onto toolkit operations in the same PR; the externals guard proves no handler calls a service directly.
  • The ceiling is data — tool.effect is the maximum; tool_binding.effect_ceiling narrows it; a request above the ceiling is 403 tool_effect_forbidden; a destructive call without the tenant's configured approvals is refused before the destination is called.
  • Validation is closed — validate_input gains pattern, minimum/maximum, minLength/maxLength and minItems/maxItems, and a tool-specific 422 tool_input_invalid with the offending field.
  • Credentials are sealed — a binding names a credential_alias; the broker resolves it from secret; the compiled prompt carries no key, token or URL.

Architecture artefacts

None are mandatory for this slice: the TOGAF ADM capability (T9) is not yet built, so there is no ADM phase or plateau to satisfy and no typed artefact catalogue to fill. This design document is the slice's architecture artefact; its reviewer is the T13 issue owner, and its acceptance is the scenario table above. When T9 lands, T13's tables and actions enter the artefact repository as a derivation of the blueprint.

Migration and rollout

Forward-only, one migration 0052. The V1 external actions move onto toolkit operations in the same change; each destination alias is registered as a toolkit key@version with its tools and schemas. Rollout is by binding: a toolkit is published, then bound to a job, then called. Rollback is by retiring/unbinding the toolkit — new runs refuse 409 tool_not_ready, in-flight runs finish, and no migration is reversed.
