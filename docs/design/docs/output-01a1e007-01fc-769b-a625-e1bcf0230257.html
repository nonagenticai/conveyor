Project brief template

Programme: conveyor buildout · Status: adopted by P0 · Date: 2026-11-15 Source: docs/plans/P0-programme-definition.md §4–§5

Every delivery project has one brief, published on the project with meta.category = project-brief. The brief is the contract the project is held to; it is not a plan summary.

The mandatory fields

FieldContent
OutcomeOne sentence: what is true after the project that is not true now
BoundaryIn scope, out of scope, and the existing surfaces it must not fork
Reuse sourcesPaths inside the conveyor, estate services/modules, upstream crates. Each with the analysis question it must answer
Inception unitsanalysis and architecture, the project's first two claims
DependenciesTyped: blocked-by, acceptance-blocked-by, blocks, related
AcceptanceA BDD scenario per part, each with a Verify: command or an executable gate
CapabilitiesThe organisation positions/capabilities that own it
PlanThe slice/S## plan path, or the T## SPEC_V2 section

The inception standard

Analysis — current state and reuse: for the project's capability, inventory the code that already exists (inside the conveyor repo, in the wider estate, and upstream), the contract and licence constraints, the build-vs-reuse decision, and the risks. It cites path:symbol inside the repo; outside, it names the capability, not a private host or URL.

Architecture — the project's design: aggregates, tables, actions, modules, integrations, the decision record, and acceptance. It must fit the blueprint; a deviation is a decision record, not a silent fork.

Both are documents on the project with meta.category set to analysis / architecture. Both are published when accepted. A project without both published is an inception gap; its build units are not claimed.

The brief's own rules

  • No invention. If the plan does not state a field, the brief says "not recorded — the inception analysis supplies it"; it does not fill the gap with a guess.
  • No private references. Name capabilities, not hosts, paths or credentials.
  • One page. A brief is read before every build unit; if it takes more than a page, it is a plan.
  • The brief is published, not filed. It appears on the project's workspace, in the Outputs register and at its stable public URL.

Worked example

programme/<project-key>/project-brief/ in this repository is the exported copy of every project's brief. The P0 set's own brief is the programme definition; the delivery briefs follow this template exactly.
