Phases

The profile runs the full ADM for software delivery: Preliminary once per organisation, then A–H per architecture initiative. It is a tailored profile, not a claim of TOGAF certification (docs/SPEC_V2.md §8.1's scope note).

A phase is not skippable in this profile: every phase closes on its mandatory set and its contract. The mechanical refusal (architecture.phases.advance, which names the missing artefact or the contract's state and writes no contract row — docs/plans/T9-architecture-capability.md §4.3) is T9's deliverable; until it exists, the programme architect's review enforces the rule.

Tailoring for this programme. Conveyor is one workspace with one data model and one delivery estate, so the typical initiative is a delivery project on an existing blueprint, not a new enterprise architecture. Its architecture inception is therefore a PSA (Phase A–E at the project-start plateau) under the blueprint, not a fresh B–D cycle. A project that changes the blueprint itself (a new aggregate, a new store, a new estate service) escalates to the HLD set and, if it changes the deployment or the technology standard, the SD set. The escalation rule is the one in the P0 plan §5: a deviation from the blueprint is a decision record, never a silent fork.

Requirements management is continuous, not a phase: the requirements catalogue types each requirement as condition/constraint/assumption/delta and trace-links it to the artefacts, contracts, cards and evidence that realise it (docs/SPEC_V2.md §8.5's trace chain).

Plateaus. The PSA is the project-start set. The HLD adds the business, data, application and technology views; the SD adds process, interface, migration and platform detail. A delivery project's brief names the plateau its own architecture inception must satisfy. The programme's default: every T-project inception satisfies the PSA; a project that changes the blueprint satisfies the HLD; a project that changes the estate satisfies the SD.

What this profile does not yet have. The adm_profile, artifact_type and architecture_contract rows are T9's deliverable (#81, proposed). This document is the baseline those rows will encode. Until they land, the profile is applied by review: a project's architecture inception is checked against this table by the programme architect, and the result is a decision/evidence document, not a gate row. A missing artefact is a visible gap in the project's checklist; it is not yet a mechanical refusal. The gap is recorded as a kata candidate on the kata project.

Contracts

Four contract kinds govern the phases (docs/SPEC_V2.md §8.1; docs/plans/T9-architecture-capability.md §4.3):

  1. Statement of Architecture Work (SAW) — opens Phase A: the assignment, scope, responsibilities and acceptance criteria; distinct from the designs produced under it. This P0 definition set is the programme's SAW-equivalent; each delivery project's brief plus its inception pair is the project's.
  2. Delivery contract — after Phase F: the delivery commitments and the method by which compliance will be assessed. In this programme the delivery contract is the project's accepted brief and its gate evidence; a change is a new version and re-opens the gate.
  3. Statement of intent / business usage agreement — at completion: intended use, ownership and measures of effectiveness. In this programme it is the closure review's decision record.
  4. Request for Architecture Work — Phase H: further architecture work when the current architecture no longer meets its purpose; the board reviews it.

A contract change is a new version and re-opens its gate; the approved version's body is immutable. When T9 lands, a delivery design gate resolves only against a live approved contract trace-linked to the delivery project — absent, draft or superseded all refuse and no approval row is written. Until then, the project's brief and its inception pair are the evidence the review uses.

Adoption

This profile is proposed as the programme's default adm_profile; P0's definition-set acceptance is the adopting act. Every delivery brief names the plateau its own architecture inception satisfies and the contract it operates under. The profile is reviewed at each tranche review against the maturity assessment: a mandatory artefact that no project produced, or a phase that never refused, is evidence that the profile is mis-tailored — and the correction is a decision record, not a silent edit.

Board and rows gap. The Architecture Board's charter, membership, commissioning authority and decision limits are proposed with PF-1. The board's governance_body rows, the adm_profile row and the architecture_contract rows are T9's; until then, the proposal is recorded by this document and the board's decisions are recorded as decision documents on P0. That gap is a kata candidate, not an exception to the phases.
