# S18-B — the `conveyor` arm's producer, its door, and the improvement verdict

Third commit of lane `s18-kata-improvement`. S18-A built the trend (step 2); this builds **steps
1, 3 and 4**: the producer, the arm's door, and the loop that records a verdict. Migration
**`0034_s18_kata_arm.sql`**.

## What "the conveyor arm" is, exactly

A `conveyor` run measures **the tenant's own `capability_agent`** against the suite. Per case, one
`benchmark.case.produce` job invokes `agent.run` with the instance's **problem statement** and takes
the agent's final text as the patch; the patch is then graded exactly as a `gold` patch is — one
`batch/v1` Job applies it and runs the instance's tests.

⛔ **Known limitation, recorded rather than hidden:** the agent has no repository tool. It answers
from the problem statement alone, so this arm measures the conveyor's *reasoning over a description
of the bug*, not its ability to read and edit a checkout. That is a real measurement of a real
configuration — and it is weaker than the `baseline` arm, which fetches the source — but nobody
should read a low `conveyor` rate as "the conveyor cannot fix bugs" until the agent has a
repository. The producer's module documentation and this paragraph are the two places that say so.
The same holds for the prompt: the arm sends no `prompt_ref` (see §Session 2), so it measures the
model over the producer's instruction, not the agent's configured prompt.

## The pieces

**The producer** (`apps/server/src/benchmark_producer.rs`, job kind `benchmark.case.produce`).
One job, one case, one `agent.run` — a tick may not make a model call (CONTRACT §19's "one bounded
tick"), so the driver enqueues and moves on. It reads the instance through `producer_instances_tx`,
which carries no `gold_patch`, no `test_patch` and no `fail_to_pass`: the answer key is never in the
model's context (S18 §8 trap 1). A typed refusal, an empty reply or an over-cap patch is
`produce_status='no_attempt'`, which the graded denominator withholds — never a model failure.

**The door** (`benchmark_runs.start`). `arm='conveyor'` now requires a subject: a capability agent
(an active one, resolved in the caller's tenant; a missing or non-active one is `409 arm_not_ready`
**before the first case**, S18 §5) and records `subject_version` at start, so the run pins the
version it measured (S18 §3) instead of joining a row an edit would have moved. A `procedure`
subject is refused with `arm_not_ready`: a procedure run is card-scoped and a benchmark instance is
not a card, so that producer needs a mapping that does not exist — the same honest refusal S17 gives
the `baseline` arm.

**The verdict** (job kind `benchmark.improvement.run`, enqueued by `benchmark_runs.start` when it is
given a `baseline_run_id`). It observes with `benchmark_runs.get` and judges with
`benchmark_runs.compare` — the two actions a person reading screen 14 calls, never a private path
(S18 §9.1) — and records `keep | revert | inconclusive` on the candidate run with the p-value in the
note. The rule is S18 §10 Q3: significant (p < 0.05) and positive is `keep`, significant and
negative is `revert`, everything else is `inconclusive`. It never starts a second candidate (Q4) and
never promotes (Q2).

**Liveness.** A producer that keeps failing must not hold a run live for ever: `benchmark_case.attempts`
is spent by each producer job and, at `MAX_PRODUCE_ATTEMPTS` (3), the driver writes `no_attempt`
itself. The reaper only catches a *dead* driver, not a live one that never finishes.

## Session 2 — the live path was dead, and is now proved (2026-11-09)

⛔ **The producer could not produce.** `produce()` called `invoke(..., action:"agent.run")`, but
`agent.run`'s handler refuses a direct invocation by construction — an internal action holds the
invocation transaction and no pool (`crates/actions/src/workflow/agent.rs:231`; the same defect
class `procedure_agent` fixed for `procedure.step`). Every `conveyor` case was therefore written
`no_attempt`, and the arm measured nothing. The missing test was the only thing that would show it.

The fix: `run_step` — the one seam `procedure.step` and `workflow.node` already share — is now
`pub`, and the producer drives it with its explicit, tool-less step input, carrying the agent row's
`max_turns`/`timeout_ms`. No action, scope, event, table or lock entry moved (**277 actions · 305
ops**). Two limitations are recorded rather than hidden: the arm is **tool-less**, and it sends **no
`prompt_ref`** — `agent@1` requires procedure/capability sources a benchmark run has no facts for, so
the ledger must not claim a prompt the loop never applied (`inference_call.prompt_ref` is NULL; the
call is `caller_kind='agent_run'`, `run_id = <benchmark_run id>` — no FK).

Proof: `apps/server/tests/benchmark_producer.rs`, **5/5**, each property a way the producer could
lie — one real model call carrying the problem statement and none of the answer key; an empty reply
is `no_attempt`; a 4xx is `no_attempt` and not a retried job; a 5xx is a retryable `JobFailure` with
the attempt spent; a re-delivery replays the idempotency key and buys no second call. Reversal: with
the old `invoke` call restored, 4/5 fail (the happy path records `no_attempt`). Regressions:
`agent_run` 1/1, `procedure_agent` 1/1, `benchmark_jobs` 8/8; fmt clean; clippy `-D warnings` on both
touched crates; `--check-lock` exit 0.
